## 一、这是什么

BossMonitor 最初是一个「7 路摄像头铺满一块大屏」的网页，后来长成了下面这套东西：

- **一块大屏**：多路实时画面（H.265 ws-flv 也能解），支持网格 / 自动铺满 / 自由摆放三种布局、单路放大、隐藏、隐私遮罩。
- **一个检测大脑**：画面移动、人形识别、**人脸识别（可建人脸库）**、**区域进出 / 徘徊**、**人形姿态（跌倒 / 举手 / 蹲下）**、**人员计数**。
- **一条推送链路**：钉钉群机器人 / 企业微信群机器人 / Telegram Bot 三端，带限流、合并、免打扰时段、静默期汇总。
- **一个常驻后端**：`server/` 下的 headless 服务 —— **把所有页面关掉，它照样在盯人、照样在推送**。
- **一套远程遥控**：在手机上私聊 Telegram 机器人发指令，就能静默推送、查岗要截图、重启服务，甚至重启整台机器。**静默哪些渠道可选** —— 默认只静默钉钉 + 企微（TG 留着收发指令），临时想改就在指令里写（`/silent 2 wecom`），长期想改在设置页配（见 5.6.1）。

核心设计取向：**同一份逻辑，不让它漂移两份**。前端和 Node 后端跑的是**同一批 composable 源码**（靠一层 `compat.mjs` 补上 `window` / `document` / `localStorage`），所以钉钉的加签、企微的限流、消息模板、静默策略在两边的行为天然一致。

## 二、核心能力

### 画面与播放

| 能力 | 说明 |
|---|---|
| 多路实时预览 | 网格（自适应列数）/ 自动铺满 / 自由摆放（拖拽改位置尺寸） |
| H.265 ws-flv | 用 Jessibuca（WASM 软解）在浏览器内解码，无需插件 |
| 主 / 子码流切换 | 网格里多路同看自动拉子码流降压；点开放大单路切主码流 |
| 解码路数保护 | `maxDecode` 限制并发解码路数，超出自动排队 |
| 单路放大 / 隐藏 | 未隐藏的通道可随时恢复；顶栏一键「恢复全部」 |
| 隐私遮罩 | 一键盖住整屏，可设自动遮罩时长与解锁密码（遮罩期间画面可继续播）；解锁密码**只存摘要、界面不回显**（见 5.15） |
| 盲视模式（单路） | 隐藏这一路画面但**解码与检测照常跑**；面板实时回答「还有没有在检测」（任意一项检测开着即算在跑）与「这一路会推送到哪些渠道」（见 5.16） |
| 屏幕常亮 | Web / Electron / iOS 三端统一开关，挂机值守必备 |

### 检测与分析

| 能力 | 实现 | 依赖模型 |
|---|---|---|
| 画面移动 | 帧差法，缩到 ~256px 灰度逐像素差分 | 无（零模型） |
| 人形识别 | YOLO 检测 COCO `person` | `yolo11n` / `yolo11s` |
| 人脸识别 | SCRFD 检测 + MobileFaceNet 512 维特征 + 余弦比对 | `scrfd-500m` + `mobilefacenet` |
| 区域规则 | 进出 / 徘徊（纯几何，靠跨帧轨迹连续性） | 无 |
| 人员流向 | 同人在时间窗内先后离开 A 区域、进入 B 区域（可串联 A→B→C），判定一次「走向」事件；零额外推理，只复用已算好的人脸 identity | 无（默认人脸档） |
| 人形姿态 | 17 关键点 → 跌倒 / 举手 / 蹲下 | `yolov8n-pose` |
| 人员计数 | 按配置间隔播报当前 / 累计人数 | 复用跟踪器 |
| 未录入人脸收集 | 认不出的脸自动进「待录入」队列，可一键录入人脸库 | — |

> 四项扩展能力（人脸 / 姿态 / 区域 / 计数）有两层开关：**全局总闸**（`options.face.enabled` 等）和**通道级分流**（`cam.aiExt`）。总闸关着时，通道级即使为 true 也不会有动作 —— 这一份判定集中在 `src/config/features.js`，前后端共用，不会出现「画面上显示开了、推送里说没开」。
>
> 同一个文件还提供 `activeDetects()` —— 「这一路开了哪些检测」的**全集**（画面变动 / 人形 / 人脸 / 姿态 / 区域 / 计数）。画面顶部的检测芯片与盲视面板的「检测运行中」都从这里取，两处不可能一个亮一个灭（见 5.16）。

### 推送与通知

- **三渠道**：钉钉（加签 + text/markdown）、企业微信（markdown + 图片 base64）、Telegram Bot（直接上传截图）。
- **各渠道独立限流**：`globalMinIntervalSec`（全局最小间隔）、`rateLimitPerMin`（每分钟上限）、超限合并策略（`merge` / `drop`）。
- **事件筛选**：按通道勾选推哪些事件类型（移动 / 人形 / 人脸 / 区域 / 姿态 / 计数）、按最小面积比过滤。
- **免打扰（静默）**：支持多个时段（如 `20:00-08:00` + `12:00-13:30`）和临时静默（`/silent 2`、`/until 08:00`），静默开始/结束都发提醒，静默期间的报警**收存起来、结束时汇总推送**。静默**可以只静默其中几个渠道**（默认钉钉 + 企微，刻意不含 TG —— 见 5.6）。
- **通道静默**：只让**指定的那一路**在指定时段对指定渠道不推送（`/csilent 门口 2`，或设置 → 监控通道 → 该路的「通道静默」）。与上面的整体静默是**并集**：任一命中即静默；一条事件同时被两边覆盖时只进整体汇总，不重复。三处刻意与整体静默不同（零报警不发汇总 / 只发给被静默的渠道 / 不发开始提醒）—— 见 5.6.2。
- **消息模板**：三端排版可自定义并实时预览（`推送模板` 页）。
- **关键事件单独提醒**（可选，默认关）：静默提醒 / 静默汇总 / 人脸命中三类事件，除正常渠道外**再私聊推给指定 TG 用户**（授权用户 + 额外 id）。人脸命中**不受静默影响** —— 见 5.5.1。
- **补图推送**：报警后补拍完整人形 / 人脸特写再补推一条。
- **状态巡检**：通道掉线推「监控异常」，恢复推「监控恢复」，持续异常按间隔重复提醒；另有定时巡检报告。
- **系统通知**：Web Notification / Electron 原生通知 / iOS 本地通知，三端统一封装。

## 三、整体架构

```
┌──────────────────────────────────────────────────────────────────────────┐
│                            展示端（同一份 frontend）                       │
│                                                                            │
│  浏览器 / macOS(Electron) / Windows / iOS(Capacitor) / 小程序(web-view)     │
│    ├─ 大屏画面    CameraTile × N ── Jessibuca(WASM) ── 摄像头 ws-flv/rtsp    │
│    ├─ 事件列表    EventPanel  ← IndexedDB(useEventStore)                    │
│    ├─ 设置抽屉    SettingsDrawer（14 个分页）                                │
│    └─ 纯前端模式下的检测与推送（默认；后端模式开启后本地停掉）                  │
└───────────────────────────────┬──────────────────────────────────────────┘
                                │ POST /api/config（把配置整体推给后端）
                                │ GET  /api/events（拉后端事件增量）
                                ▼
┌──────────────────────────────────────────────────────────────────────────┐
│                    常驻后端  server/headless-monitor.mjs                    │
│                                                                            │
│  摄像头流 ──ffmpeg──▶ JPEG 帧 ──onnxruntime-node──▶ 人形框                   │
│                              ├─ Tracker（复用前端 useTracker）──▶ 区域/徘徊/计数│
│                              ├─ SCRFD + MobileFaceNet ──▶ 人脸比对            │
│                              └─ YOLOv8n-pose ──▶ 姿态动作                     │
│                                                                            │
│  事件 ──▶ 推送调度（复用前端 useAlertPush 全套：三渠道 / 限流 / 合并 / 静默）    │
│       ──▶ SQLite(server/data/monitor.db) + 快照(server/data/shots/)          │
│                                                                            │
│  旁路：状态哨兵 watchdog（掉线告警 + 定时巡检）                                │
│        自愈重启 restart.mjs（端口释放→spawn→自检→回滚）                        │
│        系统级硬重启 hard-reboot.mjs（最后手段，默认关）                         │
│        Telegram 远程控制 tg-remote.mjs（getUpdates 长轮询）                    │
│        静默查岗 duty-check.mjs（/check duty）                                 │
└──────────────────────────────────────────────────────────────────────────┘
```

**为什么后端也要起一个 HTTP 服务**：它同时充当三件事 —— ① 给前端拉事件 / 推配置的 API；② 把 `dist/` 静态页直接 serve 出去（所以一台机器只跑 `npm run server`，浏览器打开 `http://<ip>:8787` 就能看大屏）；③ 钉钉 / 企微 / Telegram 的**反向代理**（官方接口都没有 CORS 响应头，浏览器直连必被拦）。

## 五、运行逻辑

### 5.1 两种运行模式

这是理解整个项目的关键。同一套代码有两个「谁是大脑」的选择：

| | **纯前端模式**（默认） | **后端检测模式** |
|---|---|---|
| 谁做检测 | 浏览器里的 Web Worker（ORT Web） | `server/` 的 Node 进程（onnxruntime-node） |
| 谁发推送 | 页面里的 `useAlertPush` | 服务端 `notify.mjs`（同一份 `useAlertPush`） |
| 关掉页面会怎样 | **停止检测与推送**（画面也没了） | **照常检测、照常推送** |
| 事件存在哪 | IndexedDB | SQLite + `shots/` 快照 |
| 怎么开启 | 默认 | 设置 → 检测识别 → 「后端检测服务」打开 |

开启后端模式后会发生三件事：

1. 前端把**当前整份配置**（含每路流地址、区域、推送凭据、人脸库）POST 到 `POST /api/config`，后端落盘并热生效 —— **正常情况下你不需要手改 `server/config.json`**。
2. 前端把各通道的本地 AI 检测临时置为关闭（`App.vue` 把 `aiEnabled` 置 false 传给画面），运动检测保留（几乎不占资源，且只对当前在看的画面有意义）。
3. 前端改为轮询 `GET /api/events?since=<上次毫秒时间戳>`、`GET /api/status`，把后端事件合进同一份事件流展示。

> 前端配置里的后端地址默认是 `http://10.0.0.12:8787`（那台常驻设备的局域网地址，见 `DEFAULT_BACKEND_URL`）。换机器记得改这里。
>
> 这两种模式还决定了**登录门禁拦在哪一层**：前端模式未登录不加载大屏，后端模式登录页只是一层遮罩（见 5.14）。
>
> **配置同步是双向的**：除了上面第 1 条（前端 → 后端），后端还能被**拉回去**（`GET /api/config`）—— 局域网里另一台机器打开同一个地址时，先把它手上那份取回来，而不是把自己那份空的推上去。开开关的瞬间会先判断"该拉还是该推"，见 [5.18](#518-配置双向同步局域网多台机器看同一份配置)。

### 5.2 「一份代码跑在两个运行时」

后端要复用前端逻辑，靠 `server/compat.mjs` 补三样东西：

| 需要补的 | 用途 |
|---|---|
| `window` | 运行环境判断、`crypto.subtle` |
| `document` | canvas（图片压缩 / 人脸对齐），由 `imageops.mjs` 提供最小实现 |
| `localStorage` | 推送统计持久化，落成 `server/data/localstorage.json`（写盘 300ms 防抖） |

⚠️ **必须在 import 任何前端模块之前**调用 `installBackendCompat()`。

所以像 `useAlertPush.js`（推送调度）、`useDingTalk.js`（加签）、`useTracker.js`（跟踪器）、`features.js`（能力判定）这些文件是**前后端共用的同一份源码**。前端改了推送策略，后端下次启动自动跟着变。

### 5.3 后端检测流水线

```
摄像头流
  │  ① source.mjs：rtsp:// / http-flv 直接给 ffmpeg；
  │     ws:// / wss:// 先用 ws 客户端收二进制帧，原样灌进 ffmpeg stdin（-f flv）
  ▼
ffmpeg  ── `-f image2pipe -vcodec mjpeg` ──▶ JPEG 连续字节流
  │  ② JPEGFrameSplitter 按 SOI/EOI 切成一个个 Buffer
  ▼
detector.mjs（onnxruntime-node）
  │  ③ 人形检测（yolo11n / yolo11s）→ person 框
  ▼
analyzer.mjs（每路一个实例）
  │  ④ Tracker 跨帧关联，给出稳定的身份 id
  │  ⑤ 人脸：只在**检出人形的帧**上跑 SCRFD + MobileFaceNet，同一个人靠轨迹去重
  │  ⑥ 姿态：同样只跑在有人的帧上，17 关键点判跌倒/举手/蹲下
  │  ⑦ 区域：进出 / 徘徊（纯几何，靠轨迹连续性）
  ▼
事件 ──┬──▶ store.mjs：正文进 SQLite，快照 JPEG 落 shots/，库里只存相对路径
       ├──▶ notify.mjs：交给 useAlertPush（限流 / 合并 / 静默判断）→ 钉钉 / 企微 / TG
       └──▶ GET /api/events 供前端轮询
```

**几个刻意的性能约定（实测结论，别改）**：

- 人脸、姿态**只在检出人形的帧上才跑**，空帧直接跳过；
- 同一个人的脸**不会每个周期都重提特征**（靠轨迹去重），否则 2fps 下站着不动的人会白烧大量算力；
- 区域 / 徘徊 / 计数是**纯几何**的，不需要任何模型。

### 5.4 关于 ffmpeg（最容易踩的坑）

- 市面平台的 ws-flv 大量使用**增强型 FLV（E-FLV）**：视频 tag 里 `codecId=0`，真正的编码放在 FourCC 里（`hvc1` = H.265）。
- `ffmpeg-static` 自带的是 **6.0，解析不了**，表现是 `Decoder (codec none) not found for input stream #0:0`，**而且一行错误日志都不打**，只是静默不出帧。
- 所以本项目的 ffmpeg 查找顺序是：

  ```
  显式指定（config.json 的 ffmpegPath / 环境变量 BOSSMONITOR_FFMPEG）
    → server/.cache/ffmpeg/<版本>/（首次运行自动下载，≥7）
    → ffmpeg-static（6.0，只能解普通 H.264）
    → 系统 PATH
  ```

- 完全离线时设 `BOSSMONITOR_FFMPEG_OFFLINE=1`，只查缓存不下载。
- 想提前预取：`npm run ffmpeg:fetch`。
- ⚠️ 上面第 1 条读的是**环境变量 `MONITOR_CONFIG` 指定的那份配置**（没设才是 `server/config.json`），与后端进程用的配置保持同一份 —— 详见 5.17。
- ⚠️ 「探测 ffmpeg 版本」是一次 `spawnSync` 同步调用（失败还会重试 3 次、每次同步睡 400ms）。所以它**绝不能被放进每请求路径**（`/api/status` 曾经就是），见 **5.17**。

### 5.5 推送调度（`useAlertPush` 内部）

```
事件进来
  │
  ├─ ① 静默判断：当前在免打扰窗口内？
  │     ├─ 是 → 存进 silentBuffer（只存文字字段），等结束/查岗时汇总，本次结束
  │     └─ 否 → 继续
  │
  ├─ ② 通道筛选：这一路勾了「要推送」吗？这个事件类型勾了吗？
  │     没勾 → 结束（通道无关的事件直接丢弃，不会误推）
  │
  ├─ ③ 每渠道独立限流：
  │     · globalMinIntervalSec  两条之间的全局最小间隔
  │     · rateLimitPerMin       每分钟上限
  │     · 超限 → 按 overflowMode 合并（merge）或丢弃（drop）
  │
  └─ ④ 按渠道协议发送
        钉钉：加签（HMAC-SHA256）→ text / markdown（图片需公网图床）
        企微：markdown + image base64（直接发截图，不用图床）
        TG  ：sendPhoto 直接上传文件
```

#### 5.5.1 关键事件单独提醒（TG 私聊推送）

场景：静默时段 / 深更半夜，主渠道发到群里没人看；而**授权用户**（自己人）需要第一时间单独收到。

配置位置：`TG 推送 → 📨 关键事件单独提醒`（字段 `options.telegram.directPush`）。

| 项 | 说明 |
|---|---|
| `enabled` | 总开关，**默认关**（不打开就完全不影响现有行为） |
| `events.silence` / `events.summary` / `events.face` | 三类事件各自开关：静默提醒 / 静默汇总 / 人脸命中。判据是 `!== false`，即**缺省视为开** |
| `chatIds` | 额外接收人（Telegram 用户 id，纯数字） |

几个关键取舍：

- **接收人 = 授权用户名单（`telegram.remote.allowUserIds`）+ `chatIds`**，去重、去空，并**排除主会话 `telegram.chatId`**（不排除会把同一条消息发两遍）。`chatIds` 是可选的补充项，留空也能用 —— 授权用户本来就是私聊过机器人的自己人。
- **⚠️ Telegram 的硬限制：机器人不能主动给「从没跟它对话过」的用户发消息**（会返回 `chat not found` / 403）。所以新接收人必须**先在 TG 里私聊机器人发一条任意消息**把会话打开。设置页有这个提示。
- **人脸命中不受静默影响**（刻意为之）：静默的本意是「别打扰」，而这个开关存在的唯一理由恰恰是「静默了也想第一时间知道库里的人来了」。跟着静默一起收存，它就和普通报警没区别了。
- **只在「命中在库人脸」时私聊**：判据是 `type === 'face' && faceName` 非空。陌生人脸**不**私聊 —— 否则门口路过一个人就打一条，比不静默还吵。
- **带的是事件原图**（事发那一帧，取 `record.shot || record.thumb`），不是人脸特写 —— 私聊要回答的是「现场怎么回事」，放大的脸另由 `pushFaceShot` 单独补一条。三端共用这一份图片，详见 5.46。
- **逐个串行发送**：TG 对同一 Bot 连发有限流，接收人一多并发轰过去会被 429 全丢；慢一点但一条不落更划算。
- **不计入推送统计**：这条消息是同一事件的补充副本，主渠道那边已经计过一次；再计一遍会让「累计推送 / 成功率」随接收人数量膨胀，那个数字就不再代表报警量了。
- **设置页「试发」不打扰别人**：「试发一条开始提醒」「试发一条」都显式带 `test: true`，只发主会话，不给所有接收人发私聊。

### 5.6 静默（免打扰）

- **定时时段**：`silent.slots`，可配多段（默认 `20:00-08:00` 与 `12:00-13:30`），跨零点自动处理。
- **临时静默**：`/silent 2 [渠道]` 或 `/until 08:00 [渠道]` 开启，`silent.tempUntil` 记截止时刻、`silent.tempSince` 记**真实开始时刻**。
- **开始 / 结束都推提醒**：开启前推「免打扰已开启」，结束时推「免打扰已结束」+ **期间积压事件的汇总**。
- 静默期间的事件不丢 —— 统一收存，结束或查岗时汇总发出。
- 汇总正文复用同一个 `buildSilentSummary`，保证「结束汇总」和「查岗汇总」口径一致；其中「**人脸命中（在库）**」单独成区（见 5.7.1）。

#### 5.6.1 「静默哪些渠道」——两处勾选，语义完全不同

这是最容易被混淆的一点，所以配置项刻意分成两个、互不牵连：

| 勾选项 | 配置字段 | 管的是什么 | 默认 |
|---|---|---|---|
| `报警提醒 → 静默时段` 下的「暂停推送的渠道」 | `silent.channels` | **定时时段**（夜间 / 午休那两场）内暂停哪些渠道 | 三端全勾 |
| `TG 推送 → 远程控制 → 可用指令` 下的「默认静默哪些渠道」 | `telegram.remote.silentChannels` | 手机上发 `/silent`、`/until` **不写渠道时**静默哪几端 | **钉钉 + 企微** |

- **远程默认为什么不含 TG**：TG 是**下发指令的通道**。把 TG 一起静默掉，连「静默开没开、还剩多久」的回执都收不到，等于把自己锁在门外。想连 TG 一起静默当然可以，显式勾上或指令里写 `/silent 2 tg` 即可。
- **指令可临时覆盖**：`/silent 2 wecom`、`/silent 2 ding,tg`。渠道名不区分大小写，支持 `ding` / `dingtalk` / `dd` / `钉钉`、`wecom` / `wx` / `企微` / `企业微信`、`tg` / `telegram` / `电报`；分隔符可以是空格、`,`、`，`、`、`、`/`、`|`。认不出的名字会**报错点名**，不会静默照做。同一批渠道里重复写只算一次。
- **回执里会列清楚**：开启静默的回执与 `/status` 都会写明「静默渠道：钉钉 + 企微（默认渠道）」；指令里临时指定的则标「（本次指定）」。
- **空数组 ≠ 用默认值**：把渠道全部取消勾选，是「一个都不选」，不是「没配」—— 这时远程指令会**直接拒绝执行并提示**，而不是悄悄回落成默认那两个（否则"取消勾选反而静默了钉钉 + 企微"，比不选还糟）。前端手动开启临时静默时同理，`startTempSilent` 最内层也有一道同样的守卫。
- **勾了但没配好的渠道会被跳过**：只静默「启用且有凭据」的渠道（`notifier.channels()`），被跳过的会在回执里点名说明。一个可用渠道都没有 → 同样拒绝开启。
- **「静默提醒」本身不受渠道勾选影响**：免打扰开始/结束那条提醒走 `restrictIds()`，刻意不按渠道勾选裁剪，一律发给**当前已配置好的渠道** —— 免得「静默了钉钉」连静默开始提醒都收不到。
- **前端手动「开启临时静默」的渠道初值跟随这份默认**：同一个概念不让用户配两遍。想改就改上面那一处。

#### 5.6.2 通道静默（只静默某一路）

上面那套静默是**全局**的：一静就三端全不推、所有通道一起安静。但真实需求常常是「只有门口这一路晚上别吵我，电梯照常推」。这就是**通道静默**。

配置位置：**设置 → 监控通道 → 每一路卡片里的「通道静默」**（挂在 `cameras[].silent` 上）。

| 字段 | 说明 |
|---|---|
| `enabled` | 这一路的**定时**静默开关 |
| `slots` | 每日时段，可多段，支持跨零点（如 `19:00 ~ 08:00`） |
| `channels` | 定时时段内静默**哪几个**渠道 |
| `tempUntil` / `tempSince` / `tempChannels` / `tempLabel` | 远程指令下发的**临时**静默（与全局临时静默同构） |

**与整体静默的关系是「并集」**：对某个渠道而言，**全局静默 ∨ 该路的通道静默** 任一命中，它就被静默。通道静默是全局静默的补充，不是替代 —— 全局覆盖全通道，通道静默覆盖指定的那几路。

```
渠道「钉钉」这条事件要不要实时推？
  ├─ 整体静默命中钉钉  → 不推（进整体汇总）
  ├─ 这一路的通道静默命中钉钉 → 不推（进这一路的汇总）
  └─ 两边都没命中 → 正常实时推
```

**汇总归属：同一条事件只进一个汇总。** 一条事件如果**同时**被两边覆盖，按「**汇总归整体**」处理 —— 它进整体汇总就够了，通道汇总里不再出现（否则同一条会在两个汇总里各出现一次，看起来像重复报警）。

通道静默与全局静默有**三处刻意不同**，改代码前请先看理由：

| | 全局静默 | 通道静默 |
|---|---|---|
| 零报警时要不要发「已结束」 | **要发**（否则用户以为静默卡住了） | **不发** —— 通道静默图的就是"这一路这段别吵我"，为"什么都没发生"再补一条通知，等于把刚省下的打扰又还回去 |
| 汇总发给谁 | 全部已配置渠道 | **只发给被静默的那几个渠道**（其余渠道这些事件早就实时收到了，再发一份就是重复打扰） |
| 要不要发「开始提醒」 | 发 | **不发** —— 通道静默多是按天固定时段，每天两条提醒太吵；要确认有没有生效用 `/cams` 查 |

其余实现要点：

- **时段判定只有一份实现**（`defaults.js` 的 `hmToMinutes` / `parseSilentSlots` / `matchSilentSlotAt`），全局静默与通道静默共用。各写一份迟早出现「全局静默 22-2 跨零点、通道静默却不跨」这种对不上的行为。
- **判定「被静默」而不是「本来就不推」**：用 `checkChannel(..., ignoreQuiet=true).ok` 先算出「这条事件本来能推的渠道」，再与静默渠道求交集。不区分就会把「这一路自己关了某渠道 / 变动幅度低于阈值」也算进收存，汇总里冒出一堆根本没打算推的事件。
- **`cam.silent` 挂在通道上**，不另开一张按通道 id 索引的表：通道会被增删、改名、拖拽排序，另开一张表就得自己维护「通道删了要清、重命名要跟」，迟早留下指向不存在通道的僵尸配置。通道被删时对应的缓冲与定时器也一并清掉（否则汇总会发往不存在的通道，且 Map 会随反复增删无限长大）。
- **收存的心跳先跑通道那套**：`tickSilentWindow` 里的全局逻辑有好几处 `early return`，把通道检查放在后面会被跳过，表现成「配了通道静默却永远不结算」。
- **展示层与引擎同源**：设置页每一路的状态文案直接调 `camSilentState()`（引擎用的同一个函数），不自己算一份 —— 否则会出现「界面显示静默中、实际没静默」。
- **渠道勾选允许清空**（与「远程静默默认渠道」刻意不同）：这里是长期配置，先清空再逐个勾很自然；空数组在 `camSilentState` 里就是不生效，行为明确。
- **临时静默是运行期状态**：与全局临时静默一样只存在于内存（进程重启即失效，不会跟着配置落盘）。长期固定的时段请配在 `slots` 里。

### 5.7 静默查岗 `/check duty`

场景：半夜开着静默，人不在手机旁边，想中途看一眼积压了什么。

| 语义 | 实现 |
|---|---|
| 首次查岗 | 区间 = **静默窗口开始 → 现在**，推汇总 + 区间内**全部截图** |
| 再次查岗 | 区间 = **上次查岗 → 现在**（增量，不重复推） |
| 不在静默时段 | 直接回提示，不推任何东西 |
| 静默中无事件 / 已查完 | 分别给明确提示 |

几个关键实现取舍：

- **查数据库而不是内存缓冲**：`silentBuffer` 里只存文字字段、**没有截图路径**，满足不了「图片全部推过来」。改查 `events` 表拿 `thumb` 再读文件，顺带解决了「进程重启后缓冲清空」的问题。
- **游标用 `created_at` 而不是 `time`**：`time` 是分析器判定时刻，落库在它之后；按 `time` 做游标会永久漏掉「查询跑在 time 之后、入库之前」那几十毫秒里的事件。
- **游标存 SQLite 的 kv 表**（`dutyCursor`），所以后端自愈重启后不会重复推。
- **截图丢后台串行推**：几十张要几十秒，同步等待会把 TG 长轮询卡死，期间什么指令都收不到。汇总则先发（确认发得出去再回执）。
- **结果发回你发指令的那个私聊**（`ctx.msg.chat.id`），而不是配置里的 `chatId`（那可能是群）。
- **防呆**：单次硬上限 200 张；连续 3 次失败熔断；读图三道防线（非空 / 无 `..` / 解析后仍在 `SHOTS_DIR` 内）。
- 想要「不限静默、指定任意时段回查历史」那一版，见 §八 的 `/collect`（两者共用同一份汇总正文与人脸命中分区）。

#### 5.7.1 人脸命中（在库）单列

静默汇总与静默查岗都会把「**认出库里的人**」单独成区，而不是混在事件流水里 —— 静默期间翻消息时，第一个想知道的就是「有没有认识的人来过」。

- **判据是 `type === 'face' && faceName` 非空**（= 认出库里的人）。只判 `type === 'face'` 是错的：陌生人脸也走这个 `type`，把陌生人当命中列出来，等于每次门口过人都是「命中」。
- **按人聚合而不是逐条列**：同一个人一晚上来 20 次，逐条列就是噪音。汇总里每人一行 —— `**张三**：2 次 · 最近 08:50 · 门口 · 相似度 92%`（次数 / 最近一次 / 通道 / 该人最高相似度）。
- **陌生人单独统计**：另有 N 次未识别的人脸，并明确标注「不计入命中」。
- **没有命中就整块不出现**：空着摆一行「0 次」只占地方。
- **三处都单列**：
  · **静默汇总正文** —— `buildSilentSummary` 的 `🚨 人脸命中（在库）` 分区，插在「人员与识别」与「按通道」之间；
  · **查岗消息头部** —— `🚨 人脸命中：N 次 · M 人（张三、李四…）`，要一眼看到，不能只埋在正文里；
  · **查岗回执** —— `🚨 其中人脸命中 N 次（已在汇总里单列）`。
- 汇总与查岗复用同一个 `buildSilentSummary`，所以「结束汇总」与「查岗汇总」的口径天然一致。

### 5.8 自愈重启（`restart.mjs`）

设置 → 系统维护 → 定时重启 / 持续异常自动重启 / 手动「立即重启」，走的是同一条流程：

```
风暴保护 → 通知 → 停流 → 【await 关闭 HTTP server，真正释放端口】
  → spawn（绝对脚本路径 · 显式 cwd · stdio 落 restart.log · detached）
  → 轮询 /api/status，校验 startedAt 确实变新（自检）
      ├─ 成功 → 记台账 → 本进程退出
      ├─ 超时 → 回滚（本进程重新 listen）+ 告警
      └─ 回滚也失败 → 才考虑系统级硬重启兜底
```

老的实现是「spawn 一个进程 → 400ms 后 `exit(0)`」，实测会把**重启变成停机**，五个原因：

1. **端口竞态**：旧进程 400ms 后才释放端口，新进程何时 `listen()` 不确定 → 撞 `EADDRINUSE`；
2. **`listen()` 没挂 error 处理器**：异常冒泡到 `uncaughtException` 被兜底吞掉 → 新进程**活着但没人监听端口**；
3. **没有自检**：spawn 完就退出，从不确认新进程有没有接管；
4. **`restarting` 标志永不复位**：第一次失败后，**后续所有重启请求（含远程 `/reboot`）被静默忽略**；
5. **作用域错位**：`/api/restart` 写在模块级 `server()` 里，而 `requestSystemRestart` 定义在 `main()` 内部 → 点「立即重启」只产生一条 `ReferenceError`。

配套还有 `listenWithRetry`：端口被占用时退避重试（`EADDRINUSE` / `EACCES`），失败则明确报错退出，而不是假活。

**两层重启保护**（互补，别只留一层）：

| 保护 | 统计什么 | 拦什么 |
|---|---|---|
| 风暴保护 `stormMax = 3 / 10 分钟` | **失败**的重启次数 | 自愈连续失败（端口被别的程序长期占着）→ 暂停自动重启，保持服务运行 |
| 循环保护 `loopMax = 4 / 10 分钟` | **成功**的重启次数 | 重启循环。循环里每一次重启其实都成功，所以风暴保护一次都不会触发 —— 这层就是补那个缺口 |

另外，`spawn` 新进程时**必须带 `windowsHide: true`**：`detached` 的新进程没有控制台，而 Windows 会给「无控制台进程创建的控制台程序」自动分配一个可见终端窗口（见 5.13）。同理，重启时会把「TG 指令游标」通过环境变量 `MONITOR_TG_OFFSET` 交给新进程（见 5.12）。

### 5.9 系统级硬重启（`hard-reboot.mjs`，最后手段）

⚠️ 这不是「重启 BossMonitor」，而是**重启整台机器**。

| 平台 | 命令 | 权限要求 |
|---|---|---|
| Windows | `shutdown /r /t 5` | 管理员 |
| macOS | `osascript -e 'tell application "System Events" to restart'` | 给本进程授「辅助功能」 |
| Linux | `sudo -n systemctl reboot` | root 或免密 sudo |

**默认关闭**，两个开关都要打开才会生效：`systemReboot.enabled`（总开关）+ `systemReboot.onFailure`（仅在「自愈重启失败 + 回滚也失败」时自动执行）。

> 打开前必须先配好**开机自启**（Windows 任务计划程序 / NSSM、macOS launchd、Linux systemd），否则硬重启的结果是「机器起来了，但监控还是死的」。

### 5.10 状态哨兵（`watchdog.mjs`）

- **掉线告警**：哪一路掉了推「监控异常」；恢复了推「监控恢复」；持续异常按 `repeatMinutes` 重复提醒。
- **定时巡检**：每 `intervalMinutes` 分钟把全通道状态汇总成报告推出去（可设「仅异常时推」）。
- **判定口径**：后端模式下没有播放器，所以以「最近一次出帧时间」为准 —— 有帧且在 `STALE_MS` 内 = `playing`；从未出过帧 = `connecting`；曾好但现在超时无帧 = `error`；没配地址 / 停用 / 没拉流 = `idle` / `closed`。这比播放器状态更接近事实（后端 ffmpeg 24 小时在拉，页面开不开都不影响判定）。
- **流自愈**：某路持续异常超过 `streamRecovery.restartSystemAfterMin` 分钟（默认 30），升级为触发一次自愈重启。

### 5.11 Telegram 远程控制（`tg-remote.mjs`）

用 **`getUpdates` 长轮询**（方案 C）而不是 Webhook 卡片，原因是：卡片回调必须有一个**公网 HTTPS 入口**，得额外开隧道、配证书、维护域名；长轮询是「后端主动去 Telegram 拉」，全程出站连接，内网机器不开任何端口就能用。

三道硬约束，任何一条不满足就不执行、也不回执：

1. **必须是私聊**（`chat.type === 'private'`）—— 群里任何人发都直接丢弃；
2. **必须在白名单**（`from.id ∈ allowUserIds`）；
3. **必须以 `/` 开头**。

危险指令（`/reboot`、`/stop`、`/hardreboot`、`/shutdown`）额外要 `allowReboot` 开关，且默认关闭。`/reboot` 与 `/stop` 只需这一道开关（只动服务、不动机器）；`/hardreboot` 与 `/shutdown` 还要再多开 `systemReboot.enabled`。每条指令都写一行审计日志（时间 / 来源 id / 指令 / 结果）。

### 5.12 启动重放与积压（为什么「一启动就反复重启」）

`getUpdates` 是**确认式**的：Telegram 只有在收到「**下一次带更大 offset** 的 `getUpdates`」时，才认为之前那批已送达并真正删除。如果服务在确认之前就退出/重启了，那批 update 会**原封不动留在队列里**；而**不带 `offset`** 调用 `getUpdates` 会返回**全部未确认的积压**，并且不删除。

而 `/reboot` 恰好就是「执行完立刻把进程换掉」的指令 —— 于是三件事叠加成死循环：

1. 取到积压里的 `/reboot confirm` → 执行重启 → 进程被换掉，`offset` 没来得及确认；
2. 指令游标原先**只在内存里**，重启就归零；
3. 远程 `/reboot` 走 `force: true`，**故意跳过**重启风暴保护（那条保护统计的是「失败的自动重启」，而循环里每一次重启都是「成功」的，转多久都不会触发）。

⇒ 新进程不带 `offset` 再取一遍 → 同一条 `/reboot confirm` 被重放 → 再重启 → 无限循环。

三处修复：

| 修复 | 位置 | 作用 |
|---|---|---|
| **指令游标落盘** `server/data/tg-offset.json` | `tg-remote.mjs` | 重启后从上次位置继续，**不重放**。关键：**先把游标落盘、再执行业务** —— `/reboot` 会在执行过程中把进程换掉，只有提前落盘才来得及 |
| **远程重启熔断** | `tg-guard.mjs` | 10 分钟内因 TG 指令重启超过 3 次就拒绝并告警（回执里直接说明原因与解除时间）。台账**落盘**，否则每轮重启都把内存计数清零 |
| **`--drop-pending` 启动参数** | `headless-monitor.mjs` | 手动清一次积压：启动时**先清空、再开始收指令**，日志报出清掉几条 |

游标落盘带来的是 **at-most-once** 语义：若在「落盘之后、执行之前」崩溃，这条指令会**丢失**。对 `/reboot` 这类危险指令这正是想要的偏向 —— 宁可漏执行一次，也绝不重复执行。

**为什么光落盘还不够**（这是修完上面那条之后仍然会踩的坑）：Windows 上 `rename` 会被 Defender / 文件索引锁住而报 `EPERM`，而落盘函数里原来把异常**静默吞掉**了 —— 于是「没写进去」和「写进去了」在运行时毫无区别，下一次重启照样重放。所以又加了一条独立通道：

```
父进程 spawn 新进程时 → 环境变量 MONITOR_TG_OFFSET = 当前游标
新进程启动      → lastUpdateId = max(磁盘, 环境变量)
```

两条通道互不依赖，坏一条也不会重放。另外游标落盘失败会记进 `status.tgRemote.offsetSaveError`（设置页诊断面板可见），不再无声降级。

### 5.13 Windows 上「重启后反复弹出终端窗口」

症状：在 Windows 上执行 `/reboot confirm` 之后，**反复弹出好几个终端窗口，关掉又弹、弹了又关**；而双击 `start-windows.bat` 启动时完全看不到这个现象。

成因是**控制台的归属**：

```
start-windows.bat → node 继承 cmd 的窗口 → ffmpeg 也继承同一个窗口   → 什么都看不见
自愈重启        → node 是 detached（没有控制台）
                  → Windows 给它的每个控制台子进程**新开一个窗口**（每路摄像头一个 ffmpeg）
                  → 流断开重连再开一次 → 看起来就是「反复弹出、又关闭、又反复」
```

所以窗口数 ≈ 摄像头路数。修法是给**所有运行期 `spawn`** 加 `windowsHide: true`：

| 位置 | 拉起的进程 | 说明 |
|---|---|---|
| `restart.mjs` | node（新进程自己） | 同时保留 `detached: true`，守护性不能丢 |
| `source.mjs` | ffmpeg（每路流一个） | 弹窗的主要来源 |
| `ffmpeg-fetch.mjs` | `ffmpeg -version` / `tar` / `xattr` | 启动时探测版本，也会闪窗口 |

回归探针断言的是「**本项目所有 `spawn` 都带 `windowsHide`**」这条不变量（用模块加载钩子抓真实服务里每一次 spawn 的完整参数），所以在 macOS 上也能守住这个 Windows 缺陷。

`start-windows.bat` 也一并改了：启动前先 `netstat` 查 8787，**已在运行就不再起第二个**（重复启动会互相抢端口、各弹一个窗口）；自愈重启接管后旧窗口不再停在 `pause` 上误导人（打印说明后 6 秒自动关闭；只有非 0 退出码才 `pause` 等你看错误）。

### 5.14 登录门禁（先登录才能看画面）

**门禁拦在哪一层，取决于「监测在不在这台机器上」** —— 也就是 5.1 的两种运行模式。
判据只有一处：`useAuth.readBackendMode()`，它复用 `useBackendEvents.backendOn()`，
跟顶栏那颗「后端模式 / 前端模式」徽标、跟「运行时长取后端还是取本页」是**同一条规则**。
别在这里另写一份判断：三处一旦漂移，就会出现「徽标写着后端模式、登录页却把大屏拦在门外」这种说不清的现象。

| 运行模式 | 未登录时 | 退出登录时 | 为什么 |
|---|---|---|---|
| **前端模式**（本页就是监测本身） | `App.vue` **根本不挂载** —— 不是盖层遮罩，是连组件都不实例化：没有一路流被拉起来，也没有本地检测在跑 | App 卸载，走正常 `onBeforeUnmount`（停轮询、释放解码器、停检测） | 这个页面**就是**监控。放它进来，未登录的人就在消耗解码与 AI 算力；"退出登录"也确实等于把监测停了 |
| **后端模式**（监测在常驻设备上跑） | `App.vue` **照常挂载**，登录页只是盖在它上面的一层**遮罩** | 大屏**不卸载**，只是重新被登录页盖住 | 采集与检测根本不在这台机器上：拦住 App 既省不下算力、又只会让人对着登录页白等。反过来，登录 / 退出 / 干脆不开这个页面，都不影响常驻设备（照旧检测、照旧推送） |

```
main.js → LoginGate.vue ─┬─ 前端模式 + 未登录 → LoginView.vue（独占整屏的门）
                         ├─ 后端模式 + 未登录 → App.vue（大屏照常跑）
                         │                      └─ LoginView.vue（overlay：盖在上面的一层遮罩）
                         ├─ 会话检查中         → 启动态（别让已登录的人瞥见登录页）
                         └─ 已登录             → App.vue（后端模式下登录只是把它露出来）
```

两个容易忽略的实现细节：

- **遮罩必须压过大屏里的所有浮层**：`.login-root.overlay` 用 `z-index: 700`，压在顶栏 / 放大画面(90)、设置抽屉(120)、事件面板(300)、画面遮罩(400)，以及 teleport 到 `body` 的下拉面板(600)、画面右键菜单(640) 之上。低一点点，未登录的人就能从边上看见画面。
- **遮罩挡得住鼠标，挡不住挂在 `window` 上的键盘监听**。所以 `App.vue` 有个 `interactive` 开关，门禁在"盖着遮罩"时传 `false`，把 `M / F / R / E / Esc` 让给登录页。不这么做的话，未登录的人敲一下 `M` 就把遮罩盖上了（他看不见），等真正登录进来第一眼是「已锁定」—— 排查起来极其费解。
- 模式在**进登录页时**（`restoreSession`）和**退出登录时**（`logout`）各重读一次：用户完全可能刚在设置里把「后端检测服务」开关动过，那时存的档才算数（否则会出现"关掉后端开关后退出了，大屏却仍没卸载"）。
- **「接管」这一步放在门禁层**（`LoginGate` 的 `onMounted`），不在 `App.vue`：前端模式下 App 根本不挂载，写在 `App.vue` 里的自动发现**永远跑不到**。顺序也不能反 —— 必须**先接管、再 `restoreSession()`**，因为后者第一件事就是重读后端模式，而门禁要拿它的结果决定挂不挂 App。见 [5.18](#518-配置双向同步局域网多台机器看同一份配置)。

**口令不以明文存在任何一侧、也不以明文上线**（三层）：

| 层 | 做法 | 代码位置 |
|---|---|---|
| 存 | 只存摘要 `H1 = sha256("账号:密码")`，源码 / 配置里都没有明文口令 | `src/config/auth.js` |
| 传 | 领一次性 nonce → 提交 `proof = sha256("H1:nonce")` | `useAuth.js` ↔ `server/auth.mjs` |
| 比 | 前端本地兜底也只比摘要（定长异或，不提前短路） | `sha256.js` / `auth.mjs` |

- nonce **一次性、2 分钟作废**，同一条 proof 第二次提交返回 `stale-nonce` —— 抓包重放无效。
- 带 `password` 字段的请求**一律拒绝**（`plaintext-rejected`）：不给"顺手退回明文"留路。
- 服务端会话只存 `sha256(token)`，落 `server/data/auth-sessions.json`（tmp + rename）。
  所以**自愈重启不会把人踢出去** —— 这个项目一天要重启好几次，会话只放内存就等于每次都要重登。
  落盘失败（Windows 上杀软锁文件）只记进诊断，不影响本次登录。
- 失败节流是**两道独立的闸**：前端本地计数 + 后端按 IP/全局计数（5 次 → 锁 60 秒，锁定期内正确口令也进不去）。
- 后端不能成为单点：**后端不可达时退回本地凭据**并给出中性提示（`local` / `offline` 标记会显示在「关于系统」页）。值守大屏不能被"后端正好没起来"锁在门外。

**改账号 / 密码**（推荐放到后端的 `server/config.json`，改完重启服务即可，不用重新构建前端）：

```bash
# 1) 生成摘要（把 账号:密码 换成你自己的）
node -e "console.log(require('crypto').createHash('sha256').update('xiaomao:新密码').digest('hex'))"
```

```jsonc
// server/config.json —— 只写摘要，不写明文
{ "auth": { "username": "xiaomao", "passwordHash": "<上一步生成的 64 位十六进制>" } }
```

不配 `auth` 段就用内置默认（`src/config/auth.js` 的 `DEFAULT_AUTH`：账号 `xiaomao`，口令 `xmjt` 的摘要）。
老写法 `auth.password`（明文）**仍能识别**，但会在启动日志里告警建议换成摘要 —— 明文躺在配置里迟早出问题。

> ⚠️ 安全边界（别自欺欺人）：这是**摘要**不是加密，也挡不住"能开控制台的人改前端绕过门禁"；弱口令的摘要可被离线穷举。
> 它保证的是「明文不外泄、报文不可重放、挡住随手打开链接的人」。
> 要真防：换强口令 + 上 HTTPS + 让后端校验成为唯一入口。
> 另外 `npm run serve`（**纯静态**预览）没有 `/api` 反代，那条链路上 `detectBackend()` 探不到后端，登录只能走本地兜底校验。
> 注意**模式判定看的是存档里的配置**（不是"这台机器上有没有后端"）：所以如果你的存档里开着「后端检测服务」，即使这样打开页面，门禁仍按后端模式处理 —— 登录只是遮罩。

### 5.15 其它本地校验型口令（遮罩密码 / 内置配置口令）

「本地校验型口令」= 校验只在本机做完、不需要拿去联网换凭据的口令。系统里有三处，**一律只存摘要、只比摘要**，代码里不存在明文常量，也没有任何"明文对明文"的比较路径：

| 口令 | 存哪儿 | 摘要算法 |
|---|---|---|
| 登录口令 | `src/config/auth.js` → `DEFAULT_AUTH.passwordHash`（或后端 `config.json` 的 `auth`） | `sha256("账号:密码")` |
| 隐私遮罩解锁密码 | `options.mask.passwordHash` | `sha256("boss-monitor:mask-unlock:口令")` |
| 「加载内置配置」访问口令 | `src/config/auth.js` → `HIDDEN_PASSCODE_HASH` | `sha256("boss-monitor:hidden-config:口令")` |

统一走 `src/composables/sha256.js` 的 `secretDigest(scope, 口令)` / `secretMatches(...)`，靠 `scope` 做**域分隔**：三处口令就算碰巧写成同一个字符串，摘要也互不相同 —— 某一处泄漏的摘要不能拿去顶替另一处（探针里有一条专门断言这个）。

- **遮罩密码界面上不回显**：配置里只有摘要，系统自己也反推不出原文。设置页那个输入框的语义是"设一个新的"（留空 = 不改），想清掉用旁边的「清除密码」。状态片的「已设密码 / 免密码」是唯一的查看方式。
- **老存档会自动升级**：老版本存在 `mask.password`（明文）的存档，在载入时由 `migrateSecretFields()` 换算成摘要并**删掉明文字段**（幂等）。前端载入存档时会做，后端读 `config.json` 时也会做 —— 后者覆盖"用户直接手改过配置文件"那条路。
- **`secretMatches` 不做特例**：期望摘要为空时一律返回 false，"没设密码就地放行"这个策略由调用方决定（遮罩是"点击即恢复"，内置配置是"必须先输口令"）。

> ⚠️ 这三处都是**摘要不是加密**，弱口令照样能被离线穷举 —— 内置默认值只是"能开箱即用"，**不是"安全"**，请按上面的命令换成自己的。
> 内置配置口令的原文刻意**不出现在本文档里**：文档会跟着仓库一起分发出去，写出来就等于把门槛抹平了（登录默认口令是例外 —— 首次登录必须让人知道它）。
>
> ⚠️ **钉钉加签密钥 / TG Bot Token / 企微 Webhook 不在此列**：它们不是本地校验型口令 —— 要原样发给第三方服务器才能用，摘要化会让功能直接失效。那类凭据靠"别进版本库、别导出、走 HTTPS"，不是靠哈希。**别顺手把它们也摘要了。**

换遮罩密码 / 内置配置口令（生成摘要后替换对应常量或配置字段）：

```bash
# scope 换成 mask-unlock 或 hidden-config
node -e "console.log(require('crypto').createHash('sha256').update('boss-monitor:mask-unlock:你的口令').digest('hex'))"
```

### 5.16 盲视模式（画面隐藏、检测照常）

盲视模式是**单路**的（通道「更多」菜单里切换，`cam.blind`）：隐藏这一路的画面以省渲染开销，但**解码、采样、检测照跑不误**。它跟顶栏那个「遮罩」（盖住整屏、纯隐私用途）不是一回事。画面隐藏后会显示一个状态面板，回答两个问题：

**① 还有没有在检测？** 判据是「任意一项检测开着就算在跑」，权威定义在 `src/config/features.js` 的 `activeDetects()`：

| 面板里的一行 | 什么时候出现 |
|---|---|
| 画面变动 | `options.analysisEnabled` 开着 **且** `cam.motion !== false`（即 `motionOn()`） |
| 人形 | `cam.ai` 开着（与画面顶部的人形芯片、通道菜单里的「人形识别」同一口径） |
| 人脸 / 姿态 / 区域 / 计数 | 走 `activeFeatures()`：全局总闸（`options.face.enabled` 等）**且**这一路没关；区域还要求真圈过区域 |

标题写「检测运行中」当且仅当上表里至少有一行。**这一条以前是错的**：判据直接用 `analysisOn`（只看移动检测），于是「关了移动检测、开着人形识别」时面板写着「检测已关闭」，而同一块画面顶上的人形芯片亮着。现在面板与芯片同源 —— 探针里有一条断言专门盯着这两处不能各说各话（`activeDetects` 必须等于「移动芯片 ∪ 人形芯片 ∪ 附加芯片」）。

> 人形这一项**刻意不叠全局 `aiEnabled`**：后端模式下前端会把 `aiEnabled` 强制关掉（检测跑在服务端），叠上去反而会把"真的在跑"显示成没跑。

**② 这一路会推送到哪些渠道？** 三枚 chip，三种状态，与设置页「监控通道」页那排渠道小勾、以及推送调度器 `checkChannel` 同口径：

| chip | 含义 |
|---|---|
| 绿 · 会推 | 这一路开着 + 渠道已启用 + 凭据齐全（`channelUsable()`） |
| 黄 · 未就绪 | 这一路开着，但渠道没启用 / 凭据没配好 —— **实际一条都推不出去** |
| 灰划线 · 这一路已关 | `cam.push === false`（总开关）或 `cam.channels[渠道] === false` |

三种状态都带 `title` 说明原因；一枚都不亮时补一句「这一路当前不会推送到任何渠道」。渠道清单与短标签取自 `PUSH_CHANNEL_KEYS`（钉钉 / 企微 / TG），与设置页同一份；「能不能推」也**只有一份定义**（`defaults.js` 的 `channelGlobalOn` / `channelCredReady` / `channelUsable`），推送调度器 `useAlertPush` 复用同一份 —— 免得展示层与调度层各判一次、迟早在某个字段上漂移成「面板说能推、实际推不出去」。

> ⚠️ TG 的 `enabled` 缺省即视为**开**（`normalizeTelegram` 会把 `undefined` 补成 true），钉钉 / 企微缺省视为关 —— 这条差异写在 `channelGlobalOn()` 里，别统一成 `!!cfg.enabled`。
> TG 在推送层还有一条「钉钉/企微开着就强制带上 TG」的运行时兜底，**面板不体现它**：面板显示的是用户的实际配置，与设置页三个渠道的「已启用 / 未启用」芯片同源。
>
> 面板正文色板全部走主题变量（以前写死浅灰，亮色主题下面板是白底 → 几乎看不见）。

### 5.17 性能：为什么「轮询状态」曾经把整个服务按住

这一节记录一次真实的排查（用户报的两个症状：「系统运行时长经常只显示 `—`」和「`npm run server` 打开页面很慢」）。**两个症状是同一个根因。**

**根因：`/api/status` 每个请求都要 spawn 一次 ffmpeg。**

链路是这样接起来的：

1. `statusPayload()` 为了报告「用的是哪个 ffmpeg」，每请求都调一次 `resolveFfmpeg()`；
2. `resolveFfmpeg()` 为了「挑缓存目录里大版本最高的那个」，会对**每个**缓存里的 ffmpeg 调一次 `ffmpegMajor()`；
3. `ffmpegMajor()` → `probeFfmpeg()` → `spawnSync(bin, ['-version'])`，而且拿不到版本号时还会**重试 3 次、每次之间 `sleepSync(400)`**（`Atomics.wait` 把主线程真的按住）。

实测代价（都是同步阻塞，Node 是单线程）：

| 场景 | 耗时 |
|---|---|
| 冷启探测一个真二进制（77MB） | **1432 ms** |
| 探测一个跑不出 `ffmpeg version` 的文件 | **4580 ms**（3×400ms 睡 + 3 次 spawn） |
| 热态探测（页缓存已热） | ≈ 63 ms |

于是：**每一次状态轮询都把事件循环按住 63ms～4.6s**，而静态资源、事件接口、推送回执全排在这一件小事后面。前端拉状态是 6 秒超时 —— 被顶穿一次，`remoteUptime` 就是 `null`，「系统运行时长」显示 `—`（口径如此：连不上就是 `—`，**绝不退回前端页面时长**）。页面首屏那几个资源也就一起被拖慢。

**修法：两层记忆化，外加把压缩补上。**

| 改动 | 位置 | 效果（实测） |
|---|---|---|
| `resolveFfmpeg()` 记忆化（含环境变量快照） | `server/source.mjs` | 每请求只花一次字符串比较 |
| `probeFfmpeg()` 结果缓存 | `server/ffmpeg-fetch.mjs` | 成功结果永久复用；**失败只留 60s**（瞬时失败不能永久缓存，否则再也恢复不了）；键带 `size+mtime`，换了同名文件自动失效 |
| 静态产物 gzip（内存缓存 + `Vary`） | `server/headless-monitor.mjs` | 首屏文本 1363KB → **375KB（省 72%）** |
| 拉不到时短间隔补拉两次 | `src/components/AboutSystem.vue` | 一次抖动不再空掉整个 10 秒周期 |

实测前后：

| 指标 | 改前 | 改后 |
|---|---|---|
| `/api/status` p50 | 65.1 ms | **0.5 ms** |
| `/api/status` max | 95.5 ms | 15.3 ms |
| 6 个并发 `/api/status` | 65/129/194/258/322/387 ms（**严格串行**） | 总耗时 **2 ms** |

> 两层缓存**互为兜底**，回退验证时只拿掉一层是**测不出来**的（另一层顶上，请求路径照样是毫秒级）—— 变异必须同时打掉两层才会变红。这不是"断言是空的"，是这两层在这条路径上确实冗余。

**顺带揪出的两个真缺陷**（都是排查过程中撞出来的）：

1. **`resolveFfmpeg()` 读的是硬编码的 `server/config.json`**，而不是本进程实际使用的那份配置。后果一个是隔离环境里界面设的「ffmpeg 路径」看起来不生效（写进临时配置、读的却是生产配置），另一个是生产配置里的路径会**漏进**隔离环境。现在统一走 `MONITOR_CONFIG`，与 `headless-monitor` 的 `CONFIG_PATH` 同口径。
2. **落盘顺序**：`resolveFfmpeg()` 从**磁盘**读 `ffmpegPath`，而 `saveConfig()` 排在重解析之后 —— 于是保存新路径时它读到的是旧值，还把旧路径**记忆化**下来，表现为「改了 ffmpeg 路径，状态里慢一拍才变」。现在先落盘、再重解析。

另外，**自动下载完新 ffmpeg 之后必须让记忆化失效**（否则 `/api/status` 会一直报旧路径，而后台拉流用的是新的，两边对不上）。

gzip 只压 `.js / .mjs / .css / .html / .json / .svg / .txt`，且 `>= 1KB`：`png / jpg / gif / wasm / onnx` 本身就是压缩格式，压了更大还白费 CPU。压缩结果按「路径 + size + mtime」缓在内存里，一个文件一个进程只压一次。

### 5.18 配置双向同步（局域网多台机器看同一份配置）

**现象**：值守机 A 开常驻后端，在 A 的页面上把通道 / 推送配好；用另一台机器 B 打开 `http://A:8787` —— **一块空大屏**，什么通道都没有。

**原因**：配置同步原本**只有一个方向**（前端 `POST /api/config` → 后端），没有回读接口。前端每次打开都从**自己浏览器**的 localStorage 读存档，读不到就回落成初始化配置。于是那份配置只活在两个地方：**配它的那个浏览器** + 后端进程。B 拿不到。

比"看不到"更糟的是**次生风险**：B 打开「后端检测服务」开关时，旧的实现会把 B 手上那份**空白配置整体推给后端**，把 A 配好的通道与凭据一起清掉。

现在的做法（三件事）：

| | 谁做 | 说明 |
|---|---|---|
| 反向接口 | `GET /api/config` | 返回后端正在用的那一份（`options` + `cameras` + `faces` + 只读 `settings`）。`faces` 必须用 `faceLib.exportAll()`（**含向量**）—— `list()` 只有 `id/name/thumb`，向量丢了前端重建不出底库，表现为"人还在、名字也对、就是比对不出" |
| 接管 | `LoginGate` | 页面由监测后端自己服务出来时（`/api/auth/info` 的 `service` 判据，与顶栏「后端模式/前端模式」徽标**同一份**），且本机**还没配过任何东西** → 自动打开后端模式并填上同源地址。**只在本机是空的时接管**：用户手动关掉的后端模式不该被偷偷打开 |
| 对齐 | `alignWithBackend()` | 本机一路通道都没有 → **只拉不推**；本机落后（`localRev < 后端 rev`）→ 不推、不静默覆盖，只在设置页提示「后端有更新」+ 一键以后端为准；从没跟这个后端交换过 → 推；已对齐 → 什么都不做 |

**两个 rev 别混**（这是最容易搞反的地方）：

- `localRev`（落盘 `monitor-wall-sync-rev-v1`）= **本机这份配置对应后端的哪个版本**。只在真的推成功 / 拉成功之后才写。
- `syncRev` = **后端当前版本**。每次轮询 `/api/status` 都会被刷新。

拿 `syncRev` 当"本机版本"，落后判定会**永远成立**（刚推完就显示落后）。

**空白覆盖闸门**（`checkBlankOverwrite`）：`baseRev` 缺失或 0 **且** 后端当前有通道 **且** 送来的是一个**空** `cameras` 数组 → `409` 拒绝并说明原因。三个刻意不这么做的点：

- **不用"凭据为空"当判据**：默认配置里的钉钉 / TG 凭据是硬编码在 `src/config/defaults.js` 里的，一份全新空白配置**照样带着真凭据** —— 拿它判空永远不成立。
- **不误伤主动清空**：用户主动清空只会从"已经对齐过"的页面（`baseRev > 0`）发起，走不到这条分支。
- **不带 `cameras` 字段的请求不拦**：那是"只改设置参数"，不是把通道清空。

**踩过的两个坑**（都是"看着对、其实是错的"那一类）：

1. **拉完又回推一发**：自动推送走 900ms 节流，而"正在采用远端配置"是个**瞬时标志** —— 定时器醒来时标志早复位了，于是把刚拉下来的原样推回去，rev 空涨一格，别的机器立刻从"已对齐"变成"后端有更新"。
2. **别让配置对象中途出现半成品状态**：采用远端配置时如果先把 `options` 整个清空再填，`options.backend` 会有**一瞬间是 undefined**，`backendActive` 跟着闪一下 false —— 够把轮询停掉、也够把排队中的一次自动推送取消掉。于是"采用完还会不会回推"变成了"取决于有没有恰好闪一下"。现在清键时保留 `backend`，最后单独合并（本机的 `enabled/url/pollMs` 用本机的，`ffmpegPath` 用后端的）。

> 验证：`/tmp/cfg-pull-probe/`（后端探针 30 条 + 真实 `dist/` 无头 Chrome UI 探针 43 条，含"保存 → 900ms 内点拉取"的节流窗口时序场景）。每一步都做过**回退验证**：把对应实现拿掉，相关断言（`★ 这一页从没往回推过配置` / `★ 排队中的那一发被作废` / `①未对齐客户端推空白 → 409 拒绝`）会**真的变红**。

### 5.19 设置页发涩：抽屉里的 147 枚嵌套毛玻璃

**现象**：在设置页里点时间选择器（以及任何输入框）都发涩，改个静默时段要对好几次。

**根因（量出来的，不是猜的）**：设置抽屉自己是一块 30px 毛玻璃，而抽屉**里面**的每一个小控件（`.btn` / `.field` / `.sf-ctl` …）也各自挂着 `backdrop-filter`。实测抽屉打开时**抽屉内有 147 枚**（全页 156 枚）：`button.btn.small` 21、`button.btn.tiny` 25、`input.field.mini` 40、`textarea.field.url-sub` 12、`input.field` 15、`select.field.mini` 4、`input.field.name-input` 6、`textarea.field.url-input` 6、`button.sf-ctl.field` 7 等。而抽屉后面是 **6 路正在解码的直播画面（每帧都在变）**：

```
直播画面（每帧都在变） → 抽屉的 backdrop 每帧重算
                      → 抽屉内 147 枚小 backdrop-filter 也跟着每帧重算
```

于是**任何一次输入 / hover / focus 引起的重绘**，都要把这一整条链重新合成一遍。

**修法**：一条 CSS 规则把毛玻璃限制在"大块面"上（`src/style.css`）：

```css
html[data-theme='liquid'] .drawer :is(.btn, .field, .sf-ctl, .switch, .tag, .mini-btn),
html[data-theme='liquid'] .event-panel :is(.btn, .field, .sf-ctl, .switch, .tag, .mini-btn) {
  -webkit-backdrop-filter: none;
  backdrop-filter: none;
}
```

实测：**抽屉内 backdrop-filter 元素数 147 → 1**（只剩抽屉自己），全页 156 → 10。

**为什么直接删掉视觉上几乎无差**：这些小控件底色本身就是 `rgba(255,255,255,0.06)` 这类极淡的半透明，叠在**已经糊过的**抽屉上再糊一次，肉眼分辨不出来；抽屉背景有 82%~86% 不透明，背后本来也只剩一团色块。真正需要毛玻璃的是"隔着它还能看到背后内容"的大块面：**顶栏 / 抽屉 / 事件面板 / 下拉弹层**（`.sf-pop` 是 `Teleport to body` 的，不在上面的选择器范围内，照样保留）。原则就一句：**大块面保留、块面内部全去掉** —— 以后往抽屉里加新控件也不必再管这件事。

> **没有引入 UI 组件库**：卡顿根因在**合成开销**，不在控件实现。换一套组件库只会多一层需要同时适配 iOS / Android / WebView 的依赖，色彩与圆角也要再和现有玻璃主题对齐一遍，反而更麻烦。

> **验证上的坑**：无头 Chrome 走**软件合成**，测不出真机的掉帧 —— 装了修复后 `frames` 恒为 64 / 60fps、`over33 = 0`、`ScriptDuration` 只有 1.2ms / 40 次。所以断言**不能**落在"快了多少 ms"上（那种数必然假绿或假红），只能落在**机制性、可计数的量**上：**「抽屉内 backdrop-filter 元素数 ≤ 5」**。修复后实测 1。

### 5.20 人脸库「加载不出来 / 一会有一会不见了」

用户这个说法其实是**三件事**叠在一起：两件是加载时机，一件是真会把底库弄丢的缺陷。

**① 一打开设置页就看到「人脸库（0 / 50）」—— 其实只是没加载，不是丢了。**

`faces` 这个 ref 只有 `refreshFaces()` 会填，而原先只有点「管理」按钮时的 `watch(faceLibOpen)` 会调它。于是刚打开设置页时标题写着 `人脸库（0 / 50）`、名单一片空白 —— **没有任何"加载中"状态**，看上去就是底库被清空了。现在抽屉 `onMounted` 里直接 `refreshFaces()`。抽屉是 `v-if`，每次打开都会重新挂载，正好等价于"每次打开设置页都刷一次"，时效性也正是想要的。

**② 关掉设置再打开，人脸列表又折叠回去了 —— 看着像"人又不见了"。**

`faceLibOpen` 原本是**设置抽屉的组件级 ref**，而抽屉是 `v-if` 挂载的：关掉设置就跟着销毁，再打开又被重置回折叠态。现在提到 `useFaceLib` 的**模块级** —— "我习惯看这一块"属于用户偏好，不该被一次抽屉的开关重置掉。

**③ 真会丢人：两份"空底库"能互相把对方清空。**

| 场景 | 原来会怎样 | 现在 |
|---|---|---|
| 新机器 / 刚清过站点数据的机器打开，开机对齐推一把配置 | 载荷里 `faces` 是空数组，后端 `faceLib.replaceAll([])` **毫无保护** → 后端 30 人被抹成 0 | 后端加闸门：`baseRev <= 0`（这台设备从没跟这个后端对齐过）**且** 后端有 N>0 人 **且** 来件是空数组 → **跳过**（不动底库），并回执 `facesSkipped` |
| 后端那份底库是空的时候点「从后端拉取」 | `replaceFaces([])` 把本机 3 人整体清掉（探针抓到了 `IDBObjectStore.clear` 的调用栈） | `replaceFaces` 在**唯一收口处**拦住"空数组清非空底库"：先 `count()` 看一眼本机，有人就**什么都不做**（连 `clear()` 都不发），返回 `{ skipped: true, count }` |

两个判据的取舍：

- 后端闸门**只看 `baseRev`**。不误伤"用户主动清空"的理由是：那个操作只能从**已对齐**的页面发起（`baseRev > 0`）；也不拿"凭据为空"判空（见 5.18 —— 默认配置里就硬编码着真凭据）。
- 前端守卫**只放在 `replaceFaces` 一个收口处**：三个调用点各判一次迟早漏一处，且判据会漂。真要清空就走设置页的按钮（显式 `{ force: true }`）。
- **两个方向都必须说出来**。只回 `ok: true` 会让人以为"整个人脸库都同步过来了"，而实际自己被拒了一半载荷。于是设置页「配置同步」区显示 `⚠️ 本机人脸库是空的，后端已保留它自己的底库（没被推空）`；`POST /api/config` 的回执透出 `facesSkipped` / `faces`；反方向（拉取时保住本机）走 toast：`… · 后端人脸库为空，本机 3 人已保留`。

> 验证：`/tmp/settings-probe/`（真实 `dist/` + 无头 Chrome UI 探针 **17 条**，含"后端底库为空时拉取"和"本机底库为空时推送"两个**跨进程**场景）。回退验证分两组：**R1**（CSS + `refreshFaces` + 模块级 `faceLibOpen`）17 → **13**，恰好 4 条红；**R2**（后端闸门 + `replaceFaces` 守卫）17 → **13**，恰好 4 条红 —— 每条修复都有对应的红，且两组互不干扰。

> **产物比对的坑（做回退验证时撞上的）**：`vite.config.js` 里有 `define: { __BUILD_TIME__: JSON.stringify(new Date().toISOString()) }` —— 每次构建都会把**当前时间**烙进主 JS，于是主 JS 的文件名哈希每次都变、`index.html` 也跟着变（**CSS 与 aiWorker 不含它，所以逐字节稳定**）。所以"还原后产物与基线逐字节一致"这条断言**天生不可能成立**（一条自造的假红）。要比就比**归一化内容指纹**：先抹掉 ISO 时间戳与 `index-<hash>.js` 这类文件名，再哈希（`/tmp/settings-probe/hash-dist.mjs`）。而且这个指纹**本身要先验证对源码变化敏感**（注入变异后它必须变），否则又是个"什么都测不出"的空断言。

> 待录入列表那侧的「一片空白」是另一码事（拉取失败 vs 真的没人 vs 开关没开），处置见 **5.26** —— 同一条教训的另一个面：**空白不许覆盖非空**。

### 5.21 统计页图表：为什么自绘 SVG，而不是引 ECharts

统计页（`src/components/StatsPanel.vue`）原先是一排 CSS 柱条 + 横条。要「改高级一点」时先认真评估过**引图表库**，结论是**不引，全部自绘 SVG**。

三条理由都是对着本项目的实际情况说的，不是「自己画更酷」：

| 维度 | 引 ECharts 的代价 | 自绘 SVG |
|---|---|---|
| 数据规模 | 上限是「7 天 × 24 小时 = **168 格**」。ECharts 的强项（大数据量 canvas、缩放刷选、地图）一条都用不上 | 168 个 `<rect>` 毫无压力 |
| 主题 | **canvas 读不到 CSS 变量**。本项目三套主题（`dark` / `light` / `liquid`）全靠 CSS 变量 + `color-mix()`，用 canvas 就得把整套色板**再维护一份**、并监听主题变化重建 —— 撞上项目铁律「同一个事实只有一份判定」 | `<rect style="fill: var(--type-zone)">`，切主题**什么都不用做** |
| 体积 | 主包已 579 kB（gzip 205 kB），ECharts 全量 gzip 与整个主包同量级；而统计页是**静态 import**，会直接进主包 | **+0** |

关于「会不会影响各端适配」：**不会"某端跑不起来"**（canvas 在 WKWebView / web-view / Electron 里都在），真正的代价是「四端一起变重 + 主题同步要各验一轮 + web-view 里 tooltip / 缩放手感差」。反过来说，**自绘 SVG 的最大优势正是"零适配面"** —— 五个端里四个跑同一份 H5（小程序是纯 `web-view` 壳，不是原生渲染），矢量在任意 DPR 下都锐利，`liquid` 主题下还直接透出玻璃底（canvas 是不透明矩形，得手动抠背景）。

**落地结构**（`src/components/charts/`）：

| 文件 | 职责 |
|---|---|
| `scale.js` | 纯函数几何：`niceTicks` / `tickTop` / `ratio` / `heatOpacity` / `fmtInt` / `fmtHour` |
| `ChartFrame.vue` | 坐标系骨架（网格 / y 刻度 / x 标签），slot 暴露 `plot` / `x(i)` / `x0(i)` / `y(v)` / `step` / `top` |
| `TrendArea.vue` | 面积 + 折线 + 数据点（报警趋势） |
| `DonutShare.vue` | 描边圆 + `dasharray` 画的环形占比 |
| `DistBars.vue` | 类型分布横条（统一刻度尺 + 百分比列） |
| `PushStack.vue` | 三端推送成功 / 失败堆叠 + 成功率刻度 |
| `HeatGrid.vue` | 7 天 × 24 小时热力图（两个分类轴，故不套 `ChartFrame`） |
| `SparkLine.vue` | KPI 卡内嵌迷你折线（刻意不带坐标轴与交互） |

> `scale.js` 独立成文件的理由很具体：**刻度算法是唯一会被多个图型共用的几何逻辑**。写在某个 `.vue` 里，另一张图要用就只能复制一份，两边迟早漂。
> `niceTicks` 的两个细节：档位取 1/2/5/10；`nSteps = Math.round(Math.ceil(m / step - 1e-9))`（减 epsilon，否则 `max` 恰为整数倍时会多出一档）；刻度值用 `i * step` **乘法重算**而不是累加，避免 `0.30000000000000004` 这种脏值；缩放上限取**刻度最大档**而不是数据最大值，否则柱子会顶到画布边。

**三个容易踩的实现取舍**（都写进了组件文件头）：

- **用固定 `viewBox` + `width:100%` 等比缩放，不用 `ResizeObserver`。** 统计区在 `v-show` 的「关于系统」页签里、抽屉本身又是 `v-if`：挂载那一刻容器可能 `display:none`、宽度为 0，观察器会先收到 0 再收到真实值，处理不当就是「图挤成一条线」。等比缩放（`preserveAspectRatio` 默认 `meet`）根本不需要知道真实像素。代价只有一个 —— 字号随宽度整体缩放（480 的 viewBox 落在 320~520px 宽的抽屉里是 0.67~1.08 倍，9px 字变 6~9.7px，可接受）。
- **颜色一律 `style="fill: var(--type-…)"`，绝不写 hex。** SVG 的 `fill` 是**属性**，而属性值**不接受 `var()`** —— 写 `<rect fill="var(--x)">` 会静默失效。渐变里的 `stop-color` 同理，得用 `:style="{ stopColor: … }"`。
- **交互：hover 只是预览、click 才是「钉住」**（`pinned` 优先于 `hover`）。iOS 与小程序 web-view **没有 hover**，所以 tap 通道必须有；再点一下要**同时清掉 hover**，否则鼠标用户「点开 → 再点收起」会因为指针还停在原处而看起来没收起。触屏拖动同样会发 `pointermove`，所以只有 `pointerType === 'mouse'` 才算 hover。

> 分类色单独开了一组 token（`--type-person/face/zone/pose/motion/count`），**不复用 `--warn` / `--err`** —— 分类色与语义色混用会串味（区域报警若借用 `--warn` 的黄，看起来像在说「区域报警是警告级别」）。另：「姿态」刻意用**青柠绿**而不是橙，因为「区域」已经占了琥珀，橙和琥珀相邻时在深色底上几乎分不清 —— 分类色的首要职责是**能分辨**。
> 命中事件**挂在整块 `<g>` 上靠 `data-r` / `data-c` 分派**，不给 168 个格子各挂一套监听（抽屉已经因为合成开销吃过一次性能亏，见 5.19）。

### 5.22 热力图的小时桶：口径、迁移与「差额提示」

热力图要「日期 × 小时」，而原来的日统计只有按天汇总 —— 必须**新增小时桶**（`useDailyStats` 里 `days[k].hours`）。三条取舍是刻意的：

- **只存计数，不存明细。** 7×24×3 端 ≈ 几百个整数（JSON 十几 KB）；存明细则体积随报警量线性涨。
- **小时是「本地小时」**（`new Date(ts).getHours()`，与 `dayKey()` 同一套口径）。用 UTC 会让 08:00 的报警记到 00:00 那一格。
- **存储 key 不做版本升级。** 纯增量字段追加，旧存档载入时补出零结构 —— **日汇总一个数不丢**。换 key 反而要写迁移 + 处理「迁移到一半失败」，收益为负。反向也安全：新存档被旧版本读到也没事（旧代码不看这些字段）。

**`prune()` 是唯一的归一化收口**（`load()` 与 `save()` 都走它），所以「旧存档没有小时桶」只需在这一处补一次，不必写独立的迁移步骤。**以后再加字段照这个套路加。** 记录接口（`statAlarm` / `statPersonHit` / `statPush` / `statFaceHit`）与聚合（`aggregate`）同步按位累加小时桶，`hourRows()` / `hourTypeRows()` / `peakHour()` 是读取口。

> **加第四种小时指标（`hours.known`，人脸命中）时顺手改掉的一个隐患**：`aggregate()` 里原本是**三段几乎一样的显式循环**（alarms / push / hits 各写一遍）。加 `known` 时要记得复制第四段，**漏掉的症状是"这个维度全为 0"** —— 不报错、不崩溃，只是永远画出一片空。现在改成遍历 `HOUR_METRIC_KEYS` 的**一张指标表**（`HOUR_METRICS` 同时供归档、聚合、热力图和选择器使用），以后再加指标不用回来改这里。改完用 `[10] 回归` 那组用例钉住「老指标一字不变」。

> 几个具体的坑：
> - `zeros24()` **必须是函数**、每次调用都新建数组。写成模块级常量的话所有天共用同一个数组，今天 `+1` 会让前天一起变（这种 bug 极难看出来）—— 已写成专门的变异用例钉住。
> - 「类型 × 小时」表是**稀疏**的：全零行不写进存档（7 天 × 9 个类型键全量存是 1512 个数字，绝大多数天全零）。
> - 类型键有**上界**（6 个已知类型 + 区域事件的 3 个细分 `enter` / `exit` / `loiter`），不会被子存档撑大。
> - 热力图**零值也要画格子**（`heatOpacity` 的 `min = 0.07`）：留白表示「没有这一格」，而 `0` 是「这个小时没有报警」这个**有效读数**，用户要能数出 7×24 个格子。

**「差额提示」**：升级前的老记录只有按天汇总、没有小时明细，于是热力图合计会**小于**上方的报警总数。这必须在页面上说出来（`差额 N 次：来自升级前的老记录…`），否则用户会以为哪边算错了。另外「未推送」（`total = 0`）与「0%」（发了但全失败）是两回事，也分开显示。

> 验证：`/tmp/charts-probe/`。数据层 **51 条** Node 单测（记录 / 迁移 / 脏数据 / `prune` / 聚合 五组），UI **46 条**无头 Chrome 探针（含**整页扫描「长得像 SVG 却不在 SVG 命名空间」的元素** —— 跨组件 slot 一旦掉进 HTML 命名空间，元素不渲染但选择器仍选得到）。
> 回退验证分两组：**D 组 4 条**（不写小时桶 / `prune` 冲零 / 共用同一个数组 / `norm24` 不补长度）打单测，**U 组 8 条**（透明度常数 / 去掉峰值描边 / 环形写死 hex / 类型维度同色 / 绑 `c.rate` / 去掉差额提示 / `<svg>`→`<svgx>` / 塞 canvas）打探针 —— 8 条一起注入时 46 → **33**，红得干净且可归因；单条隔离（U1）46 → 45。还原后 7 个源文件逐字节等于基线，归一化指纹与基线一致。
> 无头 Chrome 是**软件合成**，测不出真机掉帧 → 断言一律落在**机制性、可计数的量**上（格数、命名空间、节点引用、解析后的颜色值），不落在 ms 上。

### 5.23 配置同步补全 hiddenIds、拉取后重载、人脸分页与取消长效登录

四个实际使用反馈回的修复，取舍记录如下：

- **`hiddenIds`（每路的显示/隐藏）纳入配置同步。** 此前它被当成「纯本机视图偏好」：`backendPayload()` 不带、后端不存、`applyPulledConfig()` 还写死 `hiddenIds = []` —— 结果 B 机从后端拉取后 7 路全部显示。教训：**先分清一个状态是「数据」还是「视图」，判据不是直觉而是「换台机器它该不该跟着走」**。通道开关直接决定报警与检测，属于数据。同步链四处都要动（payload / 后端存 / 后端回 / 采用），且 `backendSyncSignature` 必须带上它，否则改开关不触发重推。旧后端回读缺该字段时回落 `[]`（向前兼容）。
- **拉取确认成功后 `location.reload()`。** 就地采用会留下半新半旧状态（播放器、布局、旧 hiddenIds 残留）；整页重载是最便宜的「状态机复位」。自动拉取（B 是空机时的静默接管）**不** reload —— 用户还没看到页面，重载反而闪一下。
- **人脸库固定最多 4 行、超出分页。** 待录入与已录入两个网格各自独立分页；列数读 grid 实际列数（响应式布局下每行个数不固定，不能写死每页 N 个）；删除/录入后当前页为空自动回退一页；收起抽屉页码归零。
  **⚠️ 「怎么读列数」这一条后来返工过**：原先用 `getComputedStyle().gridTemplateColumns` 数轨道，在 `v-show` 隐藏的标签页里读到的是未解析的 `repeat(auto-fill, 88px)`，按空格切正好 2 段 → 列数被误判成 2 → 50 张待录入被分成 7 页。现在改成按容器宽度算，见 **5.30**。
- **取消「保持登录 30 天」。** 只保留 sessionStorage 会话（12 小时，关标签页即失效）。两个关键点：① `readSession()`/启动恢复时**顺手清掉历史遗留的 localStorage 会话**——不清的话老 token 还会继续放行，「取消」形同虚设；② 服务端 `issueSession` 不再按 remember 分叉 TTL。密码本来就从不落盘（摘要认证），这里撤的是**会话长效性**，防共用机器上的滞留登录。

> 验证：专项探针 **22/22**（登录无勾选框 / legacy localStorage 会话被清 / sessionStorage 会话可用 / 拉取后 `hiddenIds` 生效且只有 3 路画面 / `.tag` 不换行溢出 / 人脸 4 行分页·翻页·回退）。回退验证 9 条红且全部可归因（去掉后端回读 hiddenIds → A/F 组红；分页绑定改回全量 → D 组红；去掉 nowrap → E 组红；恢复读 localStorage 会话 → C 组红）。生产 `server/config.json` 与 `server/data/` 全程未被触碰。

### 5.24 人脸识别事件模型：face 事件类型 + 在库人脸命中关键事件（互不混淆）

两套「人脸」相关概念，别搞混：

1. **face 事件类型（识别到人脸就推）** —— 与人形、画面变动、姿态、区域、计数**同属一个层次**：都是「一种事件」，由各自独立的开关决定推不推，互不收窄。
   - 开启通道 `events.face`（依赖 `cam.ai` 人形检测 + `cam.aiExt.face`）后，**识别到人脸才发**（区别于人形——人形只要检测到人就发）；同帧既有人形又有人脸，两者各自触发一条。
   - `options.face.eventOnUnknown` 控制**陌生人脸**是否也生成事件：默认 `true`（陌生人也要推）；设 `false` 则只有「已知/在库」角度的识别才发 face 事件，陌生人脸静默。
   - 它**不收窄**任何人形 / 画面变动 / 姿态 / 区域的推送——各类型开关各管各的。

2. **在库人脸命中（关键事件，单发、穿静默）** —— `record.type==='face' && record.faceName`（即 `isFaceHit(record)`）表示识别出的**是已录入的人**。走 `pushDirectToUsers` 独立紧急通道，静默时段也推、三端 `critical.throughSilence` 缺省 `true`。这是另一条路，与 face 事件类型的「识别到人脸就推」是**并列**而非包含关系。

**配置字段对照（已废弃的 `hit` 收窄开关不再参与）**：

| 概念 | 配置字段 | 作用 |
| --- | --- | --- |
| 人脸识别能力 | `cam.aiExt.face` | 这一路要不要跑人脸识别（依赖 `cam.ai` 人形检测） |
| face 事件开关 | 通道 `events.face` | 识别到人脸是否推送一条 face 事件 |
| 陌生人脸也推 | `options.face.eventOnUnknown` | `true`：陌生人脸也生成 face 事件；`false`：仅已知人脸角度 |
| 在库命中关键事件 | `record.faceName` 非空 | 命中已录入人脸，触发独立紧急推送（穿静默） |
| 历史残留 | `cam.aiExt.hit` | **已废弃**：原「人脸命中」收窄开关，现不再参与任何推送判定；旧存档原样保留、无害 |

**设计取舍（取代旧的 `camHitOn` 收窄）**：

- **六个监听类型（画面变动 / 人形 / 人脸 / 姿态 / 区域 / 计数）是同级事件，互不收窄。** 旧的 `camHitOn(cam) = (aiExt.hit === true)` 一旦开启就把人形 / 陌生人脸等报警事件全部拦掉、只留「在库命中」——这正是「免打扰时段汇总显示 0 条」的根因（事件在进入缓冲判定前就被 `checkChannel` 判 off）。现已删除该收窄分支：各类型只受自身开关 `events.<type>` 约束。
- **在库人脸不再走普通推送 / 静默缓冲，避免与关键事件双推。** `handleAlarm` 中，若 `isFaceHit(record)` 为真，则 `send`/`queue`/全局静默缓冲/通道静默缓冲全部跳过，只在关键通道单发；陌生人脸 / 人形等正常进 `send` 与缓冲，于是汇总里能正确计入。
- **判定只有一份。** `isFaceHit(record)`（`defaults.js`）是唯一「是不是在库命中」判据，被关键推送与日常汇总排除共用；`features.js` 的 `camHitOn` 已删除，UI 与推送不再有第二套口径。
- **`cam.aiExt.hit` 保留为无害残留。** 迁移时原样带入、不丢弃，避免旧存档丢字段；它既不出现在 `EXT_FEATURES`（前端不再渲染「人脸命中」chip），也不再进入 `checkChannel` / 关键推送的任何分支。

> 验证：路由仿真 `/tmp/route-sim.mjs` 对实机配置（cam-1/4/6 均 `aiExt.hit:true`、`options.silent` 含 `12:00-13:30`）复现旧行为——旧 `camHitOn` 把 person / 陌生人脸 `checkChannel` 判 `off(命中模式收窄)`，导致静默窗口 `silentBuffer` 收不到事件、`buildSilentEndMessages` 报「本时段报警 0 条」；新逻辑对 person / 陌生人脸 / 在库人脸均 `PASS`，`handleAlarm` 把在库人脸导向关键通道、其余进缓冲，汇总计数恢复正常。`node --check` 通过；`env -u NODE_OPTIONS npm run build` 通过（dist 重建）。

### 5.25 超时与掐断的报错文案：别让 `signal is aborted without reason` 上屏

现象：用 `server/` 起的常驻服务，界面上经常冒出一句英文 `signal is aborted without reason`（同一场景在 Node 里是 `This operation was aborted`）。

**根因不是后端慢，是两件事叠在一起**：

- **这句话是引擎的默认文案。** `AbortController.abort()` 不传参数时，`signal.reason` 是引擎自己造的 `AbortError`：Chromium 的 message 是 `signal is aborted without reason`，Node 是 `This operation was aborted`。凡是我们自己设的 `setTimeout` 超时到点，都会造出这一句。
- **它被当成业务错误原样上屏。** 各处 `catch` 之前写的是 `errText = e.message`，于是「我们自己掐断的」和「对方真出错了」在界面上长得一模一样，用户只能看到一个看不懂的英文短语。

**修法三条，缺一条都还会漏：**

1. **掐断时给一个能读的理由。** `timeoutReason(what, ms)` 造一个 `TimeoutError` 塞进 `abort(reason)`，文案形如「待录入队列请求超时（8 秒未响应）」—— 就算它还是漏到了某处 `catch`，也是人话。
2. **一眼分类。** `isAbortError(e)` 同时认 `AbortError` / `TimeoutError` 两个 **name** 和三种引擎字符串（Chromium / Node / Firefox）—— 只认 name 会在换引擎时漏，只认字符串会在改文案时漏。
3. **在唯一收口处拦一道。** `useErrorLog.reportError()` 顶部直接 `return`：所有异步失败最后都汇到那里（`main.js` 的三个 handler）。**超时是我们自己造的，调用方已经给过一次有意义的结论**，再弹一条英文错误条纯属噪音。

配套 `netErrorText(e, what)` 把两类都翻成人话：超时 → 「请求超时：对方在限定时间内没有响应」；连不上（`Failed to fetch` / `NetworkError` / `Load failed` 这些同样是引擎黑话）→ 「连不上对方（网络不通 / 服务没起来 / 地址不对）」。**业务错误（HTTP 500 之类）原样透出** —— 那种错误的信息量在原文里，翻译只会丢信息。

> 验证：`useNet` 专项探针 **37/37**（三套引擎文案 / `TimeoutError` / HTTP 500 与业务文案必须原样通过）。回退验证：拿掉 `reportError` 的门 → 「引擎原生 abort 文案不进留档」变红；把 `netErrorText` 改回 `e.message` → 「界面上不再出现 signal is aborted…」变红。
>
> 顺带实测**后端本身不慢**：`/api/status`、`/api/events`、`/api/pending-faces`、`/api/config`、`/api/watchdog` 全部 2~3ms（e2e 里带状态码断言，避免把代理返回的 502 误读成"1ms 成功"）。所以「经常报错」的真实场景是**自愈重启的窗口期**：旧进程已放掉端口、新进程还没 listen，连接半开，客户端的超时到点 —— 病症在客户端文案，病根在重启交接期，两边都补。

### 5.26 待录入人脸库「空白」的三件事

现象：待录入列表经常加载不出来、一片空白，而且看不出是「没人」还是「坏了」。

1. **加空白占位 + 默认收起。** 这一块默认**折叠**（与「人脸库」对称，点标题旁的「管理」才展开），标题行始终带数量（`待录入人脸（N）`）。展开后若没数据，显示虚线占位框而不是一片空白；列表、分页器、「全部忽略 / 刷新待录入」都只在展开时渲染。
   **收起状态为 0 时仍留一行摘要**（`<占位标题> · 点「管理」查看原因`）—— 这一条是刻意保留的：**「默认收起」不等于让空白无声无息**，否则 5.26 想解决的"看不出是没人还是坏了"又会从另一个门口溜回来。
2. **把四种"空白"分开说**（此前四种在界面上完全一样）：

| 情况 | 占位文案 |
|---|---|
| 后端开着、这次拉取失败 | 「待录入队列没能拉回来」+ **这是几点几分的数据** + 明确写"列表没有被清空" |
| `face.collectUnknown` 关着 | 「收集陌生人脸是关着的」+ 去哪开 |
| 后端开着、确实没人 | 「后端暂未抓到未录入的人脸」 |
| 纯前端模式 | 「还没有暂存任何陌生人脸」+ 这里只留最近 24 条、不落盘 |

3. **「空白」不许覆盖「非空」。** 拉取失败时**保留**原列表（旧数据 + 一个"这是几点几分的数据"的时间戳），而不是清成 `[]`。

第 3 条是这次的核心：**失败时清空是最省事、也是最坏的写法** —— 用户看到的从"有 3 张待录入"变成"一张都没有"，只会以为人丢了。

> 验证：专项探针 **22/22**，覆盖正常加载 / 真的没人（正面基线）/ 超时 / 网络不通 / HTTP 500 五种，并断言**后三种之后列表与失败前逐字节一致**。回退验证：把失败分支改回"清空" → 「超时/掐断后列表仍是原来那 2 张」变红。

### 5.27 `/hits`：人脸命中记录（今日 / 昨日）

`/hits [T|Y] [img]`（`T` 今日、`Y` 昨日，省略为今日；`today`/`昨天` 等别名都认）—— 先给**人脸库概览**，再列出**命中已录入人脸**的记录；末尾加 `img` 连命中截图一起推（见 §5.42）。

- **概览块**（与查询时段无关，必显示）：`【待录入】N 张未建档` + `【已录入】M 人：name1、name2…`。
  读 `store.countPendingFaces()` / `store.listFaces()`，**各自独立 try** —— 任一项读失败只把
  那一项显示成「查询失败」，**绝不拖垮命中记录**（命中照常给）。名单过长（拼接 >800 字）时
  只列前 20 人并注明「其余 N 人」。

**与 `/collect` 的分工**（最容易混的一对）：

| | `/collect` | `/hits` |
|---|---|---|
| 内容 | 该时段**所有**报警（含陌生人脸、画面变动…） | **只**挑出命中已录入人脸的 |
| 输出 | 推一条汇总（`img` 时连截图） | 不带 `img`：答案就是**回执本身**；带 `img`：明细推到会话 + 命中截图（见 §5.42） |
| 锁 | 占查岗的串行锁（要逐张发图） | 不带 `img`**不占**（只读）；带 `img` 要占（同样要逐张发图） |
| 游标 | 无（绝对区间） | 无（绝对区间，重复发结果相同） |

四处刻意的取舍：

- **默认只查不推。** 用户问的就是"记录"，把同一份内容再推一条汇总是噪音；而且回执回到**发指令的私聊**，汇总会跑到配置的 `chatId`（可能是群）。带 `img` 时才推 —— 图没法塞进回执。
- **默认不抢 `running` 锁。** 它不发图、不碰游标，抢了反而会出「汇总正在发图时，问一句命中被拒」这种莫名其妙的失败。带 `img` 时例外，理由见 §5.42。
- **区间算法复用 `parseCollectRange`。** 两条指令说的「今天」必须是**同一个今天**（同一个零点、同一套"终点含整分钟"的语义）。各写一份迟早漂，用户就会看到「`/collect` 说有 3 条、`/hits` 只说 2 条」这种对不上的账。`/hits T Y` 这种矛盾的写法**直接报错**，不默默取第一个。
- **`MAX_LIST = 20`，保留最新的那批**（`slice(-MAX_LIST)`），并说明省略了几条；命中数 ≤ 20 时不出现这句话。

「什么算人脸命中」**只有一份判定**：`defaults.js` 的 `isFaceHit(rec) === !!rec.faceName`。判据只看 `faceName`，**不看 `type`** —— 后端只在真比中时才写 `face.name`，而命中可能挂在 `person` 类型的事件上，按 `type === 'face'` 过滤会漏。这一个纯函数现在被四处共用（推送收窄 / 关键事件直推 / `/hits` / 统计），否则迟早出现「面板说 3 次、TG 只推了 2 条」。

> 验证：`/hits` 专项探针 **75/75**（`parseDayScope` 穷举 + `isFaceHit` 判据 + `hits()` 全分支 + 概览块 + 串行锁），端到端 **75/75**（真服务 + 假 Bot API：库里先塞好数据，断言落到条数/人名/通道/相似度/区间外不出现，回执落在发指令的私聊，同一个 update 不重放；含 §5.42 的 `img` 场景）。回退验证：`isFaceHit` 放松成"全都算" → 陌生人脸那条红；`/hits` 抢走串行锁 → 「没有出现'还在处理中'」红；分发处改成返回硬编码 → e2e「命中次数 = 5」红；回执改发配置里的 chatId → 「回执落在发指令的私聊」红；概览改从写死的数字读 → 「待录入=7」那条红。
>
> ⚠️ 这轮顺手修了 e2e 自己的两处**假失败/假超时**（都是探针过期，不是功能坏了）：① 等回执的判据写的是**旧标题** `/人脸命中记录/`，而回执首行早就改成了「🎯 人脸库概览」—— 表现是"一直等到超时、只报没收到回执"，看着像功能挂了；② 假 Bot 的 multipart 解析只读 `chat_id`/`caption`，**没量文件字节数**，于是"推的是不是真截图"只能数张数。现在判据跟着回执真实首行走（并配正/负基线），假 Bot 用 latin1 量文件大小（用 utf8 会把二进制解成 U+FFFD，长度全部错位）。

### 5.28 统计页的「人脸命中」维度

统计页新增一列「人脸命中」，回答「**都有谁来、各来几次、最近一次是什么时候**」，数据存在 `useDailyStats` 的同一份 7 天存档里（`monitor-wall-daily-stats-v1`）：

- KPI 卡「人脸命中」+ 迷你趋势线（新增小时指标 `hours.known`，并入既有的「指标 × 24 小时」表与热力图）；
- 「人脸命中」卡：**人员榜**（次数降序，同次数按最近来的在前，复用自绘 `DistBars`）+ **最近命中记录**（最多 12 条，带通道与相似度）；
- **升级前的老记录单独提示**：升级前只记了"识别到的人"、没记"谁命中的"，这些名字会以灰色小标签列出并说明「升级后才有命中计数」，而不是让数字凭空对不上；
- CSV 导出补 `人脸命中` / `命中人数` / `命中人员`（`张三×3 李四×1`）/ `最近命中` 四列。

三条取舍：

- **录入与命中是两个口径，各记各的。** `statPersonHit` 记"识别到人"（含陌生人脸，名字为空也计人次），`statFaceHit` 记"命中已录入的人"。**两者互不污染**（有专门的隔离用例）：把命中折进人次会让「今天来了多少人」变成「库里有几个人来过」。
- **同名跨天合并：次数**求和**、最近时刻取**最大值**。两者口径不同，不能用同一套合并规则。取最大必须是 `Math.max` 而不是直接覆盖 —— `aggregate(keys)` 的 `keys` 顺序由调用方决定，面板今天按「早 → 晚」传，倒着传也得给出同一个最近时刻。
- **明细按 `t` 排序后再截断，而不是靠 `unshift` 的插入序。** 迟到的事件是常态（后端轮询一次带回好几条、重试后补上来、昨天的事件今天才落库），只靠插入序会让"最近记录"里冒出更早的时刻。

> 验证：统计专项探针 **109/109**（含 `[3b] 迟到的事件`、`[5c] 正序/倒序传键同结果`、`[5b] 两个口径互不污染`、`[10] 老指标小时桶一字不变` 四组回归）。回退验证：去掉明细排序 / 把 `Math.max` 改回覆盖 / 放松"必须有名字" / 去掉榜单排序 → 各自精准变红。

### 5.30 人脸库网格分页：别去数 `gridTemplateColumns` 的轨道

现象（用户原话）：**「50 条待录入被分成 7 页，每页只显示两排，而且第二排也没铺满就分页了。」**

**根因不在分页算法，而在「一行能放几张」量错了。**

`.face-grid` 是 `repeat(auto-fill, 88px)` 的自适应网格（一行几张随抽屉宽度变），所以每页张数 = **列数 × 4 行**，列数必须现读。原来的读法是：

```js
const tpl = getComputedStyle(el).gridTemplateColumns || ''
return tpl.split(' ').filter((s) => s && s !== 'none').length
```

它假设 computed value 一定是**已解析**的轨道列表（`"88px 88px …"`）。但**本抽屉所有标签页用的是 `v-show`** —— 抽屉一打开，全部模板都渲染，只是未选中的人脸 tab 处于 `display:none`。此时 Chrome 返回的是**未解析的指定值** `"repeat(auto-fill, 88px)"`，按空格切正好 2 段 → **列数被误判成 2**。

最小复现（同一份 CSS、三种状态一次打印）：

| 状态 | `gridTemplateColumns` | 旧算法 | 按宽度算 |
|---|---|---|---|
| 可见，744px | `"88px 88px 88px 88px 88px 88px 88px"` | 7 | 7 |
| **未选中 tab（`display:none`）** | **`"repeat(auto-fill, 88px)"`** | **2** ← 元凶 | 0（保留旧值，不写坏） |
| 可见，280px | `"88px 88px 88px"` | 3 | 3 |

于是 `pageSize = 2 × 4 = 8` → 50 张 = **7 页**；而网格真实宽度能放 6 列，每页切的 8 张就只铺出**两排（6 + 2）** —— 现象逐字对上。

**三处改动，互为备份：**

1. **列数改成按容器实际宽度算**：`floor((clientWidth + 8) / (88 + 8))`。不依赖浏览器如何解析 `repeat()`；元素不可见时 `clientWidth` 为 0 → 返回 0 → 调用方**保留上一次的值**，不会被写坏成 2。
2. **补上「可见后重新测量」**：切到「检测识别」分页那一刻，网格才从 0 变成真实宽度。于是加 `ResizeObserver`（尺寸一变就重算），并把 `watch` 的依赖补上 `tab` 与两个网格元素引用（元素被 `v-if` 重建时要重新挂观察）。
3. **兜底初值不再被当成测量结果**：`libCols / pendingCols` 的初值 6 只是「还没量过」的占位，网格一旦可见就会被真实值覆盖。

「已录入」人脸库走同一个函数，所以一并修好（30 人 = 24 张/页 = 2 页）。

**同区的另外三件反馈：**

- **「待录入人脸」默认收起**（与「人脸库」对称，点标题旁「管理」才展开）。列表、分页器、「全部忽略 / 刷新待录入」都只在展开时渲染；**收起且为 0 时仍留一行摘要**（`… · 点「管理」查看原因`）—— 「默认收起」不等于让空白无声无息，5.26 的初衷不能被自己收回去。
- **「全部忽略」加二次确认**：它一次清掉的是**全部**（前端内存队列 + 后端 SQLite 队列）且不可撤销，与「清空人脸库」「删除单个人脸」保持一致，弹窗里还写明清掉的范围与张数。
- **换视口后页数跟着列数变**：700px 视口 → 5 列 → 20 张/页（50 张 = 3 页），不会出现「宽屏的页数用在窄屏」。

> 验证：**最小复现**（`/tmp/face-probe/`，同一份 CSS 三种状态一次打印，见上表）+ **端到端 UI 探针**（`/tmp/face-ui/`：真实 `dist/` + 无头 Chrome + 假后端吐 50 条待录入）：**22/22**。断言全部落在**实测几何**上 —— 每页张数 `== 实测列数 × 4`、每页正好 4 排、页数 `== ceil(50 / (列 × 4))`，以及「默认收起 / 点管理才渲染 / 二次确认弹窗出现 / 取消后一张没被清掉 / 已录入同样 4 排分页」。

### 5.32 「待录入满库」的 TG 提醒（每填满周期只提醒一次）

用户诉求：「当待录入的人脸库满了，要通过 TG 提醒我及时去处理（属于**关键事件提醒**类型），
**仅提醒一次**，处理过后满了再提醒。」

判定收敛成**一个独立模块** `server/pending-full.mjs` 的 `createPendingFullWatcher`（纯函数、依赖注入、可测）。
状态机：

- `isFull = count >= fullAt`，`fullAt` = `PENDING_KEEP`（**100**，与收集上限一致——「满了」就是到了上限）；
- **只在「未满 → 满」的跃迁时提醒一次**（`full` 标志随即锁住）→ 满库后继续满**不会刷屏**；
- **「满 → 未满」时重新武装** → 处理过（录入 / 忽略使数量降下来）并再次填满，才会再提醒；
- `full`/`lastCount` 落 **SQLite 的 kv**（`pendingFull`）→ **自愈重启不会重复提醒**；
  数量没变时直接短路，不每帧写 kv。

触发点（队列数量变化处）：分析器新插入一条待录入（`addPendingFace` 返回 `inserted=true`，
去重重刷时间不算新增）、`/api/pending-face` 删除一条之后，各 `refresh(count)` 一次。

**两种运行模式各有一个 watcher，判定却只有一份**：

- **后端模式**（典型：headless 常驻）：队列在服务端 SQLite，`fullAt = PENDING_KEEP`（100），
  状态落 SQLite 的 kv（`pendingFull`）。由 `server/headless-monitor.mjs` 创建。
- **纯前端模式**（没接后端）：队列是前端内存里的 `pendingFaces`，`fullAt = PENDING_MAX`（24），
  状态落 `localStorage`（`monitor-wall-pending-full-v1`）。由 `App.vue` 创建。
  后端模式下前端队列恒为空 → `refresh(0)` 自动 no-op，**两种模式不会各发一条**。

推送**复用既有的「关键事件单独提醒」**（`pushDirectToUsers('pending', …)`），与
静默提醒 / 静默汇总 / 人脸命中**同一套开关与接收人**（见 5.5.1），未开启 / 无接收人时安静返回。

> ⚠️ **这道闸门差点被"假绿"蒙过去**：探针里「续满不再发」最初是被 `lastCount` 短路
> （同样的数字 100→100）挡住的，把 `if (isFull && !full)` 改成 `if (isFull)` 探针**照样全绿**。
> 补了一条「同一填满周期内数量变化（100→105）仍不重发」才把闸门单独逼出来。

>
> ⚠️ **另一个真缺陷**：三处调用 `store.countPendingFaces()`，但 `store.mjs` 里**根本没有这个函数**

> 现已把 `dedupeSec` 一并收进 `FACE_TUNING`，两个 `faceConf()` 里那两行 `|| 6` 全部删除
> （探针静态断言「文件里不再出现 `|| 6`」，并配一条运行时断言证明窗宽真的改变判定结论）。

- **`retryMs` 为什么值得暴露**：它是「采集率第二暗坑」的修正旋钮 —— 失败只记**短窗**（默认 700ms，
  2fps 下≈每帧都试一遍），成功才享长窗（`dedupeSec`）。网络抖动 / WASM 卡顿时把它调大能少空转；
  机器弱、人停留久时调小能多抓。判定在 `faceRetryDue()`，前后端共用。
- **`detSize` 的坑（务必知道）**：SCRFD-500M 的 ONNX 把**输出形状按 640 静态声明**，
  换边长时 onnxruntime 会打 `Expected shape from model of {800,10} does not match actual shape
  of {392,10}` 的**告警**。这**不是错误**：图的 anchor 网格本来就是动态的，只是导出时把元数据
  写死成了采样形状。前后端解码都从**实际**输出行数反推（`side = round(sqrt(rows/2))`、
  `stride = 8·2^g`），与输入边长无关 —— 已在真模型上验证 320/448/640/1280 全部跑通。
  值会被**吸附到 32 的倍数**（否则 anchor 网格按 stride 8/16/32 铺不对）。
- **「恢复默认」**从 `cloneDefaultOptions()` 读（= `FACE_TUNING` 的缺省），不另写字面量。

> 实测（`#243`，`/tmp/enroll-probe/measure-perf.mjs`，Node/onnxruntime-node CPU，960×540，中位数）：
> `yolo11n` 整帧 **38ms** / `yolo11s` **99ms**（**2.61×**，换 +7.5 mAP）；SCRFD 整帧 **19ms** /
> 头部裁剪 **24ms**（单次 1.26×，但被闸门限流到 ≈**7ms/秒/路**，所以「补检只 +5% 负载」成立且偏保守）；
> `detSize` 448 / 640 / 960 → **10 / 18 / 43 ms**。

> 验证：`/tmp/face-tune-probe/test-face-tune.mjs` **74/74**（缺省/夹紧/吸附/脏值不变量 + 前后端接线契约 +
> **`dedupeSec` 的运行时判定证明**（`tracksDueForFace` / `faceReuseFresh` 换窗改结论）+ 「两端 `faceConf` 里
> 不再有 `|| 6` 兜底」+「设置页候选边长全是 32 的倍数」）、`test-detsize.mjs` **6/6**（真模型四种边长跑通）、
> `/tmp/head-probe/head.mjs` **42/42**（新增「换边长后裁剪→映射回帧的闭环仍成立」）。
> 回退验证各中一处：`detectFacesInHead` 忽略 `opts.size` → head 探针红 1 条；后端不接 `fc.retryMs` →
> face-tune 红 1 条；去掉 32 吸附 → 红 2 条；`defaults.js` 另写一个字面量 → 「单一份判定」红 2 条；

> `dedupeSec` 运行时断言红 2 条。

### 5.35 运行期数据不进版本库：多设备同步的唯一正确姿势

**曾经的坑**：`server/data/monitor.db` 从 `init` 提交起就被 git 跟踪。`.gitignore` 里的
`server/data` 是后来才加的 —— 而 **`.gitignore` 对「已经被跟踪的文件」完全无效**，
所以这个库一直跟着提交走，两台设备迟早撞上。

**为什么会丢数据**（三层叠加）：

1. SQLite 是**二进制**，git 没法合并。两台设备都跑过 → 各写出一份不同的 db →
   `git pull` 报 `CONFLICT (content): server/data/monitor.db`，只能 ours/theirs 二选一，
   **另一台的事件 / 人脸库 / 待录入当场没了**。
2. 库是 **WAL 模式**（`store.mjs` 里 `db.pragma('journal_mode = WAL')`），带
   `monitor.db-wal` / `monitor.db-shm` 两个边车。只同步主库不同步边车 = 丢掉还没
   checkpoint 的事务；反过来只更新主库却留着**旧的** `-wal`，SQLite 会把陈旧 WAL
   重放到新库上 → **静默的错数据**（比丢数据更难发现）。
3. 服务**每跑一次就写库**，所以这个文件几乎每次 `git pull` 都在冲突。

**修法（已落地）**：

- `git rm --cached server/data/monitor.db` —— 只把它请出索引，**磁盘文件一个字节都不动**。
- `.gitignore` 补 `*.db` / `*.db-wal` / `*.db-shm` / `*.sqlite*` 显式兜底
  （原来只有 `server/data` 一条目录规则，将来谁把它改窄了就又漏了）。

**多设备怎么弄**：git 只同步**代码**，数据**每台独一份**。

- 新机器 clone 下来，`server/data/` 会在首次启动时自动建库（`CREATE TABLE IF NOT EXISTS`），空库起步。
- 想把某台的数据搬过去：**整目录拷**（`monitor.db` + `-wal` + `-shm` + `shots/` 一起），
  且**两台不能同时写** —— SQLite 不是多主数据库。
- 真要「一个库多处看」：让一台常驻当服务端，其他设备走 HTTP API（见 §9），别共享文件。
- `MONITOR_DATA_DIR`（见 §10）可以把数据指到别的盘 / 别的目录，与代码彻底分开。

> **⚠️ 另一台设备拉取前，先备份它自己的 `server/data/monitor.db`。**
> 这次改动是一次「删除已跟踪文件」的提交：如果那台机器的库是**干净的**（无本地改动），
> `git pull` 会把磁盘上的 `monitor.db` **一并删掉**；如果有本地改动，git 会因冲突拒绝合并。
> 所以在那台机器上先 `cp server/data/monitor.db* ~/monitor-backup-$(date +%F)/`，再 pull，需要时再拷回。
> **拉完之后 `git status` 不再把 monitor.db 列为 modified，就说明生效了。**

**备份就是拷文件**（`scripts/make-win-deploy.mjs` 里也是这么写的）：

- **冷备**（服务停止时）：`monitor.db` + `-wal` + `-shm` 三个一起拷，缺一个就可能丢事务。
- **热备**（服务在跑）：`sqlite3 server/data/monitor.db ".backup ~/monitor-backup.db"`
  或 `VACUUM INTO '~/monitor-backup.db'` —— 这两条是 SQLite 官方的在线备份入口，不会写坏原库。

> 验证：`/tmp/dbignore-probe/test-db-ignore.mjs` **16/16**（索引/HEAD 无 db + `.gitignore` 显式边车兜底 +
> `check-ignore` 命中主库与两个边车 + **磁盘上的库还在且能打开**——最后一条专门防「用删数据的方式把探针刷绿」）。
> 回退验证 2 处：`git add -f` 把库强行加回索引 → 红 3 条（其中 `check-ignore` 那条红得很有价值：
> 它证明 **`git check-ignore` 对已跟踪文件不报告**，这正是原 bug 一直没被发现的原因）；
> 从 `.gitignore` 删掉 `*.db-wal` → 红 1 条。

### 5.36 为什么头部补检曾经把整个服务按住（`faceSearchAt` 闸门）

和 §5.17 是**同一类事故**：某个功能在单线程里干了同步重活，把事件循环按住，
于是「页面很慢 / 接口轮询超时」看起来像是网络问题，其实是**服务自己卡住了**。

**症状**（用户报的原话）：`npm run server` 起后端后打开前端页面又很慢、一直在加载、
接口反复在轮询、报 `后端事件轮询超时：对方在限定时间内没有响应`；局域网另一台机器从这台拉配置也超时。

**根因：新加的「头部裁剪补检」的节流闸门读错了字段。**

「补检」是为了救**漏检的人头**（太远 / 背对 / 只露半张脸）：整帧 SCRFD 没检到这个人的脸，
就把他的人形框顶部裁下来放大到 640 再单独检一次（单次 ≈ 24 ms 的 640 全推理）。
它**必须**被节流 —— 不然每个漏检人头每帧都跑一次全推理。节流判定收口在 `tracksDueForFace()`，
而它当时读的是 `track.faceAt`：

- `faceAt` 只在**「整帧检出了脸 → 去提特征」**那一步才写（在 `for (const {face, track} of pairs)` 循环里）。
- 而补检服务的恰恰是**整帧没检出脸**的那些人头 —— 他们永远走不到写 `faceAt` 的那一步。
- 于是 `!tr.faceAt` 对这些轨迹**恒为真** → 每一帧都被判为「窗口到期」→ 每帧一发 640 全推理。

实测代价（`2fps` × N 路 × M 个漏检人头）：**3 个漏检人头跑 30 秒 = 180 次全推理**（探针里数出来的）。
单线程里这就够了 —— `/api/*` 和静态资源全排在它们后面，页面转圈、轮询顶穿 6 秒超时、
隔壁拉配置也超时。**只加功能不改闸门字段，就不会报任何错，只会整体变慢。**

**修法：闸门必须由「它节流的那一步」自己记时刻。** 新增 `track.faceSearchAt`
（发起补检即记，**检出与否都记**），闸门改读它。三个时间字段从此各司其职、互不借道：

| 字段 | 何时写 | 语义 | 谁读它 |
|---|---|---|---|
| `faceAt` | 提特征**前**（成败都记） | 上次「尝试」 | `faceRetryDue`（失败短重试窗） |
| `faceOkAt` | 提特征**成功**时 | 上次「成功」 | `faceReuseFresh`（整窗复用） |
| `faceSearchAt` | **发起补检时**（检出与否都记） | 上次「发起补检」 | `tracksDueForFace`（补检节流窗） |

写 `faceSearchAt` 的地方就是补检循环的第一行（`server/analyzer.mjs` 与
`src/composables/useAiExtras.js` 各一处）—— 先落戳、再 `await detectFacesInHead()`。

> 验证：`/tmp/face-throttle-probe/test-gate.mjs` **7/7**（吃**真实** `tracksDueForFace`；
> 含「30s @2fps × 3 条漏检轨迹」的调用量对照：**修复前 180 / 修复后 12** ≈ 每 10s 一次，正好落在窗口级）、
> `test-wiring.mjs` **8/8**（两端补检循环里都记 `faceSearchAt` + 字段存在于轨迹工厂 + 两端补检都还在）。
> 回退验证：同时打掉「加戳」与「改闸门」→ 闸门红 3 条、接线红 3 条。
> 既有探针 `/tmp/head-probe/head.mjs` ⑤ 的测试轨道也随字段改名为 `faceSearchAt`，
> 并补了一条**回归锁**：漏检人头（永远写不到 `faceAt`）在补检窗内也**不重检**——若把闸门改回读 `faceAt`，这条立刻红。

### 5.37 每日统计改由后端权威：多端一致的唯一来源

**问题**：按天统计原先**只活在开着页面的那个浏览器**的 `localStorage`
（`monitor-wall-daily-stats-v1`）。后果有两个，用户一眼就能看出来：

1. **页面一关就不记了** —— 而报警本来就是「关掉页面也照推」的 7×24 场景；
2. **换台机器打开，统计从头开始** —— 局域网里两台设备看到两张对不上的图。

**分工（后端模式）**：

| 谁 | 干什么 |
|---|---|
| 后端 `headless-monitor.mjs` | 常驻累计：`handleEvent`（检测事件）+ watchdog 的 `addStatusEvent`（掉线/恢复）里调 `server/stats.mjs` 的 `recordEvent` |
| `server/stats.mjs` | 薄壳：转发 `statEvent`、导出 `snapshot()`、清零、并把「今日/昨日/近 7 天」聚合成 `windowStats()` 供 `/compile` 用 |
| `GET /api/stats` | 回权威快照 `{ days, now }`（裸接口、带 `Access-Control-Allow-Origin: *`，与 `/api/config` 同规格） |
| `POST /api/stats/reset` | 清零 |
| 前端 | **只读**：`setStatsRemote(url)` + `syncStatsFromRemote()` 定时把后端那份整体替换本机 `days`；展示层（`aggregate`/热力图/命中榜）一概不变 |

**关键取舍**：

- **累计逻辑一份都不重写**：仍然是 `src/composables/useDailyStats.js` 里那套
  （报警分类型 / 小时桶 / 识别与命中 / 断线恢复），后端**复用**它 —— 于是
  「统计页看到的数字」与「`/compile` 报出来的数字」天然同口径，不可能各算一套。
- **「一条事件记哪几项统计」收成唯一判定**：`useDailyStats.statEvent(rec)`
  （掉线恢复单列、识别人次含陌生人、命中只认 `isFaceHit`）。前端 `onAlarm` 与
  后端 `handleEvent` 都调它；判定写在两处迟早漂移成「面板说 5 次、远端说 4 次」。
- **后端模式下前端不再自己记**：`onAlarm` 里遇到 `source === 'backend'` 的事件直接跳过
  打点。否则本机副本与权威值会互相打架，而「页面一关就不记」的那份本来就不该是
  「今日一共报了多少次」的答案。
- **落盘复用现成通道**：统计走 `compat.mjs` 的文件版 `localStorage`
  （`server/data/localstorage.json`），与「累计推送统计」同一个文件 —— 这个垫片
  后端本来就在用，不必为统计单开一套持久化。
  > ⚠️ 因此 `server/stats.mjs` **必须动态 import**（`await import('./stats.mjs')`）：
  > `useDailyStats` 在模块初始化时就 `load()` 一次，垫片还没装就会读成空，
  > 随后第一次 `save` 反而把已落盘的历史覆盖掉。
- **清零双向**：`resetDailyStats()` 本机清完会顺带 `POST /api/stats/reset`；
  不一起下发的话，下一次同步又把后端那份拉回来，用户看到「清了又回来」。
- **推送统计不用补**：后端的推送调度（`notify → useAlertPush → usePushStats.recordPush`）
  本来就在记，重复记会翻倍。
- **不另数事件表**：`/compile` 的类型分布/小时高峰/命中榜全部取自这份统计，
  只有「事件条数」还需要查库 —— 事件表受 `keepEvents` 滚动淘汰，直接数它会被截断。

**前端独立模式**（没开后端）行为不变：`remoteUrl` 为空 → 本机自己累计。
关掉后端开关时 `setStatsRemote('')` 回到本机统计（已同步过来的 days 保留，继续往上加）。

> 验证：`/tmp/stats-probe/`
> - `probe-unit.mjs` **31/31**：`statEvent` 分类（掉线不计入报警、只有带名字才算命中）、
>   `snapshot`/`windowStats` 口径、落盘 + **另起进程 load() 读回**（多端一致的前提）、
>   `replaceStatsDays`+`aggregate`（前端展示路径）、以及前端同步胶水

### 5.38 远程指令的两处「内容」改动：`/compile` 要明细、`/start` 要讲清系统

**`/compile`（统计报表）**：原来只有「事件库总量 + 今日/昨日事件与人脸命中 + 人脸库 +
通道在线 + 推送渠道」，看完还是不知道**哪类报警多、哪个时段忙、哪个渠道在掉链子**。
现在按「今日 / 昨日 / 近 7 天」三层展开，每层给：报警次数 · 识别人次 · 唯一人数 ·
人脸命中（含人数）· 断线/恢复 · **报警类型分布** · **三端推送成功率（成功/总数 + 百分比）**；
今日与昨日还列出**人脸命中榜**（谁来过、来几次、最近一次几点），近 7 天给最忙时段。
数据源是 §5.37 那份**后端权威统计**（`stats.windowStats()`），与统计页同一个 `aggregate`，
所以报表和页面不可能各算一套。只有「事件条数」仍查库 —— 它要的是原始条数。

**`/start`（机器人介绍）**：`/start` 是用户首次打开对话**必触发**的指令，原来却只是
一张指令清单，新用户看完不知道这套系统是干什么的。现在固定三段：
① **系统能做什么**（多路 AI 检测 / 人脸库 / 免打扰 / 状态哨兵 / 多端一致）；
② **我能替你远程做什么**（按「用它的场景」分组：免打扰 / 回看检索 / 状态报表 / 维护，
而不是按字母排指令）；③ 落到 `/help`。开头加一行**实时**概况
（几路画面、几路在线、人脸库几人），一句话就知道"这是我这台机器"；状态读不到就跳过，不编造。

> 验证：同上 `/tmp/stats-probe/probe-e2e.mjs` —— `/start` 断言段落结构与实时概况，
> `/compile` 断言三层数字、类型分布、成功率、命中榜（含时刻）与最忙时段，
> 并在清零后复跑一次证明报表读的确实是那份统计。

### 5.39 事件内容也要多端对齐：历史回填

**问题**：§5.37 把**统计**改成了后端权威，但**事件列表**还是"各存各的"。
后端模式下前端只做**增量轮询**（`/api/events?since=…`），且首拉只覆盖最近
1 分钟（`lastTime = Date.now() - 60000`）。于是每台机器的事件面板里都只有
「自己打开之后」那一段：
A 机昨天开过、能看到昨天的；B 机今天第一次打开、列表一片空白 ——
而真相是后端库里躺着**同一份完整历史**。

**做法**：页面载入（以及打开后端开关）时，从后端**整体回填**最近一批：

| 环节 | 位置 | 说明 |
|---|---|---|
| 取数 | `useBackendEvents.fetchBackendHistory(url, limit)` | `GET /api/events?limit=N`（**不带 since** = 最近 N 条，升序） |
| 条数 | `limit = maxEvents` | 跟着本机「最多保留条数」走；`store.recentEvents` 的上限从 **200 提到 2000** —— 卡在 200 会让"本机留 1000 条"的配置永远只拿到 200 条，两端内容还是对不齐 |
| 转换 | `useBackendEvents.backendEventToPayload` | 与实时轮询**同一份**转换（原来叫 `toPayload`，现在导出给回填复用） |
| 合并 | `useBackendEvents.mergeEventLists(existing, fresh, max)` | 纯函数：按 key 去重 → 时间倒序 → 截断；**重复时以后端那份为准** |
| 落库 | `App.vue` 的 `backfillHistoryFromBackend()` | 只把"本机没有的"写进 IndexedDB（同 key 不覆盖，本机原图不会被冲掉） |

**四个刻意的取舍**：

- **不写进 `onAlarm`**：`onAlarm` 会弹通知卡片、响铃、闪标题、走推送调度。回填几十条
  旧事件走那条路 = 一打开页面被几十条旧报警轰炸。所以抽出了 `buildRecord(payload)`
  —— 只造记录、**不带副作用**，实时与回填两条路共用同一份形状。
- **必须等历史加载完**：`loadHistory()` 是整体赋值（`events.value = list`），
  而后端开关那个 watch 是 `immediate` 的、在 setup 阶段就跑。所以回填由
  `historyReady` 把关（onMounted 里 loadHistory 落地后才置真），否则刚回填的整批
  会被紧随其后的赋值冲掉。
- **已读状态以后端为准**：回填进来的记录用后端行里的 `read`，而不是一律 `false`。
  已读本来就是**共享**的（任何一台标已读都会 `POST /api/read` 回后端），
  各机自己判会变成"A 标了已读、B 还亮着红点"。
- **同 key 不重复占位**：轮询与回填可能覆盖到同一条事件，`appendEvent` 现在按 key
  去重（IndexedDB 以 key 为主键，put 天然幂等）。不去重的话未读数会翻倍、
  事件面板看着像"重复报警"。

**纯前端模式**行为不变：没有后端可回填，事件仍只存本机 IndexedDB ——
「换台机器看同一份历史」这件事本来就依赖后端在跑。

> 验证：`/tmp/sync-probe/probe.mjs` 的 `[M]`/`[E]` 段 —— 合并函数去重/排序/截断/
> 不改入参、payload 映射、**真服务**下无 since 回填一次拿到 250 条（旧上限 200 会截断）、
> 升序、thumb 绝对 URL、已读条数与库里一致。回退验证：把 `recentEvents` 上限改回 200 → 探针红 2 条。

### 5.40 在线设备：谁在看着这个后端

**问题**：后端是**多端共享**的，但它完全不知道有几台设备连着 ——
用户问「现在几台设备在看」时，答案是"不知道"。

**做法**：新增 `server/clients.mjs`（纯函数，零依赖），把每次**带 cid 的请求**记一笔：

- **cid**：前端 `useClientId.js` 生成并落盘的 16 字节随机串（`localStorage`
  的 `monitor-wall-client-id-v1`）。**它不是凭据** —— 鉴权仍然走登录会话；
  清站点数据只会让名单里多一条设备。
  > ⚠️ 用 `crypto.getRandomValues` 而**不是** `crypto.randomUUID()`：后者要求安全上下文
  > （https / localhost），而本项目是**局域网明文 http** 部署，在那里它直接不存在。
  > 与 `sha256.js` 里「别用 `crypto.subtle`」是同一类约束。
- **心跳挂在事件轮询上**（`/api/events?...&cid=…&dn=…`），不另开 `/api/hb` ——
  页面本来每 4 秒就打一次，少一个接口、少一次请求。`/api/status` 也顺手记一笔。
- **只有带 cid 的请求才算**：健康检查的 curl、`/api/auth/info` 之类的前端探测都不带，
  于是名单里不会混进"根本没打开页面"的东西。
- `statusPayload` 里多一个 `clients` 快照：`{ online, total, onlineMs, list[] }`，
  每条含 `ip / label（UA 推出的设备+浏览器）/ name（前端自报的友好名）/ firstAt / lastAt / hits / online`。
- 展示在「设置 → 关于系统」的新区块「在线设备」：在线/总数、每台的状态点、
  设备名、IP、最近出现时间、请求次数，本机那条标「本机」。也进「复制全部信息」。

**边界（重要）**：

- **「在线」是推断，不是连接状态**：HTTP 无连接，判据只有"最近 `onlineMs`（90s）内请求过"。
  页面切后台会暂停轮询（省资源），所以这时会显示成「N 分钟前」而不是"掉线"。
- 名单**只保留最近 24 小时**出现过的，且上限 200 条（有人伪造 cid 刷请求也吃不光内存）。
- 快照里**只有 IP 与设备类型，不含任何凭据** —— 它随 `/api/status` 一起出去，
  而那是裸 HTTP 接口。

> 验证：`/tmp/sync-probe/probe.mjs` 的 `[U]`/`[E]` 段 —— 设备名解析的顺序陷阱
> （Edge 的 UA 里也含 "Chrome"，必须先认 Edge）、无 cid 不登记、同设备多次只算一台、
> 名单上限、超时判离线、以及**真服务**下两台设备分别经不断 cid 的状态查询与事件轮询被登记。
> 回退验证：去掉 `if (!id) return null` 那道闸 → 探针红 6 条。

### 5.41 首次打开：把「在同步」变成看得见

**问题**：局域网里另一台机器第一次打开这个地址时，页面要**先接管后端配置再能看**：
探后端 → 拉配置（通道 / 凭据 / 隐藏名单）→ 重建人脸库 → 回填历史事件 → 拉统计。
这一串全在后台异步跑，界面上什么都不显示：用户看到的只是一块空大屏，
不知道是"在同步"还是"这后端本来就是空的"。慢的时候（底库几十人、事件几千条）
会以为卡死，然后不停刷新 —— 而每刷一次都重跑一遍这一串。

**做法**：`src/composables/useSyncProgress.js` + `src/components/SyncProgress.vue`，
顶部居中一张卡片，五步与真实动作一一对应（`probe / config / faces / history / stats`）。

**两条刻意守住的线**：

- **进度必须是真的**：每一步由 App.vue 里那次**真实 `await`** 的起止驱动，
  不做会自己往前爬的假进度条 —— 假装在加载比不显示更糟，用户会等一个永远不来的结果。
- **不阻塞操作**：只是一层提示，可随时点掉；某一步失败页面照样能用。

**几个细节**：

- 失败时「进行中」的那一步自动标红、面板**常驻**（成功才自动收起，停留 1.8s）——
  否则用户根本看不到发生过什么。
- 人脸库那一步有第三种结果：后端底库为空时 `replaceFaces` 会**保住本机**，
  这时标成 `skip` 并写明「后端为空，保留本机 N 人」而不是 `done` ——
  `done` 会让人以为"人已经过来了"，而两边对底库的认识此刻并不一致。
- 手动拉取时整页重载从 700ms 延到 **1900ms**：让"已与后端对齐"先露够面再刷，
  免得刚显示完成就被刷新打断（看起来像"是不是又出错了"）。
- 承载它的 `SyncProgress` 挂在 App 里（**不是** SettingsDrawer）：首次打开时抽屉没开，
  而该看的恰恰是这一次。

> 验证：`/tmp/sync-probe/probe.mjs` 的 `[F]` 段（真实导入生产模块）—— 分步推进、
> 进度百分比、失败时"进行中"转 fail 且面板常驻、成功后未跑的收成 skip 并延迟自动收起。

### 5.42 `/hits` 也支持 `img` 开关：把命中的截图推出来

`/hits` 原本**只回文本**（`/hits [T|Y]`），要看图得改用 `/collect ... img`（那是全类型的事件）。结果是"我知道张三 09:00 来过，但想看一眼那张脸"这个最常见的诉求没有直路。现在 `/hits [T|Y] [img]`：**末尾加 `img`** 就连命中截图一起推。

**`img` 是开关，不是第二个参数**（这条最容易写错）：`parseDayScope` 先按 `SHOT_TOKENS` 把 `img`/`image`/`pic`/`图`/`截图` 摘出来，**再**校验日期记号。不摘的话 `/hits T img` 会被"只能给一个日期记号"的判据挡掉 —— 用户照着用法发却报错。`SHOT_TOKENS` 是**唯一一份**，`/collect`、`/search`、`/hits` 三条指令共用（原先各写一个数组，`/collect T pic` 认、`/hits T pic` 不认只是时间问题）。

**带 `img` 时它退化成 `/search img` 的形状**：先把「概览 + 命中明细」推到**这个会话**，再串行推截图，回执只回一句摘要（明细不重复出现两遍）。三条指令因此共用同一条 `imgChain` 与同一组节流参数（`dutyMaxImages` / `dutyImageGapMs`）。

**带 `img` 会抢 `running` 锁**（不带则不抢 —— 保持"只读、无副作用"的老行为）：

| | 不带 `img` | 带 `img` |
|---|---|---|
| 输出 | 答案就是回执本身（明细在回执里） | 明细推到会话 + 截图，回执只回摘要 |
| 串行锁 | **不占**（抢了会出现"汇总正在发图时问一句命中被拒"） | **占**（真的要逐张发图，与 `/collect`、`/search` 会互相插队刷屏） |
| 图 | 一张都不推 | 该时段**全部命中**的截图（不受明细 20 条截断影响） |

**四个坑，都是这轮真实踩到/测出来的**：

1. **图片说明必须补 `name` 字段。** 推送那套的 `captionOf` 读 `r.name`，而 store 的行里字段叫 `camName` —— 不映射就会每张图印出 `08:00:44 · <b></b> · 张三`（中间空一格，还挺难看出是哪里坏了）。`/collect`、`/search` 早就在那里映射了，`/hits` 是新加的路径，漏了。
2. **图覆盖"全部命中"，明细只列最近 20 条。** 这两者刻意不一致（文本不刷屏、图不丢），所以正文里必须写清楚，否则"列 20 条却收到 21 张"会被当成 bug。
3. **只统计命中，不等于"有图就推"。** 陌生人脸那条也有截图，`isFaceHit` 说不算命中就不推 —— 与文本口径共用同一个判据。
4. **`/hits T img` 并发时会被拒一次**（"⏳ 上一次查岗/汇总/检索还在处理中"），这是**预期的**：上一次推图轮次还没走完。不带 `img` 的 `/hits` 依旧随时能问。

**顺手修掉的两处过期文案**（都是我改的那份清单/同一屏里的）：

- 设置页的指令清单里还留着 `{ cmd: 'check', usage: '/check duty' }` —— 而 `/check duty` **上一版就并进 `/duty` 了**，照着设置页发会得到「未知指令」；同时清单里缺 `help` / `start` / `compile` / `search` 四条。已按后端 `COMMANDS` 对齐（`usage` 串必须逐字一致），并补了 `/tmp/hits-img-probe/parity-commands.mjs` 盯着这件事。
- 「静默查岗」调参那一屏的说明也写着 `/check duty`，同改为 `/duty`。

### 5.43 人脸库：同一人的多角度收纳，与「点了改名没反应」的真根因

两个来自使用的抱怨，其实是**同一个根因的两种表现**：

> 「待录入改名时候需要加入修改中状态，经常卡住」
> 「已录入的人脸，存在同一人多角度的抓取，显示上如何优化下，收纳下归类下」
> 「收纳应考虑，比如小刘下面有多种角度图片，推送时都要叫小刘」

**卡住的不是改名按钮，是数据库根本打不开。** `useEventStore.openDB()` 把 `dbPromise` 缓存起来，人脸/事件的每一次读写都要先拿到它。如果那一次打开请求**永远不落地**，`dbPromise` 就永远 pending —— 后面每一次 `transaction()` 都排在它后面，而拿不到 db 又**不会报错**。于是表现是"点一下没反应"，而不是"弹个错"。三条真实路径都会走到"永远 pending"：① **另一个标签页开着旧版本的连接** → 版本升级被阻塞，规范只响 `onblocked`（以前没监听，等于什么也没发生）；② 隐私/无痕模式的某些实现既不 success 也不 error；③ 升级被别的连接堵着。

**三处兜底，缺一不可**：

1. **`openDB` 加 `onblocked` + 10s 超时**（`OPEN_TIMEOUT_MS`）。`onblocked` 立刻报「本地数据库正被本应用的其它标签页占用，请关掉其它标签页后重试」；超时兜住"既不 success 也不 error"那类实现。
2. **两条路都清掉 `dbPromise` 缓存**。这条最容易漏：不清缓存的话，一次卡死 = **这一页永久失效**，只能刷新 —— 正是"经常卡住"的体感。超时后 success 才迟到时，还要 `req.result.close()` 把连接还回去。
3. **写链上看门狗（15s）**。人脸库的写操作（改名/删除/合并/录入）串行走 `runExclusive` 的 `writeChain`，队头卡住 = 后面全卡住。超时后**拒绝这次操作**而不是一直等 —— 队列是 `writeChain.then(run, run)`，拒绝也让后面照常跑，于是一次卡死退化成"这一下失败并弹窗"，而不是"整个人脸库从此不动"。另外后端模式下删待录入会 `await` 打后端的 `dropBackendPendingFace`，地址打不通又不回 RST 时 `fetch` 会一直挂着 → 卡片永远停在「录入中」，故给它加了 6s 的 `AbortController` 超时。

**「修改中」状态**：提交后整行立刻换成「保存中」、隐藏改名/删除、输入框 disabled；失败必弹窗且文案说清"名字没有改动"（用户得知道库里现在是什么状态）。状态按**组 key** 记（`renamingFace`）而不是一个全局开关：改 A 时顺手去改 B，A 的 `await` 回来不能把 B 的编辑框关掉 —— 以前就是这个 bug。

**收纳归类的两条判据**（不另立第二套判定）：

| 判据 | 说明 |
|---|---|
| 名字相同 | 用户自己定的，是**确定**判据 |
| 余弦相似度 ≥ 识别阈值 | 用设置页的 `opts.face.matchThreshold`（默认 0.38）—— **与识别判定共用同一个数**，否则会出现"推送说认出来了、库里却分成两个人" |

代表样本 = **最早录入的那条**（`getAllFaces` 本就按 `createdAt` 升序），组 key = `g${rep.id}`，`items[].sim` 是与该代表样本的相似度（代表自身为 1）。组内相似度报**最弱一环**而不是平均：并查集是链式合并的（A~B、B~C 都过阈值，但 A~C 可能不过），报平均值会把最松的那一环藏起来 —— 用户看着"平均 0.45 挺像"却不知道里面有一条只有 0.31。归类开关（"是否只按名字归"）存在 `localStorage` 的 `monitor-wall-face-group-sim-v1`，默认开。

**向量不进响应式**：512 维 × 人数若塞进 `ref` 会被 Vue 逐层代理，白花性能。用非响应式 `rawRows` 存快照 + `faceRowsVersion` 这个 ref 当"库变了"的信号供 computed 依赖。

**收纳的目的就是"推送里都叫小刘"。** 库里的 `name` 直接决定推送内容，所以：

- **改名必须整组改**（`renameFaces(ids, name)` 在同一个事务里改完）。只改一条会让同一人的不同角度各推各的名字，而且"同名归类"判据会**立刻让卡片散开**。
- **「合并为一条」更进一步**（`mergeFaces`）：把多角度的向量按**样本数加权平均**再**重新归一化**。归一化向量加权平均后长度 < 1，而"余弦相似度 = 点积"的前提依赖单位长度（见 `vecMatch.js`），不归一化会让相似度整体偏小、识别变差。合并后 `createdAt` 取最早、`samples` = 权重合计。
- **「合并为一条」按样本勾选**（组面板每条样本一个 checkbox + 头部全选，展开时默认全选，保持一键合并的旧习惯）：`doMergeGroup` 只把勾选的 id 交给 `mergeFaces`（`keepId` 取勾选的第一条，保序于 `items`），勾选 < 2 时按钮禁用并弹提示；没勾选的角度原样留在库里。为什么必须能让用户选：识别是 `matchFace` **逐条样本取最高相似度**，把不同角度全并成一张"平均脸"会丢角度覆盖（侧脸/低头对平均脸相似度中等，可能够不到阈值）—— 合并适合同一角度拍重了的去重 / 腾 `libMax` 名额，多角度样本应保留多条。删单张样本时同步清勾选里的 stale id（否则头部"全选"计数对不上）。
- **「手动拆分」卡片默认收起**：声明通常只有一两条，但每行都带解除按钮和说明文案，常显会把整页配置顶下去。标题行常显带数量（`手动拆分（N）`），点「展开」才铺开；展开状态是模块级 ref（`faceSplitsOpen`），关掉设置再打开不会被重置（与 `faceLibOpen` 同一理由）。

### 5.44 日常事件静默：按间隔把零碎事件摊平成定期播报

需求原话：

> 「在通道配置中每个通道新增一个功能，日常事件静默，即在非静默时段下，可选时间间隔，对非关键事件进行静默，每个时间间隔后仅推送汇总消息。关键事件推送配置加一个开关，即静默时段也允许推送」

拆成两件事：**一路一条的「日常事件静默」**，和**关键事件的「静默时段也允许推送」**。

#### 三套静默，互不替代

| | 触发方式 | 覆盖范围 | 收尾 |
|---|---|---|---|
| 全局免打扰 `options.silent` | 按**时段** | 全部通道、指定渠道 | 时段结束发**整体**汇总 |
| 通道静默 `cam.silent` | 按**时段** | 只这一路、指定渠道 | 时段结束发**本路**汇总 |
| 日常事件静默 `cam.digest` | 按**间隔** | 只这一路、指定渠道 | 每满一个间隔发**本路**汇总 |

前两者是"某段时间别吵我"，第三者是"平时就别一条条发，攒着定期播报"。三者**共用同一批渠道标签、同一个 `buildSilentSummary`、同一份统计口径**，只是措辞不同（`variant: 'digest'`）。

#### 三条铁律

1. **只在非静默时段工作（让位）**。此刻只要有任一静默窗口生效（全局免打扰 ∨ 这一路的通道静默），日常静默就**不吸收新事件** —— 否则同一条事件会同时进"静默汇总"和"日常汇总"两份。已经收进 digest 缓冲的那批**不丢**：窗口期间不发，窗口一结束由 30 秒心跳补发。
2. **不吸收关键事件**。判据是 `isFaceHit`（在库的人脸命中，`!!rec.faceName`），与推送收窄 / TG 直推 / `/hits` / 统计四处**共用同一份**。待录入满库（`pushDirectToUsers`）也从来不走 digest。但**系统通知（设备离线/上线、定时巡检）不是关键事件** —— 它们走 `sendDirect`，会被**另一套「系统日常汇总」**收掉（见下条）。关键事件（人脸命中 / 满库 / 静默提醒 / 静默汇总）无论何时都照推，不受系统汇总影响。
3. **没有事件就不发**。与通道静默一致：为"这段时间什么都没发生"补一条通知，等于把刚省下的打扰又还回去。

#### 判定只有一处：`defaults.camDigestState`

引擎（`useAlertPush.digestStateOf`）与展示层（`/cams`、设置页 `camDigestInfo`）都调它，只是各自把"此刻有没有静默窗口"喂进去。返回里 `active` 与 `pausedBySilent` 是**两个不同的"没生效"**：前者是"压根没开 / 一个渠道都没勾"，后者是"配了、也让路给静默窗口了" —— 设置页文案必须能区分，否则用户会以为配置丢了。各写一份判定的典型症状是「界面说在汇总、实际没汇总」。

**配置挂在 `cam.digest`**（与 `cam.silent` 同理）：随通道生灭。另开一张 `_camDigest: { 'cam-1': … }` 就得自己维护增删改名，迟早留下僵尸配置。

#### 日常静默「总开关全开」→ 多通道合并为一条汇总

`cam.digest` 原本是「每路各自一条」：开了 N 路就发 N 条本路汇总，乘上三端渠道 = N×M 条噪音。`allDigestEnabled(cameras)` 为真（**所有通道都开了 `cam.digest` 且各自勾了至少一个渠道**）时，日常汇总改成**合并为一条**，发给所有活跃 digest 通道的**并集**，攒在一个共享缓冲 `digestMerged` 里、由 30s 心跳统一到点发出。

- **吸收渠道 = 并集（`mergedDigestChannels`）**：合并汇总要发往并集，所以每条事件把**并集里所有渠道**都从实时 `send`/`queue` 摘掉，否则会出现「某路只勾了部分渠道 → 没勾的渠道漏成实时、与合并汇总重复」。`non`-合并模式仍按本路 `digest.channels` 摘（保持原语义）。
- **在库人脸命中也进合并缓冲**。判据仍是 `isFaceHit`，以前被 `!isFaceHit` 挡在门外，现在放行 —— 用户要的正是"汇总里单独强调是否命中在库人脸、命中次数、命中明细"。关键事件急推（`pushDirectToUsers 'face'`）照常、不受合并影响，日常汇总只做"记录"。
- **总开关切换的缓冲搬运**：开 ↔ 关 的判定用 `lastMergeOn` 记住上一拍；关 → 开 把各路 per-cam 缓冲并入手合并（不丢已攒事件），开 → 关 把合并缓冲**兜底发一条**（此时 per-cam 缓冲为空、继续各自汇总）。切换只发生在那一拍，搬运只做一次。
- **排程与成员**：`armMergedDigest`（幂等、让位给静默窗口）、`digestMasterOn`、`mergedIntervalMs`（优先 `options.digestIntervalMinutes`，否则取最短活跃间隔）、`flushMergedDigest`、`mergedDigestChannels` 是新增的引擎成员；返回对象里 `mergedDigestInfo()` 暴露 `{on, buffered, since}` 供展示层看"合并缓冲攒了几条"。

#### 日常静默与免打扰时段「交集」要体现出来

合并汇总（digest 变体）的时段若与全局免打扰 `options.silent` 的时段**重叠**，重叠期间事件由「免打扰汇总」单独推送、并**未计入**日常汇总。不点明的话，用户会以为"今天门口明明有人、怎么日常汇总里没有"。三处都要把交集摆出来：

1. **汇总正文**（`buildSilentSummary` 的 digest 变体）新增「⚠️ 与免打扰时段重叠」提示块，列出重叠区间，说明"重叠期间事件由免打扰汇总单独推送、未计入本汇总"。不重叠（没开免打扰 / 不重叠）则整块不出现。
2. **设置页**：开了总开关且配了免打扰时段时，提示"合并为一条 + 每日于免打扰 X 让位"的复合行为。
3. **后端 `/cams` 与 `/status`**：每路追加「每日于免打扰 X 让位」、整体汇总行加「（总开关全开 · 多通道合并为一条汇总）」「（每日于免打扰 X 让位）」说明。

计算口径：`silentYieldSlots(silentCfg)` 给出免打扰时段文案（"HH:MM~HH:MM"，跨零点带"次日"）；`silentOverlapSegments(cfg, startMs, endMs)` 按"今天零点 + 距天分钟数"展开跨零点时段并求交，返回毫秒区间。两函数都在 `defaults.js`。

#### 系统通知（设备离线/上线、定时巡检）也收入「系统日常汇总」

日常事件静默原本只收"报警类事件"。现在把**系统通知**也并入：设备离线/上线（`sendDirect` 的 `kind:'status'`）和**定时**巡检（`kind:'patrol'` 且 `digestable:true`）不再实时推，而是攒进一条独立的 `digestSystemBuf`，在**首个活跃 digest 通道**的间隔到点时作为「系统日常汇总」一次性发出。它与 per-cam 报警汇总**平行、各发各的**（一个事件报警走 digest，一个系统通知走 system digest，互不串）。

- **手动 `/patrol` 永远实时推**：`digestable:false` 的不吸收，即便 digest 开着也立即发。待录入满库（`pushDirectToUsers`）根本不走 `sendDirect`，关键事件单发不受影响。
- **判定复用同一份 `camDigestState`**：此刻**没有任何通道**处于日常静默生效态 → 系统通知**回退实时推**（不会憋死在缓冲里，缓冲里若有残留也逐条 `sendDirect({skipDigest:true})` 补发）；一旦有活跃通道就让位给 digest。
- **吸收与实时发送共用同一份渠道收口**：先按 `restrictIds` 收口，再按各渠道 `statusAlerts` / `patrol` 开关过滤。用户关掉了该类通知（比如三端都把 `statusAlerts.enabled` 设 false）→ **既不吸收也不实时发**，与原有行为一致 —— 否则 digest 会把用户明确关掉的通知又偷偷发出来。
- **排版复用 `buildSystemDigestSummary`**（`useDingTalk.js`），与报警汇总共用 `buildSilentSummary` 同一套间隔文案（`digestIntervalLabel`）；正文分「🔧 设备状态变动」「🧭 定时巡检」两段，头部写 `digestIntervalLabel(ctx.intervalMinutes)`。
- **`stopAll()` 一并清系统缓冲**：`digestSystemTimer` 拆掉、`digestSystemBuf` 清空、`digestSystemSeen` 清、`digestSystemSince` 归零。
- **远程开关**：`/digest`（总开关，一键开/关所有通道）、`/cdigest <通道> <on|off>`（单路）；两者都走配置落盘 + bump `configRev`，前端/其他端**自动拉取生效**（`App.vue` 的 `alignWithBackend` 在 `syncRev > localRev` 时 `pullFromBackend({reason:'silent'})`，无轮询死循环）。设置页监控通道 tab 顶部也有「日常事件静默（总开关）」一键接管所有通道（保留各通道独立的渠道与间隔）。
- **后端复用前端 `useAlertPush.sendDirect`**（headless-monitor.mjs 顶部"复用前端 useAlertPush 全套"）：改前端一处、前后端两种模式同时覆盖，不必各写一份。
- **一致性探针断言**：用户关掉 `statusAlerts`/`patrol` 时，系统通知既不进缓冲也不实时发，且不会误排系统汇总定时器。

#### 几个"看着能跑、其实会错"的细节

- **间隔从「本批第一条」算起**，不是从"上次汇总时刻"算起。按后者，空等一整天之后会立刻补一条空汇总；按前者，`due = since + intervalMs` 每次**重算**，用户改间隔能立刻生效，不必等下一批事件。
- **`clampDigestMinutes` 必须把「没配」和「配成 0」分开**。都丢给 `Number()` 的话，老存档里一个 `intervalMinutes: null` 会被化成 0、再夹成下限 **1 分钟** —— 变成"每分钟一条汇总"，比默认激进得多，而且看起来完全合法、不报任何错。（这条是探针逼出来的：先写了 `Number(v)` 版本，`clamp(null)` 断言直接报 `1`。）现在 `null / undefined / '' / [] / {} / true` 一律落回默认 30，显式数字 0 才夹到 1。
- **`DIGEST_INTERVAL_CHOICES` 只是界面下拉档位**，不是合法性判据；夹紧区间是 `[1, 240]` 分钟，脏值永不产 NaN。
- **让位时不许自己排"窗口结束后才响"的定时器**。那等于把两套时间轴搅在一起（静默窗口本身有自己的心跳与收尾），排出来的时长还得先算窗口还剩多久。让位就**收掉定时器、交给心跳重试**。
- **`stopAll()` 必须包含 digest**（"立刻安静下来"）。只清静默缓冲不清它，定时器到点照样把旧汇总发出去。
- **`addCamera()` 要给新通道带上 `digest`**（与 `silent` 同理）。这一条探针**测不出来**：`digestCfgOf` 有兜底、保存路径还有 `normalizeCameraDigest`，所以漏了它行为上也对 —— 属于"一致性问题"，不是功能 bug，别因为探针全绿就随手删掉。

#### 关键事件「静默时段也允许推送」

四类关键事件（`silence` 静默提醒 / `summary` 静默汇总 / `face` 人脸命中 / `pending` 待录入满库）在免打扰或通道静默期间**要不要照推**，现在由三处各自的 `throughSilence` 决定：钉钉 `dingtalk.critical`、企微 `wecom.critical`、TG `telegram.directPush`。

- **缺省 `true`，而且判定写成 `x.throughSilence === false` 才算关**。原因是老版本这几类是**硬编码放行**的，默认必须是"静默也推"，否则升级用户行为突变：原本夜里能收到的静默汇总 / 人脸命中，升级后突然收不到了。
- **"此刻在不在静默时段"只算一次，三端共用**（`criticalSilentBlocked(opts)` 在 `pushDirectToUsers` 里算完再传下去）。各端自己再算一遍迟早会漂。带 `camId` 时把**这一路自己的通道静默**也算进去 —— 不带就只认全局窗口。
- 设置页三处各加一个开关；**TG 那处整块是 `v-if="tg.directPush.enabled"`**，所以"关键事件单独提醒"没开时开关不显示（不是漏了，是整块收起）。

#### 汇总时刻对齐墙钟（整点 / 半点，#334）

日常静默的"到点汇总"原本是 `due = since + intervalMs`（`since` = 本批第一条事件到来的时刻）。副作用：用户 14:07 开启、间隔 30 分钟，汇总会落在 **14:37、15:07、15:37……** 这种错位点 —— 既不整齐也不好记。

改法：**间隔是 30 的整数倍（含整数小时：30 / 60 / 120 / 240 分钟）时，把"到点时刻"对齐到墙钟的 `:00` / `:30` 网格**，而非"开启时刻 + N 分钟"。非 30 整数倍的档位（1 / 3 / 5 / 10 / 15 分钟）维持原 `since + 间隔` 行为 —— 这些档位本就不指望对齐整点，对齐反而错。

- **纯函数判定** `isWallAlignedInterval(min)`：`clampDigestMinutes(min)` 之后 `n >= 30 && n % 30 === 0` 才走对齐；脏值（null / 0 / 非数字）先夹紧，不会误对齐。
- **求下一个网格边界** `nextWallBoundary(now, gridMinutes)`：以本地零点为锚，`Math.ceil(msSinceMidnight / gridMs) * gridMs` 求"≥ now 的第一个网格点"，与"开启时刻"无关、跨天自动续（14:30 之后下一个是 15:00，不会漂）。
- **三处调度 + 一处展示共用同一口径**：`armMergedDigest`（总开关全开 → 合并汇总）、`armCamDigest`（单路）、`armSystemDigest`（系统通知吸收），以及 `handleAlarm` 里给用户看的 `bufDue`（"将于 HH:MM 推送"标签）。展示与调度同口径，界面说的和实际排的不会两套。
- **零行为退化**：非对齐间隔完全走老路径，且对齐只在 `clampDigestMinutes` 之后判定，夹紧区间 `[1,240]` 之外的脏值永不触发对齐。

### 5.45 「事件原图」永远只有一张，两张裁图各自入列

**契约**（`server/store.mjs` 的 `events` 表 + `outEvent` 拼 URL 时共用）：

| 列 | 是什么 | 谁在展示 |
|---|---|---|
| `thumb` | **事件原图** —— 事发那一帧。对外只拼这一个 URL | 事件列表缩略图、详情页主图、`/hits img`、`/collect img`、`/search img`、导出 |
| `face_thumb` | 人脸特写（256×256） | 详情页「人脸」那一行 |
| `person_thumb` | 报警后补拍到的完整人形 | 详情页「完整人形补图」那一行 |

三条规矩：

1. **原图绝不写进裁图列，裁图也绝不顶掉原图。** 曾经的写法是「人脸事件自带特写 → 就用特写当 `thumb`」，于是 `/hits img` 推到群里的全是 96×96 的小图，事件详情页主图也是小图 —— 而人脸特写本来另有一列。另一处是补拍（`finishPersonShot` / `POST /api/shot`）拿补拍图覆盖 `thumb`。
2. **`updateEventShot` 的映射里仍留着 `thumb` 键**，纯粹是怕老调用方静默失效；注释写明了**任何调用方都不该再拿它覆盖原图**。
3. **取不到帧时 `thumb` 就留空**，宁可显示「这张没存到原图」，也不拿小图冒充原图（小图仍完整躺在 `face_thumb` 里，一点没丢）。

改动落点：`server/store.mjs`（加 `person_thumb` 列 + `insertEvent` / `updateEventShot` / `rowToEvent`）、`server/headless-monitor.mjs`（`handleEvent` / `finishPersonShot` / `POST /api/shot` / `outEvent`）、`src/App.vue` 的 `onAlarmShot`（本地补拍只写 `personThumb`）、`src/composables/useBackendEvents.js`、`src/components/EventPanel.vue`。

验证这个改动时踩到的两个坑，都值得记住：

- **`store.open()` 是懒执行的**。想用 `PRAGMA table_info` 验「老库被补上了新列」，必须先调一次真接口（比如 `store.eventCount()`）把库打开，否则 PRAGMA 看到的是**迁移之前**的结构 —— 表现成一条毫无道理的假失败。
- **UI 探针跑的是 `dist/` 产物，不是 `src/`**。变异了 `src/components/*.vue` 却不重建 dist，探针当然全绿 —— 于是「变异无效」会被误判成「断言漏网」。变异脚本里要按 `needsBuild(file)` 判断、该重建就重建。

### 5.46 关键事件的「人脸命中」推哪张图，以及「配了却收不到」的几个闸门

**推哪张图**：`useAlertPush` 里关键事件直推（`pushDirectToUsers`）带的是**事件原图**，取值为 `record.shot || record.thumb`，与日常推送完全一致。放大的脸由 `pushFaceShot` **另外单独补一条**（那条才是「特写」语义，且只发给勾了人脸分组的渠道）。

**⚠️ 千万别写成只认 `record.thumb`**：后端 `handleEvent` 会把 `record.thumb` **覆盖成落库用的相对路径**（`saveShot()` 的返回值），推送侧拿它当图时 `dataUrlToBlob` 会解出 **0 字节**的空 Blob，于是整条消息静默发不出去 —— 表现就是「人脸命中一条都没推」。`record.shot` 才是 dataURL。这条已用变异实测钉住（把取值改成 `record.thumb` → 直推字节数 0 / 钉钉上传 0 字节 / 企微 `undefined×undefined`）。

**三端共用同一个 `payload.image`**（TG 私聊 / 钉钉 critical / 企微 critical 都吃它），所以「保证三端都带事件原图」只需要改这一处。

**「配了接收人却收不到」的闸门**（`pushDirectTg` 依次判，任一不过就安静 `return { sent: 0 }`，界面上不会有任何报错）：

1. `telegram.directPush.enabled !== true` —— **默认关**。只配了「授权用户名单」但没打开这个总开关，接收人算出来是**空数组**（`directPushRecipients` 第一行就 `return []`）。
2. `directPush.events.face === false` —— 被显式关掉（缺省即开）。
3. 接收人为空：接收人 = 授权用户 `telegram.remote.allowUserIds` + `directPush.chatIds`，去重、去空，并**排除主会话 `telegram.chatId`**。
4. TG 渠道本身不可用（未启用 / Token 或会话 ID 不全）。
5. 此刻在静默时段（全局或该通道）且 `directPush.throughSilence === false`。

排查顺序：`GET /api/status` 看 `push.tg`（渠道可用性），再给机器人发 **`/status`**，看那一行 **`📨 关键事件单独提醒：已开启（N 个接收人）`** —— 开关没开、或 N=0，都在这里一眼看出来。另外别忘 Telegram 的硬限制：**机器人不能主动给从没跟它私聊过的用户发消息**（403 / chat not found）。

> 端到端探针 `/tmp/directpush-probe/`：真服务 + 假 Bot API + 假钉钉/企微 webhook + detector 替身（人脸库播种的向量与替身一致 → 必然命中）。配置齐全时三端 20 条断言全绿（钉钉上传 16229 字节 = 事件原图；企微 640×480 = 整帧，而非 256×256 人脸特写）；三个负向场景（关总开关 / 关 `events.face` / 清空接收人）各自**一条都不推**，而日常推送照常。

### 5.48 待录入录入改为「非阻塞」：优先录入写、暂缓后端删除

用户痛点：待录入的人脸点「录入」经常卡在「录入中」好久才消。

根因（`SettingsDrawer.vue` 的 `doAddPending`）：旧代码在 `await addFace(...)` 之后**又 `await dropBackendPendingFace(...)`**。后端删除带 6s `AbortController` 超时，而对方若「打不通又不回 RST」（拔网线 / IP 变了 / 防火墙丢包），`fetch` 会一直挂着直到超时 —— 于是卡片停在「录入中」、点别的也没反应。删不掉本来只影响「下次刷新它又出现」，不值得拿界面响应性去换。

改法：**落库即解锁、后端删除放后台不 await**。

- `addFace` 落库成功后，立刻本地乐观移除卡片：后端来的待录入走 `dropBackendPendingFace(url, backendId)`（其内部**先同步**把本地镜像 `filter` 掉再 `fetch` 服务端），前端内存队列走 `removePendingFace(pf.id)`；**两者都不 `await`**，紧接着 `delete enrollingPending[pf.id]` 解锁界面。
- 网络删除失败 / 超时不影响用户 —— 最坏情况是重启服务后那条待录入又回来，但用户已经把它录进人脸库了，再来一次「忽略」即可，远比界面卡死强。
- `dropBackendPendingFace` 自身仍保留 6s 超时（服务端真通时正常删掉，避免「刷新又冒出来」）；只是调用方不再被它拖住。

**回退验证**：探针把 `/api/pending-face` 做成「收到请求但不回响应」（挂起）。若代码真 `await` 了删除，卡片要等 ≥6s 才消失；实测 25ms 即消失，证明非阻塞路径成立，且请求确实发起了（fire-and-forget 已记录）。

### 5.50 人脸库独立 IndexedDB 连接：根治「本地数据库写入超时（15s）」的级联

用户反馈「人脸录入 / 改名时**经常**报『本地数据库写入超时（15s）』」。根因不是偶发慢，而是**两个叠加的结构问题**：

1. **写链上的死事务级联**（主因）。`runExclusive` 的 15s 看门狗（见 5.43）在超时时只 `reject` 了这一次操作，让队列继续 —— 但**卡死的那条 IndexedDB 事务仍挂在连接上没结束**。同一连接上的事务是**串行**的，于是下一次人脸写排在它后面 → 一起卡 → 再看门狗 → 再报 15s，**一次卡死退化成"整个脸库从此每次操作都超时"**。
2. **与事件写共用连接造成的拥堵**。人脸写和检测器的事件落库（`useEventStore` 的 `putEvent`，常带整帧截图）本来共用**同一个连接**（`dbPromise`）。实时检测每有报警就往同一个库写截图，人脸写只能排在其后。

改法：**给人脸库单开一个「同库不同连接」**（`useFaceLib.js` 的 `openFaceDB` / `resetFaceDB`）。

- **IndexedDB 的事务只在「连接内」串行，跨连接可并行** —— 所以人脸写不再被事件写堵住，正好落实「**优先录入、其余写入暂缓**」。
- 写超时时（看门狗触发）**先把人脸连接重置掉**（`resetFaceDB()`：`close()` + 清缓存），再报错 —— 死事务随连接关闭而消亡，后续人脸写立刻能走新连接，**级联被斩断**。重置只关人脸连接，**不动事件写**（那是另一个连接）。
- 建库时人脸连接把**两张表（`events` + `faces`）都补齐**（幂等）：人脸连接与事件连接同库同版本，谁先 open 谁触发这一次的 `onupgradeneeded`，漏建另一张表就会出事。
- 安全边界：重置只发生在**写超时**（那条写本来就会失败，事务是原子的，不会留下半成品）。

> 回归：`/tmp/face-assign-probe/` 34/34、`/tmp/enroll-probe/` 21/21、`/tmp/pending-shot-probe/` 15/15 全绿（人脸读写改走独立连接后功能不变）。

### 5.51 人员流向（跨摄像头走向检测）

「人员流向」回答的是**"同一个人是不是从 A 走到了 B"**这一类问题 —— 比如"门口出去的人，是不是进了办公区"。它不是实时轨迹画线，也不是跨摄像头连续追踪，而是**离散相遇 + 身份关联**的轻量判定。

**判定本质**

1. 同一路摄像头内，一个人离开某个区域（**出场**）会记一条 `departure`；之后他在另一路（或同一路）某个区域**入场**，引擎尝试把这条入场和之前那条出场按**同一个身份 + 时间窗**配对。
2. 身份来源（见 §5.24）：默认靠**人脸 embedding 的归组名**（`gid`），零额外推理；也可放宽到不要求人脸（陌生人也能配，但误关联概率更高）。
3. **支持多跳串联**：一条流向是一串有序节点 `A → B → C → …`（最多 8 个），必须按序走完才算一次走向事件；任一段超时或错序即断链。方向单向（出场必须先于入场），每条 departure 配对成功后一次性消费。

**配置（`options.flows`，设置页 → 检测识别 → 人员流向）**

- 每条流向：`name`、有序 `path`（每个节点 = 摄像头 + 区域）、`windowSec`（相邻节点最大间隔，默认 120s）、`requireFace`（是否要求人脸身份）、`push`（是否推送）、`asCritical`（是否走关键事件实时急推）。
- 至少 2 个节点；相邻节点的摄像头 + 区域不能相同；节点引用的摄像头与区域必须真实存在（否则该流向标记"配置无效"，不生效）。
- 旧版 `from/to` 双节点配置会自动迁移成 `path`。

**与「走出 / 走入区域」报警开关彻底解耦（重要）**

- 走出 / 走入区域是**报警开关**，只控制"这个事件要不要作为报警上抛到事件面板 / 推送"。
- 无论这两个开关开还是关，只要通道级「区域规则」开着、且该区域的 `enterExit` 开着，**走进 / 走出事件都会喂给流向引擎做配对**。
- 所以：你**关掉「走出区域」报警 → 没有走出报警，但流向照常工作**；哪天又想收走出报警，**打开「走出区域」即可，流向也照样工作**。**不存在一刀切**——报警开关和流向检测是两件独立的事。
- 唯一不能省的前提：要产生走进 / 走出事件，通道级「区域规则」和该区域的「进出」标签得开着（那是"要不要检测区域事件"，不是报警）。
- **前提自动保活（防手滑静默失效）**：保存流向时，系统会自动把该流向路径上各节点的**摄像头「区域监测」**与**区域「进出检测」**强制开启（只在确为关闭时改、绝不凭空造区域、绝不碰报警开关）。这样"配了流向就不会因不小心关掉检测而失效"。若你**故意**在区域规则页把某个流向节点的「进出检测」关掉，流向不会悄悄失效——设置页该流向会标红「🔴 前提未满足」、`/status` 也会列出，提醒你这一条走向暂时派发不出来。

**为什么能复用现有管道**

走向事件复用了既有的 `emit('alarm') → onAlarm → handleAlarm` 链路（`type:'flow'` / `source:'flow'`），推送 / 事件面板 / 通知卡片零改造即可接收。`asCritical` 的走向事件走关键事件实时急推（三端缺省即开）；普通走向事件进静默 / 日常汇总吸收，文案标签为「人员走向」。

**性能**

默认人脸档几乎零额外推理——只消费检测器已经算好的人脸 identity 做哈希配对；贵的部分（ReID）做成了 opt-in 默认关。引擎内存受 TTL + LRU 硬上限（2000）约束，惰性淘汰防膨胀。

**状态可见性**

`/status` 远程指令（见 §八）现在会列出「🚶 人员流向」小节：规则总数 / 已启用 / 当前生效，并逐条给出路径与生效状态（未生效会区分「⚠️ 配置无效」与「🔴 前提未满足」并附原因）；设置页该 tab 上也带 on/off 总览徽标。

### 5.52 人脸库「手动拆分」：显式声明「这两个不是同一人」

**背景**：归类判据（§5.44 一族）是**概率**——「同名 ∨ 余弦 ≥ 识别阈值」，链式并查集会把两个长得像的人误并到一张卡（用户看到的「大刘」卡片里住着「黎」即此）。改名 / 手动归入都治标：把一条样本改名到另一个人，**相似度仍在，下次刷新又被并回去**。用户的原话是「这两个是我归纳的独立分组」——这是**确定事实**，必须有一条优先于一切自动判据的路。

**功能与语义**

- 混合名组（`sameName === false`）的面板头部出现「**按名字拆分**」：组内每两个不同名字之间记一条声明（样本取两名字簇的笛卡尔积），确认后人各自成卡、推送各叫各的名。
- 声明持久化在 IndexedDB 新表 `face-splits`（`DB_VERSION` 2→3，两个连接的 `onupgradeneeded` 都已幂等补建，谁先 open 都能建全），**重启 / 换浏览器不丢**；底部「手动拆分」列表可见全部生效中的声明，逐条「解除」（解除后恢复自动归类——这正是"解除"的语义）。
- 声明是**双轨**的：`{aId, bId, aName, bName}`（`defaults.normalizeFaceSplits` 归一化，容忍 `{nameA,nameB}` 单名字写法、去重、跳过全空）：
  - **id 对**管「改过名」——黎→老黎后 id 没变，仍拆着（名字对此时已失效，id 对兜底）；
  - **名字对**管「之后新录入」的同名样本——id 对覆盖不到还没录进来的脸。
- `groupFaces` 里做的是**簇级检查**（每簇维护 id 集合 + 名字集合）：只拦「这一对样本」不够，A~C~B 的链式合并会把拆开的两人又合回去；合并前看的是"并起来之后簇里会不会同时出现某条声明的两侧"。
- **改名统一自动退休**：`renameFaces` 后若声明两侧名字被改成一样（用户已把这两人统一），声明自动删除；名字仍不同则只更新记录里的名字。否则「归入到…」会被旧拆分挡着，表现为"点了归入没反应"。
- 与「同一人归类显示」开关（`bySimilarity`）正交：关掉它只按同名归类；拆分声明在两种模式下都生效。

**后端同步（`npm run server` 模式下必须）**

后端模式下识别与推送都在服务端，不把声明送过去就是「库里分开了、推送还并着」：

- `faceSplits` / `faceGroupSim` 随配置同步：进 `App.vue` 的 `backendPayload` 与 `backendSyncSignature`（依赖 `faceSplitsVersion`，缓存刷新后重算指纹）；POST `/api/config` 由 `applyIncomingConfig` 收（`faceLib.setSplits` / `setGroupSim`，声明 normalize 后落盘 `cfg.faceSplits`）。
- **空白闸门同理**：未对齐的客户端（`baseRev = 0`）推 `faceSplits: []` 上来会抹掉后端攒下的声明（"拆好的两个人又并回去"，且无任何报错）→ 拦下并回执 `splitsSkipped`（与 `facesSkipped` 同一套判据、同一种回执）。
- GET `/api/config` 回传 `faceSplits` + `faceGroupSim`；拉取时前端 `replaceFaceSplits` 整体替换、并把「按相似度归类」开关随后端（老后端不带这两个字段 → 原样保留本机，不做无依据的替换）。
- 服务重启后从落盘配置恢复（`main()` 里 `faceLib.setSplits(cfg.faceSplits || [])`），日志可见「✂️ 拆分声明 : N 条（重启后已恢复）」。
- 识别路径：`server/analyzer.mjs` 主检测与补拍两处都改调 `faceLib.matchFaceGrouped`——先 `matchFace` 找最像样本，再用**同一份** `groupFaces` 映射到组代表名；推送 `faceName` / 事件 `text` / 冷却键（按组算，同组不同角度不重复发）全部按组名走。判定函数是前端 `useFaceLib.groupFaces` 本体（Node 顶层只 import vue，链安全），不另写第二套。

> 回归：`/tmp/face-split-probe/probe.mjs` **40/40**（A 组：无拆分复现误并 / id 对拆分 / 名字对保护新样本 / 链式穿透被堵 / 装饰性改名 id 对兜底 / 两侧同名声明被忽略 / `bySimilarity:false` / 脏数据；B 组：`normalizeFaceSplits` 归一化六项；C 组：后端真实 SQLite 下 `matchFaceGrouped` 有/无声明两种推送名、陌生人 miss、空库 miss、副本隔离；D 回退验证：splits 置空后并回 1 组、后端推送名回到组代表——证明断言由声明决定，不是恒真）。

## 六、各端运行方式

### 0. 通用准备

```bash

```

vite 已配好 `127.0.0.1` 绑定，并内置了钉钉 / 企微的本地反向代理（浏览器直连这两个官方接口必被 CORS 拦）。

### 2. Web 生产构建 / 预览

```bash

```

### 3. 常驻后端检测服务 ★

这是「7×24 无人值守」的正式跑法：

```bash
npm run server                               # ★ 日常就用这条：按 server/config.json 启动，默认 8787
node server/headless-monitor.mjs --port=9000 # 换端口
npm run server:status                        # curl 一下 /api/status 看状态

npm run serve:drop                           # 只有陷入重启循环时才用（见下）
node server/headless-monitor.mjs --drop-pending   # 与上一行完全等价
```

> **⚠️ 别把 `npm run serve` 当成后端。** 它和 `npm run serve:drop` 名字像，其实是两回事：
> `serve`（见 §7 便携版）起的是**纯静态文件服务**，只反代了钉钉 / 企微那两个**外网**接口，
> **不托管本机的后端 API**。用它打开大屏，事件、配置同步、推送、远程控制全都不可用（都得有后端）。
> `npm run server` 则是**一条命令把大屏 + HTTP API + 采集检测 + 推送 + 远程控制全带起来**，
> 后端会把 `dist/` 一起托管在同一个端口上，所以日常只需要这一条。
>
> 一句话记法：**要看大屏且要功能 → `npm run server`；只想要个静态页 → `npm run serve`。**

> **`--drop-pending` 什么时候用**：如果服务**一启动就反复重启**，多半是 Telegram 那边积压了旧的
> `/reboot confirm`（详见下面「反复重启」小节）。带上这个参数启动一次即可清除，日志会报出
> 清掉了几条；下次正常启动就不用再带。它只作用于本次启动，不会被自重启的子进程继承。
>
> 两条使用纪律（不然它反而会帮倒忙）：
> ① **不要当默认启动命令**。它的语义是「把停机期间收到的指令全部丢弃」——
> 你停机时发的 `/status`、`/duty` 会一起没了，而且会掩盖真正的故障原因
> （现在游标已落盘 + 有循环保护，重启循环本不该再发生，若还需要反复清积压，说明另有问题）。
> ② **服务已经在跑时别执行它**。好消息是这种情况下它是**安全的**：程序会先在端口上撞满
> 40 次重试（约 10 秒）后报 `EADDRINUSE` 退出，**根本走不到清积压那一步**，代码不会去动积压。

Windows 上直接**双击 `start-windows.bat`**（会自动开浏览器并启动服务，窗口保持打开即代表在跑）。

启动后：

- 浏览器打开 `http://<这台机器的IP>:8787` 就能看大屏（后端会顺便把 `dist/` serve 出去）；
- 前端「设置 → 检测识别 → 后端检测服务」打开，填入这个地址（默认预设 `http://10.0.0.12:8787`），配置会自动同步过去并热生效；
- 想让它开机自启：Windows 用「任务计划程序」或 NSSM 装成服务，macOS 用 launchd，Linux 用 systemd。

首次启动会**自动下载 ffmpeg（≥7）**到 `server/.cache/`，需要联网；离线环境先在有网的机器上跑一次 `npm run ffmpeg:fetch` 再把 `.cache` 带过去。

## 七、配置说明

配置分成两层，互不污染（`src/config/defaults.js`）：

1. **初始化配置（`DEFAULT_*`）**：「空白」—— 打开就是一块空大屏，没有通道、没有推送凭据、AI 附加能力全关。设置里的「恢复初始化」就是回到这一份。

内置隐藏配置里的 7 路：**门口 / 电梯 / 大厅**（开检测 + 推送），**厕所 / 通道1 / 通道2 / 楼梯**（默认隐藏，设置里把「显示」打开即可恢复）。

## 八、远程控制指令

前提：`telegram.remote.enabled = true`，且你的 `from.id` 在 `allowUserIds` 里，且**必须是私聊**。

| 指令 | 作用 |
|---|---|
| `/help` | 查看全部指令。**常用指令平铺展示**；系统操作类（关机 / 重启 / 终止服务等危险动作）单独收进一块，只给概览 + 引导「发送对应指令看详情」，不堆完整说明。输入 `/` 也能唤起命令菜单 |
| `/silent <小时数> [渠道]` | 开启临时静默，如 `/silent 2`（开启与结束都会推送提醒，期间报警收存、结束时汇总）。不写渠道就走设置页那份默认（钉钉 + 企微）；也可临时指定：`/silent 2 wecom`、`/silent 2 ding,tg` |
| `/until <HH:MM> [渠道]` | 静默到指定时刻（今天已过则顺延到明天），如 `/until 08:00`，同样可跟渠道 |
| `/resume` | 立刻结束临时静默，并推结束提醒 + 已收存报警汇总 |
| `/csilent <通道> <小时数\|HH:MM\|off> [渠道]` | **通道静默**：只让**某一路**在指定时段不推送（见 5.6.2）。`/csilent 门口 2`（门口静默 2 小时）、`/csilent 门口 08:00`（静默到 08:00，已过则顺延明天）、`/csilent 门口 2 ding`（只静默钉钉；不写就用这一路配置的渠道）、`/csilent off 门口`（提前恢复这一路）、`/csilent off`（恢复**全部**通道的临时静默）。通道可写名称（门口）、id（`cam-1`）或序号（`1`）；名称包含命中多个会**报歧义**而不是挑第一个。与整体静默是**并集**，互不干扰 |
| `/cams` | **通道状态**：逐路列出在线/出帧/画面人数/错误，以及这一路的通道静默状态（生效中 / 已配但当前未生效），末尾附整体静默一行。与 `/status` 的分工：`/cams` 只看通道，`/status` 看整机 |
| `/patrol` | 立即推送一次巡检报告（各通道状态与功能开关） |
| `/status` | **完整运行状态**（口径与设置页「关于系统」同一份快照）：🕐 运行（系统运行时长含中断 / 中断累计 / 系统起点 / **本次进程**时长 / 配置 rev / 模型 / ffmpeg 版本与偏低警告）· 📹 通道（出帧 N/M、未出帧名单、仅监控不跑 AI、当前画面人数、累计出帧、**🔕 通道静默**摘要行）· 🧠 检测能力（模型就绪四项、功能开关三项、人脸库人数）· 🚶 **人员流向**（规则总数 / 已启用 / 当前生效，逐条路径与生效状态；与走出/走入报警开关相互独立）· 📣 推送渠道（三渠道 ✅❌、静默状态与静默渠道、关键事件单独提醒是否开启）· 🤖 远程控制（监听状态、收到/执行/拒绝/失败、授权人数、最近指令、游标落盘失败）· 🗂 事件记录 · 🔐 登录 |
| `/collect [T\|Y] [起-止] [img]` | **时段内事件汇总（整天完整、不再按 1000 条截断）**：`T`=今日、`Y`=昨日（省略为今日），起止按小时或 `时:分`（省略为全天）。**人脸命中逐个列出每次记录**；汇总过长会**自动分多条**发送。例：`/collect T`（今日全天）、`/collect T 9-18`、`/collect Y 00-08:30`、`/collect T img`（连截图一起推） |
| `/hits [T\|Y] [img]` | **人脸库概览 + 人脸命中记录**：先给「待录入 N 张未建档 + 已录入名单（当前实时状态）」，再列命中**已录入人脸**的记录（陌生人脸不算），给出命中次数 / 涉及人数 / 通道数 / 逐条明细（时刻 · 通道 · 姓名 · 相似度）。例：`/hits Y`。默认答案就是回执本身（不另推汇总、不占查岗的串行锁）；末尾加 `img` 才把该时段**全部命中**的截图推过来（那时会占串行锁，回执只回摘要）—— 见 §5.27、§5.42 |
| `/check duty` | **静默查岗**：推静默期间积压事件的汇总 + 全部截图；再发一次只看增量 |
| `/duty` | 同上（短别名，**也单独注册进了命令菜单**，手机上手打更省事） |
| `/reboot` | 重启检测服务（需另开 `allowReboot` + 回复 `confirm`） |
| `/stop` | 终止监控服务（仅退出本进程，机器仍开机，需手动重启服务才能恢复；需 `allowReboot` + 回复 `confirm`）。与 `/reboot`（重启服务）、`/hardreboot`（重启机器）、`/shutdown`（关机器）构成四级生命周期动作 —— 门槛比关机轻，**不需** `systemReboot.enabled` |
| `/hardreboot` | 重启整台电脑（需 `allowReboot` + `systemReboot.enabled` + 回复 `confirm`） |
| `/shutdown` | 关闭整台电脑（比硬重启更彻底：断电后需人工开机或主板通电自启才回得来；同样需 `allowReboot` + `systemReboot.enabled` + 回复 `confirm`）。`systemReboot.enabled` 这个开关同时解锁 `/hardreboot` 与 `/shutdown` 两条电源指令 |
| `/db` | **导出运行数据库**：把当前运行的 `monitor.db`（含报警 / 人脸 / 统计 / 待录入）用 `db.backup()` 在线热备成自包含单文件，直接发到发指令的这个私聊。还原：把下载的 `.db` 拷回 `server/data/monitor.db`（已含 WAL，无需 `-wal` 文件） |
| `/config` | **导出当前生效配置**：把后端现在实际在用的那份配置（通道 / 区域 / 推送 / 人脸库，含 `configRev`）打包成 JSON 发到本私聊；与设置页「配置方案 → 导出当前配置」同构，但导出的是**运行中**的，不是 config.json 旧快照 |

`/checkduty` 与 `/check duty`、`/duty` 三者等效。

> **`/db` 与 `/config` 的安全口径**：与既有的裸 LAN 接口（`/api/config` 等）一致 —— 仅在**私聊 + 白名单**内可用（`tg-remote.mjs` 的 `checkPermission` 已拦住群聊与非授权来源，且非白名单用户**连回执都不给**，避免探测机器人能力）。文件通过 Telegram 私聊直接发回「发指令的那个人」，不经过任何 web 路径、不生成临时下载链接。导出的是整库 / 整份配置，敏感信息（推送凭据、人脸数据）随文件一起走 Telegram 加密通道 —— 和 `/api/config` 同等信任级别，若要给整组 HTTP 接口统一加网关，这两个指令一并被覆盖。

### `/collect`、`/check duty`、`/hits` 的分工（最容易混的一对）

| | `/check duty` | `/collect` | `/hits` |
|---|---|---|---|
| 区间 | **静默窗口开始 → 现在**（相对） | 用户指定的**绝对时段**（今日 / 昨日） | 同样指定**绝对时段**（今日 / 昨日） |
| 内容 | 区间内全部事件 | 区间内**全部**事件 | **只**挑出命中已录入人脸的 |
| 游标 | 有，再发一次**只看增量** | **没有**，重复发同一时段结果相同 | **没有**，同左 |
| 前提 | 必须处于静默中，否则只回提示 | 任何时候都能用，与静默无关 | 同左 |
| 截图 | 一律把区间内全部截图推过来 | 默认不推，末尾加 `img` 才推 | 一律不推（答案就是回执本身） |
| 串行锁 | 占 | 占 | **不占** |
| 用途 | 「静默期间积压了什么」 | 「昨天下午两点到五点有人来过吗」 | 「昨天**都有谁**来过、各几次」 |

`/collect` 的参数细节：

- **三段（日期 / 时段 / `img`）都可省略，也可换序**，按空白分开写即可：`/collect Y 9-18 img`、`/collect img`、`/collect 9-18`。
- **日期**：`T` = 今日、`Y` = 昨日（`t`/`y`、`today`/`yesterday`、`今日`/`昨日` 都认），省略为今日。
- **时段**：`9-18`、`9:30-18:00`、`9~18`、`9至18` 都认，省略为全天。
- **终点含整分钟**：`9-18` 实际覆盖 `09:00:00 ~ 18:59:59`，即 18:00:30 那条也算 —— 按 18:00:00 硬切会把边界那一条漏掉，而写 `9-18` 的人要的是「到 18 点为止」。回执里仍按你写的样子显示 `09:00 ~ 18:00`。
- **终点早于起点 = 跨零点**：`22-2` 表示当天 22:00 ~ 次日 02:59（与静默时段的跨零点口径一致）。
- **时段还没走完会点出来**：省略时段即全天，白天查「今天」必然没走完，回执会补一句「该时段尚未走完（现在 HH:MM），以上只是到目前为止」—— 否则上午看到「没有捕获到任何事件」很容易被读成「监控坏了」。
- **整天完整汇总，不再按 1000 条截断**（用户要求「要看完整数据」）。真正的天花板是 Telegram
  单条 4096 字符，不是库能查多少条 —— SQLite 一天几千条毫无压力。所以 `/collect`：
  - 查询上限提到 **20000 条**（`store.listEventsBetween` 的防呆上限，与之一致），
    统计口径覆盖**区间内全部事件**；
  - 汇总正文**不再截断**，而是**按行切成 ≤3500 字符的多条**依次发送（`sendLongText`），
    回执里如实写「汇总分 N 条发出」。按行切是为了不把头部的 `<b>…</b>` 标签劈开
    （跨条的标签会被 Bot API 以 `can't parse entities` 直接拒掉）。
  - 只有真到了 20000 条才会提示「可能有遗漏」（一天不可能真有 2 万条报警）。
- **人脸命中单独成区，且「统计次数 + 命中明细」两样都给**（用户最终要求，各类汇总统一）：
  区里先「共 **N** 次命中 · **M** 人」总账 + 按人计数（谁来了几次、最近几点、哪几路、相似度），
  再跟一个「命中明细（逐条）」小标题，逐条列 `时刻(秒) · 通道 · 姓名 · 相似度`（时间正序、不折叠）；
  陌生人脸单独计一句「另有 N 次未识别的人脸」，不计入命中。**没有命中时整块不出现**（不摆「0 次」占位）。
  通用「事件明细（前 N 条）」在**推送类汇总里一律省去**（人脸命中已逐条 + 按通道/按类型统计就够），
  只有 `/collect` 手动回查（`variant:'range'`）还按 `hideEventDetail` 开关摆。
- 汇总与「静默结束汇总」「静默查岗」复用**同一个生成器**，只是标题换成「监控事件汇总」—— 这段并没有发生静默，写「静默时段」会让人以为系统记错了。
- 结果发回**你发指令的那个私聊**（不是配置里的 `chatId`，那可能是群）。

> 指令菜单通过 `setMyCommands` 注册进 Telegram，输入 `/` 会自动弹出候选，不用背。`check` 与 `duty` 都注册，两条都会出现在候选里；`collect`、`hits` 也各有独立指令名，同样在菜单中。
>
> ⚠️ **指令表有两处，加指令时两处都要动**：`server/tg-remote.mjs` 的 `COMMANDS`（真正决定菜单注册与 `/help` 内容）和设置页的 `TG_COMMANDS`（「可用指令」列表的展示）。两处漂移的表现是「菜单里有、设置页列表里没有」（或反过来），而不是报错。`/hits` 就是照着这条规矩两处一起加的。
>
> **`/silent`、`/until` 默认静默哪几端**，在 `TG 推送 → 远程控制 → 可用指令` 里配（默认钉钉 + 企微）。指令里写渠道可以临时覆盖；一个都没勾则远程指令会**拒绝执行** —— 详见 5.6.1。
>
> **远程控制是热生效的**：在设置里打开开关并保存，监听器会立刻起来，不需要重启后端。设置页「远程控制」区还有诊断面板（机器人身份 / Token / 白名单 / 最近被拒原因）和「测试连接」「删除 Webhook」两个按钮 —— 「配好了却没响应」的六种成因都能在那里直接看到结论。
>
> **`/status` 只回结论与统计，不回凭据**：不返 Token、不返白名单 id、不返账号名（`/api/status` 本身就是裸 HTTP 接口）。白名单只回「N 人」这个数字。
>
> **关键事件单独提醒**（`TG 推送 → 📨 关键事件单独提醒`，默认关）：静默提醒 / 静默汇总 / 人脸命中 / **待录入满库**四类事件，除正常渠道外**再通过 TG 机器人私聊**给「授权用户 + 额外 `chatIds`」。⚠️ 接收人**必须先在 TG 里私聊过机器人**（Telegram 不允许机器人主动找从没对话过的用户）；**人脸命中不受静默影响**；设置页「试发」只发主会话、不打扰别人。详见 5.5.1，人脸命中在汇总/查岗里如何单列见 5.7.1。
>
> **「待录入满库」提醒**（每类可单独关）：未建档人脸攒到收集上限（**100 张**）时提醒一次去处理。
> **每个填满周期只提醒一次** —— 满库后继续满不会刷屏；处理过（录入 / 忽略使数量降下来）
> 并**再次填满**才会再提醒。判据「已提醒过」落在 SQLite 的 kv（`pendingFull`）里，
> 所以**自愈重启不会重复提醒**。状态机是独立模块 `server/pending-full.mjs`（纯函数、可注入），
> 由「新插入一条待录入」「删掉一条待录入」两处驱动。

## 十一、常见问题与排障

**Q：所有通道都是「拉流失败」，但同一路流在前端页面播得好好的？**
ffmpeg 版本问题。市面 ws-flv 大量使用增强型 FLV（`codecId=0` + FourCC `hvc1`），`ffmpeg-static` 的 6.0 解不了，且**静默不出帧、不打日志**。确认 ffmpeg ≥ 7：看启动日志里的版本号，或用 `BOSSMONITOR_FFMPEG` 指定一个 9.x。

**Q：自动重启之后服务直接停机了？**
已在 `restart.mjs` 修复（端口释放 → spawn → 自检 → 回滚）。如果还遇到，看设置 → 系统维护的诊断面板：上次结果 / 原因 / 连续失败次数 / 日志路径，或 `GET /api/restart-status`、`server/data/restart.log`。

**Q：远程 `/reboot` 没反应？**
先看 `allowReboot` 开了没；再看是不是连败触发了风暴保护（手动/远程 `force` 不受限，但自动重启会被暂停）；最后看 `GET /api/restart-status` 的 `consecFailures`。

**Q：后端服务一启动就一直在反复重启？**
Telegram 侧积压了旧的 `/reboot confirm`，被反复重放执行。用 `node server/headless-monitor.mjs --drop-pending` 启动一次即可（日志会报出清掉了几条），之后正常启动就行。根因与修复见 [5.12](#512-启动重放与积压为什么一启动就反复重启)。

已经升级过的话，正常情况下**不会**再重放（游标落盘 + 环境变量双通道），而且有三道拦截：远程重启**熔断**（10 分钟内因 TG 指令重启超 3 次即拒绝，回执里说明还要等多久）、**循环保护**（10 分钟内成功重启超 4 次即拒绝）、**风暴保护**（连续失败 3 次即暂停自动重启）。诊断面板（设置 → TG 推送）会显示积压条数 `pendingUpdates` 与游标 `lastUpdateId`。

**Q：硬重启之后监控没回来？**
硬重启只负责重启机器，**不会**帮你把服务拉起来。必须先配开机自启。

**Q：硬件重启报权限不足？**
Windows 需管理员；macOS 需给本进程「辅助功能」授权；Linux 需 root 或免密 sudo。模块会返回可读提示，不会静默失败。

**Q：钉钉推送测试失败，控制台看起来像跨域？**
用后端模式（后端内置了三个代理）；或确认 `useProxy` 开着、且代理前缀在 `vite.config.js` / `electron/main.cjs` / `headless-monitor.mjs` **三处保持一致**（不一致会让某个渠道静默失效）。

**Q：推送统计 / 事件清空后，顶部的今日报警数也归零了？**
不会。每日统计走 `useDailyStats` 独立存储，不受事件条数淘汰与清空影响。

**Q：Windows 上执行 `/reboot confirm` 之后，反复弹出好几个终端窗口，关掉又弹？**
这是「detached 的新进程没有控制台」引起的：Windows 会给无控制台进程创建的控制台程序（ffmpeg）单独分配一个可见窗口，于是**每路摄像头弹一个**，流断开重连再弹一次。已通过给所有 `spawn` 加 `windowsHide: true` 修掉；若仍能复现，说明启动脚本/二进制是你自己改过的版本。详见 5.13。

**Q：想彻底重置后端？**
删掉 `server/data/` 即重置（数据库 + 快照 + 重启台账 + TG 指令游标 `tg-offset.json` + 远程重启熔断台账 `tg-reboot.json` + 登录会话 `auth-sessions.json` 全在里面）。只清事件不清配置的话，用设置里的「清空事件」。

**Q：打不开页面，一直停在登录页 / 提示「账号或密码不正确」，但我确认没输错？**
按顺序查三件事：① 是不是被失败节流锁了 —— 连错 5 次锁 60 秒，**锁定期内正确口令也会被拒**，界面上会写「尝试次数过多，请在 N 秒后重试」，等一分钟再试；② 后端是否可达 —— 登录页左下角写着「检测服务已连接」才是服务端校验，否则走的是本地兜底，两边凭据可能不是同一份；③ 口令到底改没改过 —— 后端 `server/config.json` 里有 `auth` 段就先看它，没有才用内置默认（`src/config/auth.js`）。
口令**没法反查**（只存摘要），忘了就重新生成一份：见 5.14 的两行命令。

**Q：遮罩的解锁密码忘了，或者设置里那个框是空的，是不是我的密码丢了？**
都不是。配置里只存摘要，所以**界面上从来不回显**已设的密码 —— 输入框空着是正常现象，状态片写着「已设密码」就说明密码还在。忘了也不影响使用：到「设置 → 隐私遮罩」输入一个新密码（或点「清除密码」改成免密码），点「保存并应用」即可覆盖。老版本存在配置里的**明文**遮罩密码会在载入时被自动换算成摘要并把明文字段删掉，不需要你手工改（见 5.15）。

**Q：登录页上「身份校验」写着「本地兜底校验 / 离线沿用会话」，是不是坏了？**
不是。这是刻意留的退路：后端不可达时（后端没起、局域网抖动、或你用的是 `npm run serve` 这种**纯静态预览**——它没有 `/api` 反代）仍然让你进得去，代价是那一刻的身份校验发生在浏览器里。要回到服务端校验，起 `npm run server` 再刷新即可。

**Q：为什么我一打开页面还是先看到登录页？不是记住我了吗？**
「保持登录」（默认勾选）有效期 30 天，会话存在 localStorage。以下情况需要重新登录：换了浏览器 / 无痕窗口 / 清了站点数据、勾掉了「保持登录」（只存在 sessionStorage，关标签页即失效）、后端点「退出登录」（服务端那枚 token 同时作废）、或者会话被另一台后端的地址变更判为无效（`后端地址已变更，请重新登录`）。

## 十二、技术栈

| 层 | 选型 |
|---|---|
| 前端框架 | Vue 3（组合式 API）+ Vite 6，**无路由、无状态库**，全部逻辑收在 composable |
| 实时播放 | Jessibuca（WASM 软解，H.264 / H.265，ws-flv） |

| AI 推理（后端） | onnxruntime-node |
| 模型 | `yolo11n` / `yolo11s`（人形）、`scrfd-500m`（人脸检测）、`mobilefacenet`（人脸特征）、`yolov8n-pose`（姿态） |
| 后端 | Node 原生 `http` + `ws`，无 Web 框架 |
| 存储（后端） | better-sqlite3（WAL 模式），快照落磁盘 |
| 存储（前端） | IndexedDB（事件 + 人脸库） |
| 图像处理 | `jpeg-js` + 自实现的位图与最小 Canvas 2D（`imageops.mjs`） |
| 视频解码 | ffmpeg（≥7，首次运行自动下载到 `server/.cache/`） |
| 桌面端 | Electron 44 + electron-builder |
| 移动端 | Capacitor 8（iOS）+ 原生 SwiftUI（watchOS） |
| 小程序 | 微信小程序 web-view 壳 |
| 构建脚本 | 纯 Node 内置模块，零依赖 |
