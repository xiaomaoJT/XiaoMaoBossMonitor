# 推送通道远程控制方案（提案，未实施）

> 对应需求第 8 条：「能否通过接收推送的设备，与之交互，远程控制系统（推送静默、恢复推送、重启等能力）」。
> 本文是**方案设计**，代码里一行都没改。确认方向后再实施。

---

## 一、先说结论：可行，但有一个硬前提

**能做到**，而且不需要新增任何依赖。但**必须先解决"回调怎么回到后端"这个问题**——这是整个方案唯一的难点，也是决定它能不能落地的关键。

三端目前都只做单向 `fetch(webhook)` 推送，代码里**没有任何回调/交互相关实现**（已核实：`useDingTalk` / `useWeCom` / `useTelegram` 三个文件里搜不到 `actionCard`、`template_card`、`inline_keyboard`、`callback` 任何一个）。后端只监听 `0.0.0.0:8787` 的内网 HTTP。

所以：**"发得出去"已经有了，"收得回来"需要新建一条链路。**

---

## 二、三端能力对比（决定做哪个方案）

| 渠道 | 交互形态 | 需要公网 HTTPS 回调？ | 签名校验 | 实施难度 |
|---|---|---|---|---|
| **Telegram** | 消息下方 `inline_keyboard` 按钮；点击后回调 `callback_query` | **需要**（Webhook 必须是公网 HTTPS） | Bot Token | ★★ 最低 |
| **企业微信** | `template_card` 交互卡片，点击回调到配置的 URL | **需要** | 签名加解密（AES） | ★★★ 中 |
| **钉钉** | 交互卡片 `actionCard` + 回调地址 | **需要** | 加签 + 卡片回调 | ★★★★ 高 |

三端都要公网 HTTPS，这是**共同前提**。

### 关键判断

- **Telegram 最适合先做**：无需卡片签名（只校验 Bot Token）、交互形态最标准、官方文档最全。
- **钉钉/企微要做，需要申请"互动卡片"权限**，不是勾一下就有——个人版钉钉机器人**不支持**交互卡片回调（只有企业内部应用才行）。如果你的机器人是群里那个 Webhook 地址，**这条路直接走不通**。

## 三、整体架构

```
┌──────────────┐                ┌─────────────────────┐
│  你在手机上   │  点「静默2小时」  │  钉钉/企微/TG 平台   │
│  点卡片按钮   │ ──────────────> │  （托管回调）        │
└──────────────┘                └──────────┬──────────┘
                                          │ HTTPS 回调（带签名）
                                          ▼
                              ┌───────────────────────┐
                              │  公网入口（必须新增）   │
                              │  cloudflared / frp /   │
                              │  ngrok / 自有域名+证书  │
                              └──────────┬────────────┘
                                         │ 本地隧道
                                         ▼
                              ┌───────────────────────┐
                              │  BossMonitor 后端      │
                              │  :8787  POST /api/cmd  │
                              │  ① 验签               │
                              │  ② 白名单校验          │
                              │  ③ 执行 + 回执         │
                              └───────────────────────┘
```

**为什么必须加公网入口**：回调请求是平台主动发起的，你的机器在局域网内没有固定公网 IP，平台找不到你。三种落地方式：

| 方式 | 说明 | 适合 |
|---|---|---|
| **Cloudflare Tunnel**（推荐） | 装个客户端，一条命令给出 `https://xxx.trycloudflare.com`，有自动证书 | 临时/长期都可用，免费 |
| **frp / cpolar** | 需要一台有公网 IP 的机器做中转 | 已有服务器 |
| **自有域名 + Let's Encrypt** | 最正规，但要维护 DNS 和证书续期 | 长期生产 |

## 四、指令集设计（建议先做这 6 条）

| 指令 | 语义 | 已有能力可直接复用 |
|---|---|---|
| `silent 2h` | 开启临时静默 2 小时（开启即推一条「免打扰已开启」提醒到三端） | ✅ **本次已实现** `startTempSilent(h, channels, label, untilAt)` |
| `silent until 08:00` | 静默到明早 8 点 | ✅ 同上（支持绝对时间） |
| `resume` | 提前结束静默，并推送「免打扰已结束」提醒 + 汇总 | ✅ **本次已实现** `endTempSilent(true)` |
| `patrol` | 立即推送一次巡检报告 | ✅ 已有 `/api/patrol` |
| `reboot` | 重启检测服务（**先释放端口 → 拉起新进程 → 自检接管 → 失败自动回滚**） | ✅ **本次已实现**，走 `server/restart.mjs` |
| `hardreboot` | 重启**整台电脑**（最后手段；需管理员/root 权限 + 已配开机自启） | ✅ **本次已实现**，走 `server/hard-reboot.mjs`，默认关闭 |
| `status` | 回一条当前状态（在线路数/静默状态/最近报警） | ✅ 读 `state` 即可 |
| `check duty` | **静默查岗**：把静默期间积压的事件汇总推过来（含**全部截图**）；再发一次只看上次查岗之后的新事件 | ✅ **本次已实现**，走 `server/duty-check.mjs` |

> **关于 `reboot` 的实现要点（本次踩过的坑）**
>
> 老实现是「spawn 一个新进程 → 400ms 后 `process.exit(0)`」，实测会把重启变成**停机**：
> ① 旧进程 400ms 后才释放端口，而新进程何时 listen 不确定 → 撞上 `EADDRINUSE`；
> ② `srv.listen()` 没有 error 监听，异常被 `uncaughtException` 兜底吞掉 →
>    新进程**活着但没人监听端口**，旧进程又已退出 ⇒ 页面与 API 全不通；
> ③ spawn 完就退出，从不确认新进程是否真的起来了；
> ④ 旧的 `restarting` 标志一旦置位永不复位 ⇒ 第一次失败后**后续所有重启请求（含远程 /reboot）被静默忽略**；
> ⑤ `/api/restart` 路由写在模块级 `server()` 里，而 `requestSystemRestart` 定义在 `main()` 内部
>    —— 作用域根本看不到，点「立即重启」只会产生一条 `ReferenceError`。
>
> 现在的顺序是：**先 `await` 关闭 HTTP server 真正释放端口 → 再 spawn（绝对脚本路径 + 显式 cwd +
> stdout/stderr 落 `restart.log`）→ 轮询 `/api/status` 校验 `startedAt` 确实变新 → 成功才退出；
> 超时则回滚（本进程重新 listen）并告警**。另有重启风暴保护：短时间内连续失败会暂停自动重启，
> 避免反复把服务打停；手动/远程触发不受此限制（`force`）。

> **关于 `check duty`（静默查岗）的实现要点**
>
> 场景：半夜开着静默，人不在手机旁边，想中途看一眼「静默开始到现在积压了什么」。
>
> - **区间怎么划**：第一次 = 静默窗口开始 → 现在；再发一次 = 上次查岗 → 现在（增量）。
>   静默窗口的开始时刻存在 `silent.tempSince`（夜间定时时段则用时段自身的起点）；
>   增量游标存在 SQLite 的 `kv` 表（`dutyCursor`），所以后端自愈重启后不会重复推。
> - **为什么查库不查内存缓冲**：`useAlertPush.silentBuffer` 里只存了文字字段，**没有截图路径**；
>   用户要的是「图片全部推送过来」，只能从 `events` 表拿 `thumb`（`shots/` 下的相对路径）再读文件。
>   顺带解决了「进程重启后缓冲清空」的问题。
> - **游标为什么用 `created_at` 而不是 `time`**：`time` 是分析器判定时刻，落库在它之后；
>   按 `time` 做游标会漏掉「查询跑在 time 之后、入库之前」那几十毫秒里的事件。
> - **截图为什么串行 + 留间隔**：Telegram 对同一会话的连续 `sendPhoto` 有频率限制，
>   并发发图大概率被 429 拒掉，一旦触发后面的图会连着失败。默认间隔 700ms
>   （`telegram.remote.dutyImageGapMs`），可在设置里调。
> - **不阻塞指令监听**：汇总先发（确认能发出去再回执），截图丢到后台串行推 ——
>   几十张图要几十秒，若同步等待，期间 TG 长轮询被卡住，什么指令都收不到。
> - **三种提示**：不在静默时段 / 静默中但没有事件 / 静默中但都已查过，都会明确回一句。
> - **结果发到哪**：发回**你发指令的那个私聊**，而不是配置里的 `chatId` ——
>   后者很可能是群，两边对不上会让人找不到结果。
> - **防呆**：单次最多 200 张（代码内硬上限，`dutyMaxImages: 0` 表示不限但仍受它约束）；
>   连续 3 次读图/发送失败即中止（通常是限流或网络断）。

**指令解析建议**：正则 `^/(\w+)(?:\s+(.+))?$`，只认 `/` 开头（避免和正常聊天误触发）。`broadcast` 里 `chatId` 已经是固定的，天然限制了谁能发指令。

## 五、安全设计（这部分比功能更重要）

远程能"重启机器"，权限边界必须写死。**七道防线**：

1. **只认私聊**：Telegram 检查 `chat.id === cfg.telegram.chatId`；企微/钉钉检查 `from.userId` 在白名单里。**群聊里任何人都能触发 = 立刻被夺权。**
2. **群聊里禁用**：`chat.type !== 'private'` 直接丢弃。
3. **共享密钥**：指令带一个 `token` 参数（可配），不匹配直接忽略。防止有人猜到命令格式。
4. **验签必做**：企微要校验 `msg_signature`（AES 解密），钉钉要校验签名，TG 校验 Bot Token。**不能只靠"知道 URL 就能发命令"。**
5. **时间窗防重放**：记录 `callback_id` / 消息 ID，重复的直接丢弃；并校验时间戳在 5 分钟内。
6. **危险操作二次确认**：
   - `reboot` 不立即执行，回一条「确认重启请回复 `/reboot confirm`」。
   - 建议**加白名单时段**——比如深夜不响应重启。
7. **全量审计**：每条指令记 `时间 / 来源 userId / 指令 / 执行结果`，写进日志，出事能查。

另外**强烈建议**：`reboot` 这类能力默认**关闭**，需要在设置里显式开启（就像现在的"系统维护"那样分层）。远程重启是典型的"小配置变大事故"。

## 六、实施步骤（分 4 期，建议按顺序）

### 第 1 期：打通链路（只做 Telegram）
1. 建 `server/remote/` 模块：`verify.js`（验签）、`router.js`（指令分发）、`audit.js`（审计日志）。
2. 后端加 `POST /api/remote/tg` 接收 `callback_query`。
3. 给 `useTelegram.js` 加 `inline_keyboard` 发送能力（现在没有）。
4. 本地起 cloudflared 隧道联调。

### 第 2 期：指令集落地
5. 接入 `startTempSilent` / `endTempSilent` / 巡检（**这几个 API 这次已经写好了，第 2 期几乎不用改业务代码**）。
6. 群聊禁用 + 白名单 + 共享密钥。
7. 审计日志 + 「远程控制」设置页（开关 / 白名单 / 密钥）。

### 第 3 期：补齐钉钉 / 企微
8. 企微 `template_card` + 回调加解密。
9. 钉钉交互卡片（**先确认你的机器人类型支持不支持回调，不支持就只做企微**）。

### 第 4 期：安全加固
10. `reboot` 二次确认 + 时段白名单。
11. 全量审计视图。

## 七、备选方案（如果不想开公网入口）

**方案 B：只读回执，不做控制。** 推送里带一个"状态查询"链接，点开是带 token 的网页（渲染在公网托管的静态页 / 或内网穿透），跳转到详情页。能看不能控，**风险几乎为零**。

**方案 C：Telegram Bot 私聊 + 命令。** 不做卡片，就当个聊天机器人用：
```
/silent 2h
/status
```
实现最简单（只需长轮询 `getUpdates`，**不需要公网入口**），但要设备端主动发消息、体验不如按钮。

> 如果你的核心诉求是"手机上少点几下"，**方案 C 的成本最低、风险最低**，可以先跑通再升级到卡片。

## 八、我的建议

| 你的情况 | 建议 |
|---|---|
| 只想临时静音/恢复 | **方案 C**（Telegram 命令行），半天上线，零公网暴露 |
| 想要卡片按钮的完整体验 | 方案 A + Telegram + Cloudflare Tunnel，1~2 天 |
| 钉钉是群机器人 Webhook | 交互卡片**走不通**，只能退回方案 B/C |

**先确认两件事，我再动手：**
1. 你的钉钉机器人是**群机器人 Webhook** 还是**企业内部自建应用**？（决定钉钉这条路通不通）
2. 你能接受为这台机器开一个公网 HTTPS 入口吗？（不开就只能走方案 C）
