# 推送通道远程控制方案（提案，未实施）

> 对应需求第 8 条：「能否通过接收推送的设备，与之交互，远程控制系统（推送静默、恢复推送、重启等能力）」。
> 本文是**方案设计**，代码里一行都没改。确认方向后再实施。

---

## 一、先说结论：可行，但有一个硬前提

**能做到**，而且不需要新增任何依赖。但**必须先解决"回调怎么回到后端"这个问题**——这是整个方案唯一的难点，也是决定它能不能落地的关键。

三端目前都只做单向 `fetch(webhook)` 推送，代码里**没有任何回调/交互相关实现**（已核实：`useDingTalk` / `useWeCom` / `useTelegram` 三个文件里搜不到 `actionCard`、`template_card`、`inline_keyboard`、`callback` 任何一个）。后端只监听 `0.0.0.0:8787` 的内网 HTTP。

所以：**"发得出去"已经有了，"收得回来"需要新建一条链路。**

---

## 二、三端能力对比（决定做哪个方案）

| 渠道 | 交互形态 | 需要公网 HTTPS 回调？ | 签名校验 | 实施难度 |
|---|---|---|---|---|
| **Telegram** | 消息下方 `inline_keyboard` 按钮；点击后回调 `callback_query` | **需要**（Webhook 必须是公网 HTTPS） | Bot Token | ★★ 最低 |
| **企业微信** | `template_card` 交互卡片，点击回调到配置的 URL | **需要** | 签名加解密（AES） | ★★★ 中 |
| **钉钉** | 交互卡片 `actionCard` + 回调地址 | **需要** | 加签 + 卡片回调 | ★★★★ 高 |

三端都要公网 HTTPS，这是**共同前提**。

### 关键判断

- **Telegram 最适合先做**：无需卡片签名（只校验 Bot Token）、交互形态最标准、官方文档最全。
- **钉钉/企微要做，需要申请"互动卡片"权限**，不是勾一下就有——个人版钉钉机器人**不支持**交互卡片回调（只有企业内部应用才行）。如果你的机器人是群里那个 Webhook 地址，**这条路直接走不通**。

## 三、整体架构

```
┌──────────────┐                ┌─────────────────────┐
│  你在手机上   │  点「静默2小时」  │  钉钉/企微/TG 平台   │
│  点卡片按钮   │ ──────────────> │  （托管回调）        │
└──────────────┘                └──────────┬──────────┘
                                          │ HTTPS 回调（带签名）
                                          ▼
                              ┌───────────────────────┐
                              │  公网入口（必须新增）   │
                              │  cloudflared / frp /   │
                              │  ngrok / 自有域名+证书  │
                              └──────────┬────────────┘
                                         │ 本地隧道
                                         ▼
                              ┌───────────────────────┐
                              │  BossMonitor 后端      │
                              │  :8787  POST /api/cmd  │
                              │  ① 验签               │
                              │  ② 白名单校验          │
                              │  ③ 执行 + 回执         │
                              └───────────────────────┘
```

**为什么必须加公网入口**：回调请求是平台主动发起的，你的机器在局域网内没有固定公网 IP，平台找不到你。三种落地方式：

| 方式 | 说明 | 适合 |
|---|---|---|
| **Cloudflare Tunnel**（推荐） | 装个客户端，一条命令给出 `https://xxx.trycloudflare.com`，有自动证书 | 临时/长期都可用，免费 |
| **frp / cpolar** | 需要一台有公网 IP 的机器做中转 | 已有服务器 |
| **自有域名 + Let's Encrypt** | 最正规，但要维护 DNS 和证书续期 | 长期生产 |

## 四、指令集设计（建议先做这 6 条）

| 指令 | 语义 | 已有能力可直接复用 |
|---|---|---|
| `silent <小时数> [渠道]` | 开启临时静默 N 小时，如 `/silent 2`（开启即推一条「免打扰已开启」提醒）。**不写渠道就走设置页配的默认**，也可临时指定 `/silent 2 wecom`、`/silent 2 ding,tg` | ✅ 已实现 `startTempSilent(h, channels, label, untilAt)` + `resolveSilentChannels()` |
| `silent until 08:00 [渠道]` | 静默到明早 8 点，同样可跟渠道 | ✅ 同上（支持绝对时间） |
| `resume` | 提前结束静默，并推送「免打扰已结束」提醒 + 汇总 | ✅ **本次已实现** `endTempSilent(true)` |
| `patrol` | 立即推送一次巡检报告 | ✅ 已有 `/api/patrol` |
| `reboot` | 重启检测服务（**先释放端口 → 拉起新进程 → 自检接管 → 失败自动回滚**） | ✅ **本次已实现**，走 `server/restart.mjs` |
| `hardreboot` | 重启**整台电脑**（最后手段；需管理员/root 权限 + 已配开机自启） | ✅ **本次已实现**，走 `server/hard-reboot.mjs`，默认关闭 |
| `status` | 回一条当前状态（在线路数/静默状态/最近报警） | ✅ 读 `state` 即可 |
| `check duty` | **静默查岗**：把静默期间积压的事件汇总推过来（含**全部截图**）；再发一次只看上次查岗之后的新事件 | ✅ **本次已实现**，走 `server/duty-check.mjs` |

> **关于 `reboot` 的实现要点（本次踩过的坑）**
>
> 老实现是「spawn 一个新进程 → 400ms 后 `process.exit(0)`」，实测会把重启变成**停机**：
> ① 旧进程 400ms 后才释放端口，而新进程何时 listen 不确定 → 撞上 `EADDRINUSE`；
> ② `srv.listen()` 没有 error 监听，异常被 `uncaughtException` 兜底吞掉 →
>    新进程**活着但没人监听端口**，旧进程又已退出 ⇒ 页面与 API 全不通；
> ③ spawn 完就退出，从不确认新进程是否真的起来了；
> ④ 旧的 `restarting` 标志一旦置位永不复位 ⇒ 第一次失败后**后续所有重启请求（含远程 /reboot）被静默忽略**；
> ⑤ `/api/restart` 路由写在模块级 `server()` 里，而 `requestSystemRestart` 定义在 `main()` 内部
>    —— 作用域根本看不到，点「立即重启」只会产生一条 `ReferenceError`。
>
> 现在的顺序是：**先 `await` 关闭 HTTP server 真正释放端口 → 再 spawn（绝对脚本路径 + 显式 cwd +
> stdout/stderr 落 `restart.log`）→ 轮询 `/api/status` 校验 `startedAt` 确实变新 → 成功才退出；
> 超时则回滚（本进程重新 listen）并告警**。另有重启风暴保护：短时间内连续失败会暂停自动重启，
> 避免反复把服务打停；手动/远程触发不受此限制（`force`）。

> **关于 `check duty`（静默查岗）的实现要点**
>
> 场景：半夜开着静默，人不在手机旁边，想中途看一眼「静默开始到现在积压了什么」。
>
> - **区间怎么划**：第一次 = 静默窗口开始 → 现在；再发一次 = 上次查岗 → 现在（增量）。
>   静默窗口的开始时刻存在 `silent.tempSince`（夜间定时时段则用时段自身的起点）；
>   增量游标存在 SQLite 的 `kv` 表（`dutyCursor`），所以后端自愈重启后不会重复推。
> - **为什么查库不查内存缓冲**：`useAlertPush.silentBuffer` 里只存了文字字段，**没有截图路径**；
>   用户要的是「图片全部推送过来」，只能从 `events` 表拿 `thumb`（`shots/` 下的相对路径）再读文件。
>   顺带解决了「进程重启后缓冲清空」的问题。
> - **游标为什么用 `created_at` 而不是 `time`**：`time` 是分析器判定时刻，落库在它之后；
>   按 `time` 做游标会漏掉「查询跑在 time 之后、入库之前」那几十毫秒里的事件。
> - **截图为什么串行 + 留间隔**：Telegram 对同一会话的连续 `sendPhoto` 有频率限制，
>   并发发图大概率被 429 拒掉，一旦触发后面的图会连着失败。默认间隔 700ms
>   （`telegram.remote.dutyImageGapMs`），可在设置里调。
> - **不阻塞指令监听**：汇总先发（确认能发出去再回执），截图丢到后台串行推 ——
>   几十张图要几十秒，若同步等待，期间 TG 长轮询被卡住，什么指令都收不到。
> - **三种提示**：不在静默时段 / 静默中但没有事件 / 静默中但都已查过，都会明确回一句。
> - **结果发到哪**：发回**你发指令的那个私聊**，而不是配置里的 `chatId` ——
>   后者很可能是群，两边对不上会让人找不到结果。
> - **防呆**：单次最多 200 张（代码内硬上限，`dutyMaxImages: 0` 表示不限但仍受它约束）；
>   连续 3 次读图/发送失败即中止（通常是限流或网络断）。

**指令解析建议**：正则 `^/(\w+)(?:\s+(.+))?$`，只认 `/` 开头（避免和正常聊天误触发）。`broadcast` 里 `chatId` 已经是固定的，天然限制了谁能发指令。

## 四之补：「配好了却无响应」的三个坑（实测踩过）

### 坑 1：开关热不了 —— 只能在进程启动那一刻判一次

监听器原来只有这么一段：

```js
if (remoteCfg().enabled) {          // ← 启动时读一次，为 false 就永远不建
  state.tgRemote = createCommandListener({ ... })
  state.tgRemote.start()
}
```

后果：**用户在设置页把「远程控制」打开、点保存、配置也确实同步过来了**
（`configRev` 涨了、日志打了「配置已应用」），但监听器根本不存在 ——
私聊机器人发什么都没有任何反应。而且界面上完全看不出来：配置里 `enabled` 是 `true`，
状态片却只能显示"未启运"，两边对不上。表现就是「我明明开了，怎么没反应」。

修法是把它做成**幂等**的 `ensureTgRemote()`，挂在 `state` 上，
由 `applyIncomingConfig`（前端每次保存配置都会打进来的那条路）调用：

```
配置开着、还没建   → 建起来 + 注册命令菜单 + 跑连接自检
配置关了、还建着   → 停掉
Token 换了         → 拆掉重建（菜单要按新机器人注册）
一切照旧           → 直接返回（不重复启动、不刷日志）
```

### 坑 2：409 有两种成因，日志里分不清

`getUpdates` 与 **Webhook 是互斥的**。如果这个 Bot 以前设过 Webhook
（哪怕是几个月前随手设的、早就不用了），`getUpdates` 会一直返回 **409 Conflict**。
而「同一个 Token 有另一个进程在跑」也是 409 —— 两者日志一模一样，
用户很容易一头扎进「是不是前一个后端没退干净」，越查越偏。

现在遇到 409 会**顺手查一次 `getWebhookInfo` 定案**（只查一次，避免每轮都打接口）：
确实是 Webhook 占着，就直接在日志里点明，并提示去 BotFather `/deletewebhook`；
没有 Webhook，才判定为"另一个监听进程"。

### 坑 3：非白名单用户"静默丢弃"是故意的，但用户会以为坏了

安全设计上，非白名单来源**连回执都不给**（回执本身就是能力探测）。
代价是用户那一侧只看得到"没反应"。所以状态里必须留下痕迹：

- `lastRejectId` / `lastRejectReason` / `lastRejectAt` —— 记录**是谁、为什么**被拒；
- `/api/status` 的 `tgRemote.note` 按可能性从高到低逐条判，命中即停，
  直接把结论摆到设置页上（未开启 / 没填 Token / 监听器没跑 / 白名单为空 /
  Webhook 占用 / 自检失败 / 最近被拒）。

### 新增的诊断与动作

| 接口 | 作用 |
|---|---|
| `GET /api/tg-remote` | 完整诊断快照（含 `note`：为什么没在听） |
| `POST /api/tg-remote/test` | 真打一次 Telegram：`getMe`（Token 对不对、机器人是谁）+ `getWebhookInfo`（有没有被占） |
| `POST /api/tg-remote/webhook` | `{action:'delete'}` 一键删 Webhook（含 `drop_pending_updates`，避免把积压旧消息当新指令重放） |

设置页「TG 推送 → 远程控制」里对应一块诊断面板：机器人身份 / Token / 白名单 /
最近被拒 / 结论一句话，外加「测试连接」「删除 Webhook」两个按钮。

> ⚠️ 诊断只回统计与结论，**绝不回 Token、也不回白名单 id** ——
> `/api/status` 是裸 HTTP 接口，回凭据等于把它送出去。

### `/duty` 也要进命令菜单

菜单是按 `COMMANDS` 里的 `cmd` 字段逐个注册的，只注册 `check` 的话，
用户在聊天框输入 `/duty` **不会有候选提示**（手打完整也能执行，但没人猜得到）。
所以 `check` 与 `duty` **两个都注册**，输入 `/` 后两条都能看到，各自带用途说明。
`/checkduty` 仍可用，只是不进菜单（三个别名堆在菜单里太吵）。

## 四之补（二）：启动重放 —— 「一启动就反复重启」

第 4 个坑，也是最凶的一个：**服务一启动就无限重启**。
它不是上面三个「没响应」的变体，而是「响应得太积极」——同一条旧指令被反复执行。

### 成因：三件事叠加

**① `getUpdates` 是确认式的。**
Telegram 只有在收到「**下一次带更大 `offset`** 的 `getUpdates`」时，才认为之前那批
update 已送达并**真正删除**。而且：

- 带 `offset=N` → 返回 `update_id >= N`，并删除 `update_id < N`（这才是确认）；
- **不带 `offset`** → 返回**全部未确认**的积压，而且**一条都不删**。

所以只要服务在「确认之前」退出，那批 update 就原封不动留在队列里等着被再取一次。

**② 指令游标原先只在内存里。**

```js
let lastUpdateId = 0   // 重启归零
// 下面这行注释写着「避免重放历史指令」，实际行为**正好相反**：
lastUpdateId = 0       // → URL 走「不带 offset」那一支 → 返回全部积压
```

注释表达的是意图，实现却是「把积压全部重放」。这是最容易骗过 review 的一类 bug ——
代码看起来在防重放，实际在制造重放。

**③ 远程 `/reboot` 走 `force: true`，故意跳过风暴保护。**
`restart.mjs` 的风暴保护统计的是「**失败**的重启」，而循环里每一次重启**都是成功的**，
所以它转多久都不会触发。

叠加起来：

```
取到 /reboot confirm → 执行重启 → 进程被换掉、offset 没来得及确认
   → 新进程游标为 0 → 不带 offset 再取一遍 → 同一条又回来了 → 再重启 → …
```

### 三处修复

| 修复 | 位置 | 要点 |
|---|---|---|
| **指令游标落盘** | `tg-remote.mjs` → `data/tg-offset.json` | 启动时从磁盘恢复；**先把游标落盘、再执行业务** |
| **远程重启熔断** | `tg-guard.mjs` → `data/tg-reboot.json` | 10 分钟内超过 3 次就拒绝；**台账必须落盘** |
| **`--drop-pending` 启动参数** | `headless-monitor.mjs` | 手动清一次积压；**要先清空、再启动监听器** |

三处的关键细节，每一个都是「换个写法就失效」：

**游标必须"先落盘再执行"。** 若还是「先执行、后推进游标」，`/reboot` 会在执行过程中
把进程换掉，那条 update 在 Telegram 侧永远停在未确认状态。提前落盘相当于把它标记成
"已消费"，代价是 at-most-once 语义：若在落盘之后、执行之前崩溃，这条指令会**丢失**。
对 `/reboot` 这就是想要的偏向 —— **宁可漏执行一次，也绝不重复执行**。

**熔断计数必须落盘。** 死循环的特征恰恰是"不停把进程换掉"，纯内存计数每轮都被清零，
永远到不了阈值，那个熔断会形同虚设。

**清空积压必须在监听器起来之前。** 顺序反了的话，监听器会先把积压当成新指令取走执行，
等于没清。所以 `--drop-pending` 的处理放在 `ensureTgRemote()` 之前 `await` 掉。

另外：`--drop-pending` **不向自重启拉起的子进程传递**（`createRestarter` 的 `args` 里过滤掉）。
它是"手动清一次"的运维动作；若每轮重启都清，会把重启窗口期里用户刚发的合法指令一起吃掉，
表现为"指令偶尔莫名其妙不生效"。

### 怎么用

```bash
node server/headless-monitor.mjs --drop-pending
```

启动日志会直接回答"到底有没有积压"：

```
🧹 --drop-pending：已清空 3 条积压指令（这些指令不会被执行）
🧹 指令游标已推进到 update_id = 5
🤖 指令游标已恢复（只收 update_id > 5 的新指令，不会重放旧的）
```

平时启动就会看到第二行的「游标已恢复」—— 那是防重放在正常工作。
故障时被熔断拦下的回执里也会直接点名成因：

> 🛑 **重启已被熔断拦截**
> 最近 10 分钟内已因远程指令重启 3 次（上限 3 次）。
> 这通常说明服务陷入了**重启循环** —— 多半是 Telegram 侧积压的旧指令被反复重放执行。
> 请在本地用 `--drop-pending` 参数启动一次清空积压；熔断约 7 分钟后自动解除。

> 上述是"第一版"的防线。后来又补了两层，见下面两节：
> 磁盘游标可能被 Windows 杀软挡掉（**四之补（四）**的环境变量通道），
> 以及"每次都成功"的重启循环风暴保护管不了（**四之补（四）**的循环保护）。

## 四之补（三）：Windows 上重启后弹一堆终端窗口

### 症状

在 Windows 上发 `/reboot confirm`，然后**反复弹出好几个终端窗口，关掉又弹、弹了又关**。
诡异之处是：双击 `start-windows.bat` 启动时**完全看不到**这个现象，只有重启之后才出现。

### 成因：控制台的归属

自愈重启拉起的进程是 `detached: true` —— 在 Windows 上这意味着它**没有控制台**。
而 Windows 会给「由无控制台进程创建的**控制台程序**」自动分配一个新控制台，
也就是一个**可见的终端窗口**（除非显式 `windowsHide` / `DETACHED_PROCESS`）。

ffmpeg 正是控制台程序，而它**每路摄像头一个**：

```
start-windows.bat → node 继承 cmd 的窗口 → ffmpeg 也继承同一个窗口 → 什么都看不见
自愈重启后的新进程 → 没有控制台 → 每个 ffmpeg 各得一个新窗口 → 几路流就弹几个
                                  → 流断开重连（_scheduleRetry）再弹一次 → "反复"
```

所以窗口数量 ≈ 摄像头路数。这解释了「为什么只有重启后才出现」——启动方式不同，
控制台的继承关系就不同。

### 修法：所有运行期 spawn 一律带 windowsHide

| 位置 | 拉起的进程 | 备注 |
|---|---|---|
| `restart.mjs` | node（新进程本身） | 与 `detached: true` 并用，守护性不受影响 |
| `source.mjs` | ffmpeg（每路流一个） | 弹窗的主要来源 |
| `ffmpeg-fetch.mjs` | `ffmpeg -version` / `tar` / `xattr` | 启动探测版本时会闪一下 |

**"一律带上"是有意的**：只有把规则写成"本项目所有 spawn 都带 windowsHide"，
才能用一条自动断言守住它（不变量比逐处判断可靠）。

### 怎么在非 Windows 机器上守住这个缺陷

windowsHide 是 Windows 专有参数，"窗口有没有弹"在 macOS 上测不出来。但可以断言
**传给 spawn 的完整参数**：

```
node --import ./stub.mjs probe.mjs     # /tmp/monitor-win-spawn-probe/
```

`stub.mjs` 用 `module.register()` 把 `node:child_process` 换成记录桩
（记录 bin / args / windowsHide / detached / stdio / env / 子进程 pid），
生产代码里**没有任何测试开关**。断言覆盖：

- `StreamSource` 拉 ffmpeg 时带 windowsHide；
- `ffmpeg-fetch` 的版本探测（spawnSync）带 windowsHide；
- 自愈重启拉起的 node 带 windowsHide **且仍是 detached**（加了窗口隐藏不能丢了守护性）；
- 对整份 spawn 记录**全量复核**：任何一次 spawn 漏掉 windowsHide 就变红。

回退验证：把 `windowsHide` 从 `source.mjs` / `restart.mjs` 拿掉 → 4 条断言变红。

## 四之补（四）：光靠磁盘游标还不够（Windows 特供坑）

游标落盘之后，理论上不会重放。但在 Windows 上仍然可能**再犯**：

`fs.renameSync` 覆盖写会被杀软 / 文件索引锁住而报 `EPERM`，而落盘函数里
原来把异常**静默吞掉**了 —— 于是"没写进去"和"写进去了"在运行时毫无区别。
重启照样取到积压，照样重放 `/reboot`。

所以再加一条独立通道，与磁盘互不依赖：

```
父进程 spawn 新进程时 → env MONITOR_TG_OFFSET = 当前 lastUpdateId
新进程启动            → lastUpdateId = max(内存, 磁盘, 环境变量)
                      → 若环境变量更新，顺手补写一次磁盘
```

环境变量不受文件锁影响，所以**磁盘写失败也不会重放**。另外落盘失败现在会记进
`status.tgRemote.offsetSaveError`（设置页诊断面板显示"游标落盘"一行），不再无声降级。

### 为什么要 `max()` 而不是"优先磁盘"

父进程在 spawn 前**已经**把 `/reboot` 那条的 update_id 落过盘（先落盘再执行），
所以父进程内存里的游标必然包含它 —— 取 max 就是取最靠前的那个，任何一条通道
迟到或损坏都不会让游标倒退。

### 第三层：重启循环保护

风暴保护只统计**失败**的重启；而重启循环里每一次重启都是**成功**的，
所以它一次都不会触发。补一层只看"成功"的：

| 保护 | 窗口 | 阈值 | 拦什么 |
|---|---|---|---|
| 风暴保护 | 10 分钟 | 失败 3 次 | 自愈连续失败 |
| 循环保护 | 10 分钟 | 成功 4 次 | 重启循环（含被重放的指令、外部脚本反复拉起） |
| 远程熔断 `tg-guard` | 10 分钟 | TG 指令 3 次 | 远程指令触发的重启循环 |

三者都**落盘**（内存计数在"不停换进程"的场景下等于没有保护），
被拦下时都会给回执/通知说明成因与解除时间。

## 五、安全设计（这部分比功能更重要）

远程能"重启机器"，权限边界必须写死。**七道防线**：

1. **只认私聊**：Telegram 检查 `chat.id === cfg.telegram.chatId`；企微/钉钉检查 `from.userId` 在白名单里。**群聊里任何人都能触发 = 立刻被夺权。**
2. **群聊里禁用**：`chat.type !== 'private'` 直接丢弃。
3. **共享密钥**：指令带一个 `token` 参数（可配），不匹配直接忽略。防止有人猜到命令格式。
4. **验签必做**：企微要校验 `msg_signature`（AES 解密），钉钉要校验签名，TG 校验 Bot Token。**不能只靠"知道 URL 就能发命令"。**
5. **时间窗防重放**：记录 `callback_id` / 消息 ID，重复的直接丢弃；并校验时间戳在 5 分钟内。
6. **危险操作二次确认**：
   - `reboot` 不立即执行，回一条「确认重启请回复 `/reboot confirm`」。
   - 建议**加白名单时段**——比如深夜不响应重启。
7. **全量审计**：每条指令记 `时间 / 来源 userId / 指令 / 执行结果`，写进日志，出事能查。

另外**强烈建议**：`reboot` 这类能力默认**关闭**，需要在设置里显式开启（就像现在的"系统维护"那样分层）。远程重启是典型的"小配置变大事故"。

## 七、备选方案（如果不想开公网入口）

**方案 B：只读回执，不做控制。** 推送里带一个"状态查询"链接，点开是带 token 的网页（渲染在公网托管的静态页 / 或内网穿透），跳转到详情页。能看不能控，**风险几乎为零**。

**方案 C：Telegram Bot 私聊 + 命令。** 不做卡片，就当个聊天机器人用：
```
/silent 2            # 静默 2 小时（默认只静默钉钉 + 企微，TG 留着收发指令）
/silent 2 ding,tg    # 也可以临时指定静默哪几端
/status
```
实现最简单（只需长轮询 `getUpdates`，**不需要公网入口**），但要设备端主动发消息、体验不如按钮。

**静默渠道是可控的**（已实施）：`/silent`、`/until` 后面可以跟渠道名
（`ding`/`dd`/`钉钉`、`wecom`/`wx`/`企微`、`tg`/`telegram`/`电报`，分隔符空格或 `,`、`，`、`、`、`/`、`|`），
不写就走设置页「TG 推送 → 远程控制 → 可用指令」里配的那份默认 —— **默认刻意只有钉钉 + 企微**，
因为 TG 是下发指令的通道，把它一起静默掉就连「静默开没开」的回执都收不到了。
渠道被全部取消勾选时**拒绝开启并提示**（不是"静默全部"，也不回落成默认）；
勾了但没配好的渠道会被跳过并在回执里点名。

> 如果你的核心诉求是"手机上少点几下"，**方案 C 的成本最低、风险最低**，可以先跑通再升级到卡片。

| 你的情况 | 建议 |
|---|---|
| 只想临时静音/恢复 | **方案 C**（Telegram 命令行），半天上线，零公网暴露 |
